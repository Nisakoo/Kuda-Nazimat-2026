# Хранилище: встроенный `node:sqlite` в основном процессе

## Context and Problem Statement

Серверу нужно хранить аккаунты, сессии, позиции игроков, историю диалогов NPC, прогресс BABEL и состояние живого мира между запусками — без интернета, без отдельной установки БД, для ≤4 игроков.

## Decision Drivers

* Нет внешних сервисов и дополнительных процессов.
* Нагрузка: ≤4 игрока, запросы доли миллисекунды, пакетное сохранение раз в 10 с.
* Простое резервное копирование на ноутбуке администратора.

## Considered Options

* SQLite через встроенный `node:sqlite` (`DatabaseSync`) в основном процессе (выбрано)
* Отдельный worker для БД (оценён как ненужный для MVP)
* Облачная БД (вне scope)

## Decision Outcome

SQLite (`node:sqlite`, режим WAL, `foreign_keys=ON`), файл на сервере. Схема меняется нумерованными SQL-миграциями при старте в транзакции; неизвестная более новая версия БД — ошибка запуска. Игровой шаг к БД не обращается; позиции сохраняются по таймеру. Запросы параметризованы. Бэкап — `VACUUM INTO`.

### Consequences

* Good: ноль внешних зависимостей; атомарные транзакции (ответ NPC пишется до доставки; BABEL-агрегаты вместе с receipt).
* Bad: синхронные вызовы в главном потоке; при росте нагрузки потребуется worker.
* Bad: БД и бэкапы не шифруются.
* Bad: окно потери при аварии — до `saveIntervalMs` (10 с).

### Confirmation

`migrations.test.ts`, `crash-recovery` (kill через 5 с, `PRAGMA integrity_check`), тест бэкапа и восстановления на отдельной копии.

## Pros and Cons of the Options

### `node:sqlite` в основном процессе

* Good: просто, быстро для ≤4 игроков.
* Bad: вызовы синхронные в главном потоке (поэтому игровой шаг к БД не обращается).

### Отдельный worker

* Bad: усложнение без измеренной необходимости; допускается только при замере.
