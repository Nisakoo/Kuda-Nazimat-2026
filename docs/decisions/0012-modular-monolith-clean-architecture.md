# Один процесс: модульный монолит с чистыми слоями и одним composition root

## Context and Problem Statement

Сервер ведёт авторитетный мир, вход, сохранения и NPC на одном ноутбуке для ≤4 игроков. Нужно выбрать структуру кода, которая остаётся тестируемой и не превращается в оверинжиниринг. Те же принципы применяются к клиенту (`GameApp`).

## Decision Drivers

* Игровой шаг синхронный и детерминированный; домен тестируется без сети и БД.
* Явные зависимости без магии; единственное место сборки.
* Тяжёлый inference изолируется процессом, остальное — в одном приложении.

## Considered Options

* Модульный монолит: домен → сервисы → тонкие адаптеры, порты только на реальных границах, composition root `app` (выбрано)
* Микросервисы
* DI-контейнер, generic event bus, CQRS, generic-репозитории, абстрактные фабрики, плагинные системы

## Decision Outcome

Один процесс Node. Домен (мир, движение, AOI, delta, коллизии) — детерминированный код без IO, таймеров и `Date.now()`; время через `dt` и порт `Clock`. Сервисы оркестрируют домен и порты, не зная о Socket.IO, HTTP и SQL. Порты объявляет потребитель и только на реальной границе (хранилища, `NpcResponder`, `LanguagePort`, `Clock`). Адаптеры тонкие; коды PROTO и HTTP-статусы назначаются только в адаптере. Зависимости передаются в конструктор из `app`. Реестры адаптеров ограничены реальными портами NPC и `LanguagePort`.

### Consequences

* Good: домен покрывается unit-тестами без сети и БД; границы проверяются автоматически.
* Good: мало абстракций; новый код легко найти по слою.
* Bad: нельзя масштабировать части независимо; тяжёлая генерация изолирована только процессом worker.
* Bad: нужна дисциплина — абстракции без второй реализации или реальной границы не вводятся.

### Confirmation

dependency-cruiser (`npm --prefix server run check`, `npm --prefix client run check:imports`): запрещает циклы и импорт IO/адаптеров в домен; `game` не импортирует `realtime`/`http`/`persistence`; `shared/` не зависит от Node/DOM.

## Pros and Cons of the Options

### Модульный монолит

* Good: простота запуска одной командой; детерминированный шаг.
* Bad: один процесс — единая точка отказа (сбой NPC при этом мир не останавливает).

### Микросервисы

* Bad: в источниках явно исключены («без микросервисов»); обоснования не указаны.

### DI-контейнер, event bus и т. п.

* Bad: в источниках явно перечислены как «чего не делаем».
