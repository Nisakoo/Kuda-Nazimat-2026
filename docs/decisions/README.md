# Журнал решений

Когда читать: перед тем как менять то, что выглядит как договорённость (протокол, лимиты, стек, профили, границы модулей), и когда принимаете новое решение. Единый вход: здесь правила, индекс крупных решений и все остальные решения.

## Правила

- **MADR** — если решение дорого отменить, или оно затрагивает больше одной зоны (client + server), или ограничивает всех. Файл `NNNN-slug.md`, номера по порядку, шаблон — [template.md](template.md).
- **Остальные решения** — Y-statement в разделе «Остальные решения» этого README. Заголовок записи: `### D-<номер PR> · YYYY-MM-DD · <зона> · <статус>`. Исторические записи, перенесённые без PR, нумеруются `D-H01`, `D-H02` …
- **Зона** — одно слово: `client`, `server`, `shared`, `npc`, `llm`, `render`, `obs`, `admin`, `tls`, `world`, `ui`.
- **Принятые решения не редактируют.** При пересмотре пишут новое, а у старого меняют статус на «заменено D-…» (Y-statement) или `superseded by NNNN` (MADR).
- **Тело Y-statement:** «В контексте …, столкнувшись с …, выбрали …, отвергли …, чтобы …, смирившись с …».
- В «Considered Options» и «отвергли» только то, что действительно рассматривалось; если источники не дают альтернатив или причин — пишем «в источниках не указано», ничего не придумываем.
- Игровые решения (дизайн, UI, мир) ведутся в том же разделе «Остальные решения» (записи D-H28 и далее).

## Остальные решения

Даты взяты из истории git (по дате коммита реализации или спеки); если точной даты нет, это отмечено.

### D-H01 · 2026-10-31 · world · принято

В контексте подгрузки мира на ноутбуки игроков, столкнувшись с необходимостью ограничить память клиента, выбрали окно до 25 чанков вокруг игрока (радиус 0–2) и консервативный cap полезных данных 128 MiB с резервированием чанка до первого HTTP-запроса, отвергли процентный лимит кеша от размера мира (удалён по решению пользователя), чтобы память зависела от окна, а не от размера мира, смирившись с тем, что cap не измеряет RSS браузера и драйвера. Расхождение: часть старых документов называет guard 64 MiB; действует 128 MiB.

### D-H02 · 2026-10-31 · world · принято

В контексте выдачи данных мира игрокам, столкнувшись с риском публичного доступа к картам и моделям, выбрали единственный путь `/world/*` с Bearer-сессией и проверкой активного игрока на карте (чанк — в радиусе 3 по Чебышёву от авторитетной позиции, иначе 404, 403 не используется), отвергли публичную раздачу `maps/` и `assets/models/` из клиентской сборки, чтобы клиент не мог выкачать весь мир и не принимал 403 за потерю сессии, смирившись с тем, что в серверной поставке локальные режимы клиента не могут загрузить мир (публичного fallback нет).

### D-H03 · 2026-10-31 · server · принято

В контексте движения игроков по сети, столкнувшись с потерей пакетов остановки и риском бесконечного движения, выбрали передачу последнего намерения через volatile emit (до 20 Hz) с обнулением намерения на сервере через 250 мс без `input` и молчаливым отбрасыванием превышения частоты, отвергли воспроизведение очереди команд движения после разрыва, чтобы потерянная «остановка» не двигала игрока вечно, смирившись с отсутствием prediction и replay действий после reconnect.

### D-H04 · 2026-10-31 · server · принято

В контексте игрового шага 20 Hz для ≤4 игроков, столкнувшись с риском задержек от БД и ответов NPC, выбрали синхронный шаг без `await`, SQLite и ожидания NPC (сохранение позиций по таймеру `saveIntervalMs` = 10 с, генерация NPC за асинхронным портом), отвергли отдельный worker для БД как ненужный на MVP, чтобы шаг был предсказуемым (p95 ≤5 мс), смирившись с окном потери позиций при аварии до 10 с.

### D-H05 · 2026-10-31 · server · принято

В контексте входа одного аккаунта из нескольких вкладок, столкнувшись с необходимостью не занимать второе место и не расширять квоты, выбрали атомарный перехват управления новым соединением (старое получает `UNAUTHORIZED` «Игра открыта в другом окне.», его NPC-запрос отменяется, сущность и playerId сохраняются), отвергли второе управляющее соединение на аккаунт, чтобы один аккаунт был одним игроком и одним слотом из четырёх, смирившись с тем, что первая вкладка закрывается без отзыва сессии.

В контексте ответов NPC через очередь, столкнувшись с долгой генерацией локальной модели, выбрали аварийный срок запроса 8 с, отвергли — в источниках не указано, чтобы ограничить ожидание ответа аварийным пределом, смирившись с тем, что 8 с недостаточно для реальной модели. Дата по первой спеке LLM; точный момент принятия в источниках не указан.

### D-H07 · 2026-11-01 · npc · принято

В контексте реальных Ollama/MLX на слабом ноутбуке, столкнувшись с тем, что 8 с не хватает для ответа и очередь расходует тот же срок, выбрали настраиваемый срок: `npc.timeoutMs` по умолчанию 30000 мс (1–300000), `NPC_TIMEOUT` в Make/`--npc-timeout` в целых секундах 1–300 на запуск для обоих полей (`timeoutMs`, `streamTimeoutMs`), клиент ждёт срок +2000 мс, прочие pending 10 с, отвергли скрытый потолок 30 с в worker и молчаливое обрезание неверных значений, чтобы оператор мог подстроить срок под железо без пересборки клиента, смирившись с тем, что это аварийный предел, а не выполнение цели p95 ≤8 с. Заменяет D-H06; legacy timeout 8000 мигрирует в 30000.

### D-H08 · 2026-11-01 · llm · принято

В контексте подготовки локальных моделей, столкнувшись с разными конфигами Ollama 2B, Ollama 0.8B и MLX 2B, выбрали внешнюю versioned коллекцию профилей `~/kuda-llm/profiles.json` (runtime, модель, digest и tokenizer целиком) и выбор на один запуск через `BACKEND`/`MODEL` (вместе), отвергли автоматический fallback на другой backend и переписывание `config.json`, чтобы нельзя было случайно смешать веса с чужим tokenizer, смирившись с тем, что поддержаны ровно три пары, а при отсутствии явно запрошенного профиля сервер не стартует.
