# Игровые каналы требуют серверной сессии; в production только вход по паролю

## Context and Problem Statement

Все игровые данные — Socket.IO `/game`, `/world/*`, `/api/babylon` — должны принадлежать конкретному игроку. Сначала использовался вход по имени без пароля; затем потребовалось защитить аккаунт от входа под чужим именем и уметь мгновенно отзывать доступ.

## Decision Drivers

* Личность устанавливается только токеном; `playerId` и имя из payload доказательством не являются.
* Отзыв доступа (выход, сброс пароля, перехват) должен действовать сразу.
* Один аккаунт — один игрок и одно управляющее соединение; ≤4 активных игрока.
* Офлайн-игра: пароль простой, без почты и внешних провайдеров.

## Considered Options

* Серверные сессии с отзывом + пароль (scrypt) в production; вход по имени и автовход только в development/test (выбрано)
* Вход только по имени (первая версия)
* Почта, восстановление без администратора, внешние провайдеры, двухфакторный вход (вне scope)

## Decision Outcome

Реальные игровые каналы требуют сессию. Токен — 32 случайных байта, в БД только SHA-256, срок 12 ч без продления, ≤5 сессий на аккаунт. Production: только регистрация и вход по паролю (scrypt, 6–128 символов). Development/test: дополнительно `guest` и `dev`. Конфигурация, включающая вход без пароля в production, не запускается. Проверка токена — при handshake и при каждом защищённом HTTP-запросе, без кеша положительного результата. Новое соединение того же аккаунта атомарно перехватывает управление.

### Consequences

* Good: отзыв действует сразу; пароли и токены не попадают в логи.
* Bad: сессия живёт только в памяти клиента — после reload нужен новый вход.
* Bad: забытый пароль восстанавливает только администратор (временный пароль на 24 ч).
* Bad: минимальная длина пароля 6 выбрана ради простоты офлайн-игры; при необходимости повышается без смены формата хранения.
* Bad: режим `guest` в development позволяет войти под чужим именем — это риск dev-режима.

### Confirmation

`auth.test.ts`, `admin-auth.test.ts`; сценарий production: `guest` и `dev` отвечают `DISABLED`, `GET /api/auth/mode` → `{password: true, guest: false, dev: false}`.

## Pros and Cons of the Options

### Сессии с отзывом + пароль

* Good: сессии на сервере, поэтому отзываются в любой момент.
* Bad: нужны лимиты попыток и действия администратора.

### Только имя

* Bad: любой может войти под чужим именем; оставлен только для разработки.

### Почта, внешние провайдеры, 2FA

* Bad: в источниках отнесены к вне scope; обоснования не указаны.
