# Архитектура

## Система и режимы

Учебный 3D-мир для максимум 4 одновременно активных игроков: общение, изучение истории/знаний через индивидуальных NPC. Приёмка включает всех четверых, в том числе одновременные вопросы NPC; число вкладок не расширяет playerId или квоты. Итоговая система работает без интернета: один ноутбук запускает сервер, SQLite и ИИ; другие используют только браузер. Второй сценарий — браузер и сервер на одном ноутбуке с отключённым Wi-Fi.

LocalSession — режим разработки клиента без игрового сервера, с локально раздаваемыми файлами. Он не заменяет итоговую автономную демонстрацию с настоящим сервером, авторизацией, БД и адаптивным ИИ. OnlineSession использует авторитетный сервер; подключение игрового канала доступно только после авторизации.

## Мир и загрузка

Мир связный, с тематическими районами и переходами между ними. Район задаёт содержание и оформление; чанк — независимая техническая единица загрузки. Вход в район не требует загрузки всего района или смены игровой сессии. Центральная площадь, исторический и научный районы — предложенный состав демо, а не утверждённый план контента.

MapSource получает manifest и чанки через локальный HTTP; Socket.IO передаёт команды и динамические события. В LocalSession spawn берётся из manifest, в OnlineSession — из авторитетного состояния игрока. Сервер разрешает загрузку окрестности с запасом для перехода; область статической предзагрузки и AOI динамических сущностей задаются отдельно.

Одна сцена Three.js содержит визуальные группы загруженных чанков и отдельные динамические сущности. Ресурсы общих моделей переиспользуются. Загрузка, создание визуальных объектов и их выгрузка не должны останавливать игровой цикл; при неготовой области движение безопасно ограничивается с индикатором загрузки.

Размер чанка, радиусы загрузки/выгрузки, число параллельных запросов и точная метрика 10% не выбраны. Обсуждавшиеся 32 × 32 метра и 3 × 3 чанка — только варианты для замеров. Доля загруженных районов/чанков не считается доказательством лимита данных.

## Клиент

Один Vite-проект в `client/`: TypeScript strict, Svelte 5 + CSS, Three.js, Socket.IO Client, Vitest; карты — JSON и glTF/GLB. Three.js — единственный движок, конфигурации переключения рендера нет. Без SvelteKit и монорепозитория.

Headless Core + модульность + Ports & Adapters + ECS-lite. GameApp собирает зависимости явно, без DI-контейнера. Порты вводятся там, где изолируют реальные зависимости; пустые классы ради дерева не создаются.

| Модуль в client/src | Ответственность и зависимости |
|---|---|
| app | GameApp, GameLoop, config; связывает все модули |
| core | GameWorld, EntityManager, components/systems/commands/events; только чистые данные/логика |
| session | GameSession, LocalSession, OnlineSession; Core и интерфейс NetworkAdapter |
| render | RenderAdapter и three/ThreeRenderer; данные Core, Three.js только внутри реализации |
| map | MapSource/HttpMapSource, ChunkManager, AssetManager; без Three.js, вывод через порт рендера |
| multiplayer | NetworkAdapter, SocketIOAdapter, MockNetworkAdapter; типы протокола |
| input | InputController; DOM → команды сессии и камеры |
| ui | App.svelte, components/screens/state; GameSession или фасад GameApp |
| shared | Нейтральные types и protocol; без обратных импортов из адаптеров |

На этапе foundation существуют `app`, минимальный `render`, `ui` и точка запуска `main.ts`; остальные модули из таблицы — целевые. GameApp связывает минимальный RenderAdapter с ThreeRenderer и владеет циклом отображения, resize и visibility; фиксированная симуляция GameLoop и сессии добавляются на этапе Core.

`client/public/maps/demo/` и `client/public/assets/models/` предназначены только для локального демо и пока не созданы. В онлайн-поставке клиент содержит приложение, а данные реального мира размещены на сервере за проверкой доступа; публичного обходного URL для них нет. Core не зависит от DOM, Svelte, Three.js, сети и хранения. UI не импортирует конкретные адаптеры. Импорты между модулями ацикличны.

GameLoop принадлежит GameApp, использует единый планировщик кадров; симуляция имеет фиксированный шаг, рендер — интерполяцию. Загрузки планируются асинхронно. Map управляет данными/ссылками, ThreeRenderer — объектами сцены и GPU; владение общими ресурсами явно.

Конфигурация: session, serverUrl (same-origin по умолчанию), mapId, chunkRadius, debug. Публичная конфигурация отделена от игровых данных и серверных секретов.

Foundation читает публичный `config.json` при открытии страницы; серверный адрес не зашит в JS. `chunkRadius: null` оставляет радиус неопределённым до решения MAP. `local` пока открывает техническую сцену, `online` явно недоступен; оба значения не объявляют готовыми соответствующие игровые сессии.

## Отдельный сервер

Сервер будет отдельным проектом; каталог `server/` в этом клиентском репозитории не создаётся. Здесь хранятся серверные требования с отмеченными открытыми решениями и будущие задачи. Сервер использует Socket.IO и SQLite; язык/runtime предстоит выбрать.

Границы модульного серверного приложения: bootstrap/config, auth, realtime, world, players, persistence, ai. Это не набор микросервисов; inference изолируется процессом, SQLite выполняется вне игрового шага через ограниченный неблокирующий путь/worker. Сервер проверяет вход и команды, рассчитывает авторитетное движение/AOI, сохраняет состояние и память NPC. Транспорт и SQLite не проникают в игровые правила. Для NPC выбран локальный LLM-подход: Qwen3.5-2B 4-bit, проверенные локальные знания и индивидуальная память; профиль ещё требует квалификации. Игровой runtime сервера остаётся открытым выбором.

Общий контракт — [PROTO](specs/protocol.md). В отдельных проектах используются совместимые версии типов/схем; общий npm-пакет или монорепозиторий сейчас не требуются. Клиент никогда не присваивает авторитетные защищённые значения.

## Локальная LLM и NPC

Два backend: MLX LM на Apple Silicon и Ollama на поддерживаемых Windows/macOS (Intel Mac — CPU, требования ОС проверяются). Это серверная настройка, не LocalSession/OnlineSession. Один backend и одна модель обслуживают всех NPC; одновременная загрузка двух запрещена. Модель и runner закрепляются версиями/хешами; подготовка артефактов выполняется заранее. Браузер не имеет прямого доступа к inference endpoint.

`NpcDialogueService` координирует права, lifecycle, `GenerationScheduler`, `KnowledgeSource`, `MemoryService`, `DialogueRepository`, `PromptBuilder` и `LlmPort`; `MlxAdapter`/`OllamaAdapter` изолируют inference. MLX работает в отдельном локальном Python-worker, не навязывая язык остальному серверу. Поиск MVP — SQLite FTS5 с тематическими/межъязыковыми aliases, без отдельной embedding-модели. История ответов хранится отдельно от ограниченной детерминированной памяти; модель не выполняет SQL, ОС-команды и игровые действия.

Общий бюджет LLM — не более 4 000 000 000 байт RAM для всех процессов, контекстов и AI-кешей/буферов вместе. Начальный контекст на запрос 2048 токенов, вход ≤1792, стандартный выход до 128, расширенный до 256; thinking выключен. GenerationScheduler допускает всего 4 незавершённых запроса, по одному на игрока. Базовый профиль maxConcurrentGenerations=1; профиль 2 принимается после сравнения на том же железе, без копирования весов и смешения KV/recurrent state. FIFO, индивидуальная отмена и общий runtime-restart не останавливают мир. Слот не переиспользуется до физической остановки вычисления. Профиль включает CPU thread limits и проверяется вместе с сервером/браузером, а не только в изолированном LLM benchmark.

Временный streaming передаёт ограниченные полные partial-снимки текста без per-fragment ACK/replay; клиент заменяет текст, пропуски снимков допустимы. Финал отправляется после SQLite commit, восстановление читает result без новой generation. Буферы приложения и транспорта ограничены; сбой доставки не отменяет durable-результат. Цели single-request и 4-player burst заданы в LLM/LLM-QA; это требования, не результаты замеров.

Детали — [LLM](specs/server-llm-runtime.md), [AI](specs/server-ai.md), [STORE](specs/server-persistence.md), [NPC-подконтракт](specs/protocol.md) и [LLM-QA](specs/npc-llm-evaluation.md). Основная модель выбрана по исследованию, но скорость, русский язык, артефакты MLX и общий пик RAM должны пройти проверку на целевом железе. Резервный Qwen3-1.7B не включается автоматически.

## Общие ограничения и открытые решения

- Runtime без интернета: ресурсы, модели, декодеры и зависимости подготовлены заранее. Никаких CDN или внешних ИИ API во время игры.
- Кеш клиента ≤10% мира. Метрика, общий объём, browser cache, CPU/GPU-копии и временные буферы требуют единого решения в MAP и SERVER-WORLD до приёмки.
- Не определены игровой серверный runtime, локальный вход/handshake, полные схемы протокола, частоты обновления, коллизии и интервалы сохранения мира. Для ИИ выбраны модель/backend/границы памяти; остаются подготовка учебных материалов, pin артефактов и квалификация оборудования.
- Целевые браузеры, оборудование и бюджеты производительности определяются до итоговых замеров.
- WebXR/VR-шлем, транспортная физика, бой, квестовая система и редактор карты не входят в текущий MVP.

Требования — в `specs/`, порядок и доказательства реализации — в `tasks/`. `implementation` отражает код, а `status` — состояние документа; готовая спека не означает готовую систему.
