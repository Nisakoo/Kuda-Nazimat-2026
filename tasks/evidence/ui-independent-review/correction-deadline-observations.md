# Сохранённые deadline-наблюдения текущей коррекции

Объект: настоящий сервер 4387, `index-zupTnY5d.js`, DPR 1, 1280×800. Никакая ошибка не закрыта увеличением таймаута. Исходные browser 15/47 и render 4/8 остаются открытыми. Уведомление `826c50` относится к старым логам с другим bundle и не меняет этот вывод.

## Наблюдаемые неуспехи

1. `correction-world-attempt1-results.json` и `correction-world-attempt1-run.log`: Start кратковременно удовлетворил `enabled` за 1789 мс. Настоящий последующий pointer click не завершился за 5000 мс; в логе присутствует disabled. Тогда мир не был начат. Последующие зависимые проверки этой попытки не являются самостоятельными доказательствами дефектов окон.
2. `correction-world-attempt3-results.json`: enabled 2378 мс, pointer action timeout 5018 мс. После более длинного диагностического retry текущая проверка Pointer Lock всё равно не получила true в 5000 мс. Снимок сохраняет welcome и «Загружаем оформление…». `finally` проверяющего создал orphaned `waitForResponse` на logout, который завершил Node раньше записи `finishedAt`; это отдельная ошибка harness, не ошибка приложения.
3. Итоговый строгий pointer-поток `correction-world-results.json` / `correction-world-run.log`: initial enabled не прошёл за **5042 мс**, `Start actionable click within5s` не прошёл за **5015 мс**. Более длинная диагностическая попытка действительно открыла мир; это не превращает первые 2 неуспеха в pass. После неё отдельная проверка capture получила true за 3271 мс.
4. В том же потоке 5-секундные pointer clicks по настоящим видимым контролам (например, `Кувшин`, `Продолжить`, кнопки нижнего dock) также закончились timeout. Логи часто останавливаются на `visible, enabled and stable`. Это наблюдение автоматизации реальных контролов, не доказанная причина. Нельзя объявлять причиной GPU, shadows, геометрию, сервер или CSS без отдельного измерения.

## Что уже видно о R-06, но чего недостаточно для закрытия

В `correction-world-results.json` получены 5 настоящих выборок после I: сразу, затем через 100, 500, 1000, 1000 мс. Во всех focus внутри top modal, Pointer Lock снят. Read-only event trace отдельно показывает:

- `focusin` в DIV содержимого инвентаря на 70059.1 мс;
- unlock на 70172.6 мс;
- отложенный `focusout` DIV → BODY на 71677.8 мс;
- восстановление на реальный `Закрыть окно` на 71690.8 мс (примерно 13 мс).

Это подтверждает, что новая коррекция обрабатывает прежний отложенный focusout, а не только сам unlock. Однако первый I был отправлен через **19263 мс после возврата Start**: установка trace в этом потоке заняла время. Поэтому это **не** доказательство быстрого Start → I. Equip pointer click не завершился за 5 секунд; реальный equip POST в этом шаге не был доказан. ACK, второй I и отдельные pending/user-focus/new-modal случаи этой попыткой не закрыты.

## Отдельные ошибки проверяющего

- `correction-world-attempt2*`: была нажата правильно disabled radio saved party. Это известное read-only состояние режима; его надо наблюдать, а не кликать. Никакой app regression из этого не следует.
- В строгом итоговом потоке повторный `enroll` уже enrolled реального peer вернул ожидаемый CONFLICT. Последующий FORBIDDEN для chat — следствие не выполненного `join`, а не самостоятельный дефект чата.
- После этих ошибок зависимые шаги не дают доказательства сохранения/приватности/карты. Их скриншоты честно названы `failure-*`.
- Итоговый строгий pointer-поток всё же закрыл context/browser и подтвердил cleanup logout **204**. Orphaned Promise сохранён в `errors` как ошибка проверяющего. Для ранних аварийных попыток нельзя утверждать подтверждённый отзыв каждого токена.

## Следующий диагностический путь

`correction-world-diagnostic.mjs` использует те же реальные данные и сервер. Native keyboard activation — альтернативное управление кнопками, не force click, DOM-state injection или подмена API. Все прежние pointer/deadline неуспехи остаются. Смена способа активации не доказывает mouse acceptance и не считается новым успешным canonical browser/render pipeline.

Trace устанавливается до входа в мир. Только после настоящего события успешного Pointer Lock от явной кнопки Start проверяющий отправляет реальную клавишу I. Сам Pointer Lock не вызывается из trace. Pending-сценарии допускают только latency реального транспорта; тело и статус ответа сервера не подменяются. Event-счётчик проверяет, что ACK ещё не пришёл до выбранного пользовательского фокуса. Эти наблюдения остаются диагностикой, а не аппаратной/LAN/FPS квалификацией.
