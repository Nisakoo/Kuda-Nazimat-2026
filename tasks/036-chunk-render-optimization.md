# Небольшие исправления загрузки чанков и оптимизация камеры

## Цель и изменения требований

По результатам исследования main `dcf49bf`, 2026-10-31. Исправить зависание ближайшего перехода при ограниченном бюджете и уменьшить CPU-время проверки препятствий камеры. Новых требований нет. Пользователь одобрил реализацию предложенного пакета.

## Подтверждённые наблюдения

### Отложенный чанк не получает новый приоритет

В [ChunkManager.plan](../client/src/map/ChunkManager.ts) состояния `deferred` сбрасываются только при изменении `budgetEpoch`; `pump` пропускает любой существующий state. При приближении игрока список сортируется заново, но отложенный чанк не повторяет попытку и не запускает вытеснение уже менее нужного чанка. Вытеснение находится только в обработчике новой ошибки `BudgetExhausted`.

Воспроизведение на настоящих ChunkManager/HttpMapSource/WorldBudget и файлах market, с подменой HTTP чтением файлов и пустым визуальным адаптером:

- В spawn `(0, 0, 8)`, радиус 1: готовы 8 чанков; `0_-1` (пастбище) отложен. Резерв 1 810 665 / 1 912 050 байт, консервативная память 31 007 616 / 33 554 432 байт. Дополнительный pasture GLB требует 403 156 байт и 6 MiB: он не помещается по обоим ограничениям.
- При `plan({x: 0, y: 0, z: -15.7})` набор остаётся прежним, `loading=0`, `deferred=1`, ошибок нет. Для следующей точки `z=-15.8` готовность и проходимость ложны.
- После `retry()` пастбище готово, башня `-1_0` вытеснена, готовность следующей точки истинна; оба ограничения бюджета соблюдены.
- Минимальный пример с тремя чанками и бюджетом на два воспроизводит ту же проблему: смена ближайшего соседа не будит `deferred`, явный retry позволяет пройти.

Подтверждено отдельно в Chrome на текущем клиенте: market, радиус 1, debug, старт прогулки, удержание W 10 секунд. Игрок останавливается на `X 0.0 · Z -15.7`, показано ожидание соседнего участка, но счётчик сообщает `Чанки: 8 · Ожидание: 0`. Счётчик в [GameApp.updateVisualStatus](../client/src/app/GameApp.ts) отображает только `loading`, скрывая `deferred` и причину нехватки бюджета. Браузерный retry в этом исследовании не проверялся.

### Основная измеренная затрата CPU — камера

[CameraObstruction.resolve](../client/src/render/three/CameraObstruction.ts) выполняет пять рекурсивных `Raycaster.intersectObjects` по всем загруженным группам чанков. Three.js собирает и сортирует пересечения, после чего клиент берёт только первое. В сцене на старте 355 объектов, из них 240 Mesh.

Короткий замер Chrome headless через Vite dev, viewport 1280×800, неподвижный игрок в spawn после прогрева, около 6 секунд на вариант. Временные обёртки прототипов измеряли вызовы через `performance.now()`; исходники не менялись.

| DPR | Кадры | Средний CPU render | P95 CPU render | Средний resolve камеры | P95 resolve камеры |
|---|---:|---:|---:|---:|---:|
| 1 | 360 | 4,72 мс | 4,90 мс | 4,20 мс | 4,40 мс |
| 2 | 361 | 4,75 мс | 5,00 мс | 4,16 мс | 4,30 мс |

UI показывал 59,3–59,6 FPS и 264 draw calls; ошибок страницы не было. Проверка камеры занимает около 88–89% измеренного вызова render. Эти цифры включают инструментирование и не измеряют время GPU; короткий неподвижный dev-прогон не заменяет профиль production на маршруте и слабом ноутбуке. Сильные лаги на этой машине не воспроизведены.

### Дополнительная работа в каждом кадре

- [ThreeRenderer.render](../client/src/render/three/ThreeRenderer.ts) принудительно обновляет всю иерархию через `scene.updateMatrixWorld(true)`, затем установленный WebGLRenderer снова вызывает `scene.updateMatrixWorld()` с текущими флагами. Можно оставить единственное согласованное обновление перед лучами и отрисовкой; обновление камеры/света и анимированных объектов должно сохраниться.
- `plan` вызывается на каждом шаге симуляции, в том числе стоя на месте; он просматривает 1024 записи manifest. `region` тоже линейно ищет чанк, а проверки проходимости создают временные массивы состояний. Индекс `(x,z)` и пропуск неизменившегося плана уберут лишнюю работу. При движении внутри чанка обязательно учитывать изменение приоритетов и предзагрузку радиуса 0.
- [GltfLibrary.flush](../client/src/render/three/GltfLibrary.ts) ограничивает число экземпляров восемью, но не время работы. Вклад в рывки при загрузке ещё не измерен; временной бюджет стоит добавлять только при подтверждённых пиках.

## Реализация

- [x] Исправлен пересмотр `deferred` при смене приоритета перехода. Вытесняются менее приоритетные готовые чанки с защитой footprint игрока. Пары вытеснения запоминаются до смены приоритетов/retry или освобождения бюджета другим владельцем; отложенный запрос хранит эпоху своей последней неудачи. Доступные предзагрузки возвращаются после завершения попытки, невозможный запрос не запускает цикл. Атомарный бюджет, отмена устаревших загрузок и параллелизм 2 сохранены.
- [x] В диагностике отдельно отображаются отложенные чанки и причина: лимит кеша или памяти.
- [x] Детальный профиль выделил `market-surface`: 13 498 треугольников, 738,3 мс суммарно за 900 raycast (пять проб × 180 кадров); остальные отдельные Mesh — менее 1 мс каждый за тот же интервал. Вместо приблизительных препятствий или отбора только чанков добавлен CameraRaycast: bounding box для каждых 128 треугольников крупной обычной геометрии, затем точный Mesh.raycast только для подходящих диапазонов. Материалы, группы, drawRange, near/far и текущая matrixWorld сохранены. Буферы вершин/индексов общие; scratch-объект очищает ссылки после проверки, индексы слабо привязаны к геометрии. Skinned/morph/instanced/custom raycast остаются на обычном пути. Пять проб near plane и плавное возвращение сохранены.
- [x] Повторный автоматический обход scene отключается только на время вызова WebGLRenderer.render; ручной обход перед лучами и автоматическое обновление камеры сохраняются.
- [x] Manifest индексирован по координатам: не более 25 кандидатов вместо полного просмотра 1024 записей. Проходимость и район используют тот же индекс. Неизменные позиция/радиус/эпоха бюджета не перепланируются; сортировка при движении внутри чанка сохраняется.

Качество теней 2048→1024 и лимит DPR 2→1,5 оставить отдельными опциями для слабого GPU после замеров: это компромисс качества, текущий замер его необходимости не подтвердил. LOD, instancing, новые библиотеки и переработка движка в первый пакет не входят. Замена проверки камеры коллизионным bitmap движения неприемлема без учёта высоты, крыш и навесов.
