# PROTO — Общий контракт клиента и сервера

## Цель

Зафиксировать предварительный версионируемый контракт без привязки к реализации клиента или сервера.

## Требования

- **PROTO-001:** В клиенте типы находятся в shared/protocol; будущий отдельный сервер реализует тот же контракт. Все сообщения имеют версию протокола и тип; запросы — requestId, снимки/обновления — revision или tick. Несовместимая версия отклоняется понятной ошибкой.
- **PROTO-002:** Клиент отправляет вход в мир, ввод/команды движения, взаимодействие с объектом или NPC, текстовое сообщение игрокам и другие разрешённые действия. Сервер отправляет подтверждение входа, playerId, начальный снимок, создание/изменение/удаление сущностей, игровые события, доставленные текстовые сообщения, коррелированные ответы NPC и ошибки.
- **PROTO-003:** Игровой ввод описывает намерение, не устанавливает авторитетную позицию, здоровье, инвентарь или владельца. Сервер проверяет структуру, принадлежность игроку, последовательность и допустимость команды.
- **PROTO-004:** Снимок и изменения ограничены областью интереса игрока (AOI); revision/sequence позволяют отбрасывать устаревшие данные и запрашивать новый снимок при разрыве последовательности. Полный мир не рассылается. Delta updates допускаются без обязательной сложной компрессии.
- **PROTO-005:** После переподключения клиент повторно подтверждает доступ и получает согласованный снимок. Повторы действий не создают двойной эффект; неограниченная очередь команд движения во время потери связи не воспроизводится.
- **PROTO-006:** Контракт определяет ограниченные размеры сообщений, коды ошибок, статусы соединения и корреляцию ответов NPC. Пользовательские данные не считаются доверенными ни на клиенте, ни на сервере.
- **PROTO-007:** NPC-диалог использует коррелированные запрос, отмену, поток и чтение результата, описанные ниже. Сервер назначает владельца по AUTH, проверяет npcId/dialogueId и доступ/дистанцию, не доверяет playerId из payload. Финал содержит полный текст и признак durable-сохранения; его нельзя подменять последним delta. События чужого/закрытого диалога и устаревшие seq не применяются. Повтор requestId не создаёт второй эффект; reconnect читает durable-результат либо текущий/terminal-статус без повторной generation. Гонку completed/cancel/reset/access loss разрешает атомарный переход STORE-007: клиент не выбирает победителя по порядку пришедших пакетов.

## NPC-подконтракт

Имена ниже фиксируют NPC-подконтракт; общий envelope/валидационные схемы всего игрового протокола ещё оформляются в TASK-009. Каждое сообщение имеет общие `version`, `type`, `requestId`; ID — непустые строки до 128 ASCII-символов, разрешены буквы, цифры, `_`, `-`, `.`, `:`. Числа seq — неотрицательные safe integers. Неизвестная версия, дополнительные защищённые поля и неверный тип отклоняются runtime-валидацией.

| type | Направление | Данные и семантика |
|---|---|---|
| `npc.dialogue.request` | клиент → сервер | dialogueId, npcId, locale (`ru`, `en`, `es`) как проверяемое ожидание сохранённой настройки, text: непустой UTF-8 текст до 4096 байт; токенный лимит дополнительно проверяет LLM. dialogueId получен при разрешённом открытии взаимодействия, а не даёт право доступа сам по себе. |
| `npc.dialogue.cancel` | клиент → сервер | dialogueId; requestId указывает отменяемый запрос, отмена идемпотентна. Чужой запрос недоступен. Если completed уже committed, возвращается тот же completed/его статус, а не второй terminal cancelled. |
| `npc.dialogue.ack` | клиент → сервер | dialogueId, seq — наибольший непрерывно обработанный seq запроса; повтор идемпотентен, seq больше отправленного отклоняется. Не даёт доступа к чужому запросу. |
| `npc.dialogue.preferences` | клиент → сервер | dialogueId, locale (`ru`, `en`, `es`), responseStyle (`standard`, `simple_no_formulas`). Это явная настройка, не извлечение моделью из свободного текста. requestId уникален для операции настройки и не совпадает с ID generation. |
| `npc.dialogue.preferences.result` | сервер → владелец | dialogueId, locale, responseStyle, persisted=true и memoryRevision после commit настройки; при ошибке — безопасный code/message без persisted=true. Настройка действует для новых запросов, принятых после commit; queued/running-запрос использует снимок настроек при своём приёме, не меняет язык/стиль посреди ответа. |
| `npc.dialogue.event` | сервер → владелец | dialogueId, npcId, seq и kind: queued/running/delta/completed/cancelled/error. Для delta — text (до 4096 UTF-8 байт на событие). Для completed — полный text, finishReason, persisted=true и memoryRevision; этот финал заменяет собранный временный текст. Для error — ограниченный code и безопасное message. |
| `npc.dialogue.result` | клиент → сервер | dialogueId; requestId указывает уже существующий запрос. Ничего не генерирует. |
| `npc.dialogue.result.response` | сервер → владелец | dialogueId, npcId, state; для completed — полный text, finishReason, persisted=true и memoryRevision. Для очищенного текста — result_expired, для прерванного — interrupted; для активного — текущий статус. Для terminal указывается lastSeq; полный completed-снимок задаёт новую ACK-базу lastSeq без воспроизведения потерянных delta. Для активного запроса ответ содержит только статус, не задаёт новую ACK-базу. |

Серверные stream-события одного запроса имеют строго возрастающий seq; дубли/старые события отбрасываются. Клиент отправляет ACK после обработки непрерывного диапазона, не реже чем каждые 100 мс при активном потоке либо после 8 КиБ данных, и отдельно на terminal. Сервер учитывает UTF-8 байты сериализованных stream-envelope с seq выше последнего ACK (без TCP/WebSocket overhead); байты освобождаются по ACK, предел — 64 КиБ и 5 секунд без ACK по LLM-011. Очередь метаданных ACK также ограничена этим бюджетом. ACK подтверждает обработку клиентом, не запись в БД и не истинность фактов. Пропуск seq не подтверждается как непрерывно обработанный. При пропуске в активном потоке клиент прекращает применять delta, идемпотентно отменяет запрос и читает result до terminal; автоматической повторной generation нет. Если completed уже победил в гонке, его полный текст заменяет неполный и задаёт новую ACK-базу seq/lastSeq; затем разрешён terminal ACK без всех промежуточных delta. Для cancelled/error поток закрывается, не пытаясь восстановить потерянный текст. При reconnect активная generation также отменяется, если непрерывность потока не подтверждена. Завершённый durable-запрос не отменяется из-за отсутствия terminal ACK. Terminal seq и результат сохраняются вместе; replay финала не создаёт новую generation. Пропуск seq в delta не восстанавливается добавлением текста наугад: UI помечает временный ответ неполным, затем заменяет полным completed/result. Размер полного NPC-envelope не более 32 КиБ; сборка prompt не разрешает неограниченный вход, общий ограничитель PROTO-006 применяется до парсинга. Ответы отображаются как текст, не HTML.

Язык хранится в preferences (для нового игрока default ru). locale в dialogue.request не меняет настройку: при приёме он должен совпасть с текущим сохранённым locale, иначе locale_mismatch с предложением обновить настройки/состояние. Сервер сохраняет снимок locale/responseStyle для принятого запроса; последующее изменение preferences применяется к новым запросам. Это исключает два независимых источника языка и молчаливую смену настройки из payload.

Коды NPC включают: invalid_request, forbidden, unsupported_locale, locale_mismatch, busy, queue_timeout, input_too_long, model_unavailable, resource_limit, generation_timeout, slow_consumer, persistence_error, request_conflict, interrupted, result_expired. Отмена — отдельный terminal-kind, не успешный completed. При ошибке БД допустимо сообщить ошибку без durable-статуса, но запрещено отправлять persisted=true. Первичный запрос и повтор сравниваются по нормализованному fingerprint; ID уникален в области игрока. После проверки AUTH/владельца сервер сначала ищет существующий requestId и сверяет fingerprint, а уже для нового запроса проверяет текущее locale и admission limits. Поэтому повтор ранее принятого запроса после смены preferences возвращает прежний результат/статус, не отклоняется из-за нового locale и не создаёт эффект заново. Ни браузер, ни LLM не задают backend URL, system prompt, source corpus, игровые права или memoryRevision.

## Сценарии

- **S1:** PROTO-001–003, 006: Given сообщение неверной версии/формы или команда чужого игрока; When оно приходит; Then отклоняется без изменения мира.
- **S2:** PROTO-004–005: Given пропуск revision и переподключение; When клиент возобновляет сессию; Then получает актуальный снимок AOI и не применяет старые действия повторно.
- **S3:** PROTO-006–007: Given NPC-stream, дубль/пропуск seq, отмена и reconnect; When получен поздний fragment или запрошен результат после commit; Then нет чужого текста, повторной generation и двойного добавления финала, terminal корректно отражает сохранение.

## Ограничения и вне scope

Этот документ — общий контракт для обоих проектов. Формат payload, лимиты и handshake фиксируются до подключения реального транспорта.

## Открытые вопросы

Согласовать точные схемы сообщений, ошибки, sequence/tick, частоту обновления, размеры пакетов и передачу серверной сессии при handshake. Решение о способе локального входа из AUTH согласуется здесь до его реализации; ожидать готового сервера для проектирования handshake не требуется. Определить область чата, выдачу dialogueId при проверенном взаимодействии и согласование готовности чанков/перехода с сервером. NPC-подконтракт выше выбран; его машинные схемы, fixtures и согласование с общим envelope должны быть завершены до реальной сетевой реализации. Не считать TypeScript-типы runtime-валидацией.
