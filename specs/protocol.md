# PROTO — Общий контракт клиента и сервера

## Цель

Зафиксировать текущий версионируемый контракт без привязки к реализации клиента или сервера. Игровой контракт и API MLX/Ollama — разные границы; браузер не обращается к inference напрямую.

## Требования

- **PROTO-001:** Типы и runtime-схемы находятся в `shared/protocol/` ([SHARED](shared-contracts.md)); сервер и клиент используют их напрямую без отдельных копий. Все сообщения имеют версию протокола и тип; запросы — requestId, снимки/обновления — revision или tick. Несовместимая версия отклоняется понятной ошибкой.
- **PROTO-002:** Клиент отправляет вход в мир, ввод/команды движения, взаимодействие с объектом или NPC, текстовое сообщение игрокам и другие разрешённые действия. Сервер отправляет подтверждение входа, playerId, начальный снимок, создание/изменение/удаление сущностей, игровые события, доставленные текстовые сообщения, коррелированные ответы NPC и ошибки.
- **PROTO-003:** Игровой ввод описывает намерение, не устанавливает авторитетную позицию, здоровье, инвентарь или владельца. Сервер проверяет структуру, принадлежность игроку, последовательность и допустимость команды.
- **PROTO-004:** Снимок и изменения ограничены областью интереса игрока (AOI); revision/sequence позволяют отбрасывать устаревшие данные и запрашивать новый снимок при разрыве последовательности. Полный мир не рассылается. Delta updates допускаются без обязательной сложной компрессии.
- **PROTO-005:** После переподключения клиент повторно подтверждает доступ и получает согласованный снимок. Повторы действий не создают двойной эффект; неограниченная очередь команд движения во время потери связи не воспроизводится.
- **PROTO-006:** Контракт определяет ограниченные размеры сообщений, коды ошибок, статусы соединения и корреляцию ответов NPC. Пользовательские данные не считаются доверенными ни на клиенте, ни на сервере.
- **PROTO-007 (потоковый ответ NPC):** совместимое дополнение v3 — включается клиентом в запросе, старый клиент его не замечает. Формы — в разделе «Потоковый ответ NPC» ниже, исполняемые схемы и fixtures — в `shared/protocol/`. Сервер назначает владельца по сессии, проверяет цель и дистанцию по NPC-001 и не доверяет полям клиента. Терминальное сообщение авторитетнее любого временного снимка; подтверждение фрагментов и их replay не требуются.

- **PROTO-008:** Сервер игрового v3 соблюдает уточнения ниже. Они не меняют схемы клиента и проверяются fixtures в `shared/protocol/fixtures.json`.

## Независимый HTTP-профиль облика

`GET /api/avatar` и `POST /api/avatar` требуют `Authorization: Bearer <token>`. GET возвращает ровно `{avatarId: "lukas"|"nic"|"dan"|"ksu"|null}`; null означает отсутствие выбора, а не запрет игры. POST принимает только JSON до 1 KiB вида `{avatarId: "lukas"|"nic"|"dan"|"ksu"}` без дополнительных полей и возвращает тот же объект после сохранения. Ошибки: 400 INVALID, 401 UNAUTHORIZED, 503 UNAVAILABLE в форме `{error:{code,message}}`. Владелец определяется сессией. Общие схемы: `shared/avatar/types.ts` и `shared/avatar/validate.ts`. Это отдельная настройка и не меняет версии BABEL или игрового протокола.

## Игровое дополнение BABEL (PROTO-009)

- **PROTO-009:** `/api/babylon` — отдельный HTTP-подконтракт с собственной версией `v: 2`, типами и строгими парсерами в `shared/babylon/`. Он не меняет Socket.IO и не стримит ответы (PROTO-007 — только Socket.IO). Оба клиента используют один исполняемый контракт.

`POST`, JSON до 256 KiB, `Authorization: Bearer <token>`, без redirect/cache. Запрос `{v:2, requestId, action:{type,...}}`. ID 1–128 символов `[A-Za-z0-9_.:-]`; лишние поля запроса отклоняются. Владелец назначается из сессии. Для buy/feed/npc/chat/carve требуется управляющее соединение, уже вошедшее в мир; после ожидания генерации сессия и управление проверяются снова.

| action.type | Поля | Результат |
|---|---|---|
| state | — | Личный снимок; клиент опрашивает раз в секунду |
| enroll | size: 1–4, native, learning | Совместимость со старым клиентом: подбор/создание группы и языки |
| create | size: 1–4; необязательный replacePartyId | Создать группу; replacePartyId явно подтверждает замену собственной текущей группы. Несовпадение ID — CONFLICT. Замена и создание атомарны, повтор requestId не заменяет новую игру повторно; ошибка сохраняет старую |
| join | — | Вернуться в свою группу или присоединиться к ожидающей; не создаёт игру |
| languages | native, learning | Сохранить два разных доступных языка, в том числе до вступления в группу |
| intro-seen | — | Информационное окно просмотрено |
| buy / feed | targetId, item | Проверка роли, расстояния, инвентаря, шага задания |
| chat | text | Доставка группе с переводом по языкам получателей |
| npc | targetId, text | Личный ответ на изучаемом языке |
| carve | drawing | Неизменяемый камень группы |
| word-save | id?, word, translation, note, example?, exampleTranslation? | Создать/изменить собственную запись; отсутствующие примеры при редактировании сохраняются |
| word-learn | id, learned: boolean | Явно изменить статус собственной записи |
| word-delete | id | Удалить собственную запись |
| suggest | word | Предложение перевода на родной язык |

Успех `{v:2, requestId, state, notice?, suggestion?}` приходит после SQLite commit. `words` содержит личные записи с `learned: boolean`, `example` и `exampleTranslation` (каждый пример до 500 символов, пустая строка разрешена); новая запись по умолчанию имеет false и пустые примеры. `taskTitle` — подготовленный заголовок на изучаемом языке ru/en/es, пустой до вступления; LLM не используется. `taskTarget` — `{x:0,z:-34}` (центр загона на карте market) во время начатого незавершённого задания и null до начала/после завершения; обе координаты конечны и ограничены ±1 000 000. Прогресс — число элементов `fed` из четырёх, без фиктивных этапов. Обязательный `partyPositions` — массив максимум 4 объектов строго `{id,name,x,z}`; только другие участники текущей `party.members`, уникальные ID, без самого игрока. Сервер берёт только реальные позиции активных акторов карты market по стабильному playerId, независимо от AOI/загруженных клиентом чанков. Отсутствующие акторы/другие карты пропускаются, fallback на spawn/SQLite отсутствует. До enrollment или без runtime-порта возвращается пустой массив. Координаты конечны, ограничены ±1 000 000; другие игроки, accountId, y, роли и произвольные запросы чужой позиции через этот массив не выдаются. Получение позиций идёт с существующим polling state без нового endpoint; клиент может предпочитать более свежий AOI для того же подтверждённого участника. Снимок содержит profile, party, partyPositions, task/goatGuide, inventory, fed, stones, words, messages, replies; чужой словарь, исходники чужих переведённых сообщений и личные диалоги не выдаются. Ответ клиент ограничивает 8 MiB и валидирует до отображения. Поздний polling-ответ не заменяет результат новой команды.

Лимиты коллекций и текста — BABEL. Камень: координаты 0–320, ≤64 штрихов, ≤256 точек/штрих, ≤4096 точек суммарно. Поля игрока, роли, прогресса и количества предметов не принимаются как команды. Все тексты отображаются без HTML.

Идемпотентность по `(playerId, requestId)` и SHA-256 нормализованного действия: тот же запрос возвращает сохранённое подтверждение и актуальный снимок без второго эффекта; другое тело даёт CONFLICT. Неудачный перевод разрешено повторить с тем же ID; успешные доставки не дублируются. После рестарта незавершённые доставки помечаются ошибкой. Для сообщения резервируется один слот общей очереди; уникальные целевые языки выполняются последовательно внутри него. Совпадающие языки не требуют генерации.

Ошибка `{v:2, requestId, error:{code,message}}`; до разбора запроса допускается общий `{error}` без requestId. HTTP: INVALID 400, UNAUTHORIZED 401, FORBIDDEN 403, CONFLICT/NOT_READY 409, RATE_LIMIT 429, UNAVAILABLE 503. Ошибка не подменяется исходным текстом или клиентским успехом. На карте market участник BABEL не может обойти этот контракт через старые chat-send/npc-question.

## Будущий контракт диалога NPC

Текущий v3 остаётся без изменений: обычный вопрос до 240 символов, ответ до 4000, обычный NPC отвечает по-русски. Цель по [поведению персонажа](npc-character-behavior.md) и [NPC](server-npc-dialogue.md) — проверенные вопрос и отображаемый ответ до 800 кодовых точек Unicode, ответ на en/es A2 по серверной настройке игрока. Это не изменение действующих схем и не завершение TASK-041 или TASK-044.

До реализации нужно согласовать и проверить конкретные wire-схемы открытия и первого приветствия без фиктивного вопроса, настройки языка, области AUTH-сессии, отношения, статуса неудачной попытки и чтения результата. Названия новых событий здесь не заданы. Открытие и приветствие проходят общие очередь, дедлайн и дедупликацию; повторное открытие того же диалога не генерирует новое приветствие. Успешный ответ отличается от локального заранее написанного сообщения об ошибке; последнее не становится историей успешного ответа и не вызывает скрытую повторную генерацию.

Целевая память и доступ на чтение истории или результата изолированы по `(sessionId AUTH, playerId, npcId)`; кеш и выдаваемый модели контекст также фильтруются по этой области и правам роли. Целевой повтор NPC-операции и BABEL-снимок не раскрывают результат другой AUTH-сессии; для этого требуется отдельная реализация и проверка. Тот же действительный токен нужно явно повторно использовать после reload или reconnect; новый вход создаёт новую сессию и не восстанавливает старую память NPC. Меню не отзывает сессию; возврат ко входу отзывает. AUTH-002 TTL 12 часов не меняется. Глобальные лимиты очереди остаются ≤1 на игрока и ≤4 всего, даже при нескольких сессиях. Хранение после завершения сессии и её удаление — отдельная политика; данные завершённой сессии недоступны новым промптам.

Совместимость существующих непроверенных `npc-partial` с будущей проверкой содержания — открытый этап: части не должны обходить её. Текущий поток не доказывает наличие такой защиты.

## Игровое движение v3 (MOVE-013)

Текущая согласованная поставка использует `auth.version: 3` и `v: 3` во всех игровых пакетах. Версии 1/2 отклоняются с VERSION; параллельная поддержка не требуется. Формы и лимиты прежнего контракта ниже сохраняются, кроме явно перечисленного:

- `input`: обязательные `sprint: boolean`, `jumpId: safe integer ≥0` дополнительно к sequence/direction/preparedChunks. Клиент не отправляет физическое состояние. jumpId монотонен в соединении; 0 — нет запроса; увеличенный ID обрабатывается один раз, даже при отказе в воздухе. Повтор ID не прыгает повторно. После join нового соединения счётчик и подтверждение обнуляются.
- Сущность игрока содержит `motion: {grounded,phase,verticalVelocity,locomotion,stamina,sprintBlocked,jumpAck}`. grounded/sprintBlocked — boolean; phase — grounded/rising/falling; locomotion — idle/walk/sprint; stamina ∈[0,100], verticalVelocity ∈[-100,100], jumpAck — safe integer ≥0. grounded согласован с phase и нулевой вертикальной скоростью. Поля обязательны для character.kind=player, NPC их не получает.
- При пропуске delta запрашивается snapshot. Resync не сбрасывает jumpAck или запас; новое соединение сбрасывает только ввод/ID. Никакого replay ввода.
- Авторитетные параметры и алгоритм — MOVE и SHARED. Сервер проверяет весь путь и след с preparedChunks; клиент передаёт исходное намерение, разрешённое скольжение не теряется.
- Подконтракт NPC — npc-question/npc-answer с необязательным потоком PROTO-007. HTTP BABEL сохраняет v2.

## Общие формы текущего игрового v3

Формы унаследованы от базового клиентского контракта, но текущие handshake и envelope используют только v3; исполняемая версия — `shared/protocol/`. Сервер production требует пароль, development/test допускает вход по имени ([AUTH](server-auth.md)); парольные формы и logout подключены; полная приёмка TASK-044 остаётся отдельной. Готовая серверная сессия передаётся приложению как `{token, expiresAt}` и хранится в памяти, без localStorage/URL/логов. Токен — непрозрачная строка 16–512 символов без пробельных и управляющих символов, `expiresAt` — Unix ms.

**Транспорт.** Socket.IO: namespace `/game`, path `<serverUrl pathname>/socket.io`; на клиенте autoConnect и reconnection отключены. Handshake: `auth: {version: 3, token}`. Все игровые данные идут одним событием `game`. HTTP-источник мира `<serverUrl>/world/` требует тот же `Authorization: Bearer <token>`; публичного fallback нет, redirect запрещён, `Cache-Control: no-store`.

**Пакеты.** Все пакеты — JSON-объекты `{v: 3, type, ...}`. Лимиты:

- пакет ≤256 KiB UTF-8;
- ≤256 сущностей в AOI, ≤256 upsert, ≤128 remove;
- ID 1–80 символов `[A-Za-z0-9_-]`;
- координаты ±1e6, скорость ≤20;
- имя ≤80, чат 1–500, вопрос NPC ≤240, ответ NPC ≤4000 символов.

Неизвестные поля, лишние компоненты и нечисловые координаты отклоняются.

| Направление | type | Данные |
|---|---|---|
| клиент → сервер | join | requestId, mapId |
| клиент → сервер | input | requestId, sequence, direction {x,z} (‖d‖ ≤ 1, намерение), sprint, jumpId, preparedChunks[] (≤25 ID чанков) |
| клиент → сервер | interact | requestId, targetId |
| клиент → сервер | npc-question | requestId, targetId, text, stream? |
| клиент → сервер | chat-send | requestId, text |
| клиент → сервер | resync | requestId, revision |
| сервер → клиент | joined | requestId, playerId, revision, snapshot {tick, entities}, world (bootstrap) |
| сервер → клиент | snapshot | revision, snapshot |
| сервер → клиент | delta | revision, baseRevision, tick, upsert[], remove[] |
| сервер → клиент | interacted | requestId, targetId |
| сервер → клиент | npc-answer | requestId, targetId, text |
| сервер → клиент | chat | requestId, messageId, playerId, name, text |
| сервер → клиент | error | requestId, code, message |

`joined.snapshot` обязан содержать сущность `playerId` с `character.kind = player` и `transform`. Компоненты сущности: `transform {position, rotationY}`, `movement {direction, speed}`, `renderable {assetId}`, `interactable {radius, label}`, `character {kind: player|npc, name}`, `animationState {name}`. Обязательный компонент игрока `motion` определён выше в MOVE-013. Bootstrap `world`: `manifestUrl` (путь относительно `/world/`), `worldBytes`, `manifestBytes ≤ worldBytes/10`, `assets` — до 128 записей `path → {bytes ≤ worldBytes/10, memory ≤ 32 MiB}`.

**Ошибки.** Коды: UNAUTHORIZED, VERSION, INVALID, FORBIDDEN, RATE_LIMIT, NOT_READY, UNAVAILABLE. Клиент закрывает сессию при UNAUTHORIZED и разрывает соединение без retry при VERSION.

**Запросы.** requestId уникален в рамках соединения; сервер не повторяет эффект дубликатов. Обычные pending-запросы, включая чат, ограничены 10 с. Для single-final NPC клиент получает effective `npcTimeoutMs` через публичный `/api/game-config` фактического serverUrl при подключении/переподключении и ждёт этот срок +2000 мс. Устаревшая настройка другого соединения игнорируется; без достоверной настройки NPC недоступен, но мир/чат не блокируются. Серверный `npc.timeoutMs`: default 30000 мс, config 1–300000 мс; Make `NPC_TIMEOUT`/CLI задают целые секунды 1–300. Override не меняет формы пакетов. Ожидающих запросов у клиента ≤32, сообщений в чате ≤50, всё отображается как текст, без HTML.

**Частоты и движение.** Симуляция сервера — 20 Hz, рассылка AOI — до 10 Hz. Клиент отправляет последнее намерение до 20 Hz, не очередь движения. sequence монотонен в соединении и начинается заново после нового join. Сервер проверяет принадлежность preparedChunks карте и не пускает игрока в неподготовленную область. Клиент при неготовой области отправляет нулевое движение и не меняет авторитетную позицию.

**Revision.** revision монотонен в подтверждённом потоке AOI. Delta применяется только при `baseRevision` = последней revision и `revision = baseRevision + 1`; старые пакеты игнорируются. При пропуске клиент очищает историю отображения и отправляет `resync`. Snapshot не откатывает revision/tick. Повторное соединение всегда делает join и получает новый снимок, без воспроизведения действий до разрыва. Клиент применяет обновления на шаге своей сессии; входная очередь — максимум восемь пакетов, переполнение вызывает resync. Удалённые объекты интерполируются с задержкой 100 ms по последним восьми снимкам.

**Подключение.** Retry клиента: 1/2/4 секунды, не более трёх попыток после потери связи; timeout подключения 5 секунд. При отказе авторизации или несовместимой версии retry прекращается. Сервер не доверяет присланным preparedChunks, requestId и sequence как доказательству полномочий.

### Уточнения для сервера (PROTO-008)

Уточнения сохраняют семантику базового контракта; исполняемая версия handshake и пакетов — v3.

1. **Отказ handshake** — `connect_error` с `data: {code, message}`:
   - `UNAUTHORIZED` — нет, истёк или отозван токен;
   - `VERSION` — `auth.version ≠ 3`;
   - `UNAVAILABLE` — заняты все 4 слота игроков или сервер останавливается.

   На `UNAVAILABLE` клиент выполняет свои 3 retry и показывает «Сервер недоступен».
2. **Сообщения вне запроса.** `error`, не связанный с запросом клиента (перехват управления, истечение сессии), имеет `requestId: "server"`. Для `chat` другого игрока `requestId` — это requestId отправителя.
3. **Delta.** `upsert` содержит **полную** сущность со всеми текущими компонентами: клиент заменяет сущность целиком, отсутствующий компонент считается удалённым. Сервер отправляет delta только при изменениях, и revision растёт только с отправленными delta. Ответ на `resync` — `snapshot` с текущей (последней отправленной) revision. После него поток продолжается от этой revision.
4. **Ввод.** Сервер применяет последнее намерение до следующего `input`. Если `input` нет 250 ms, намерение обнуляется: клиент шлёт `input` через volatile emit, и потерянная «остановка» не должна двигать игрока бесконечно. `input` с `sequence` ≤ последнего принятого игнорируется. Превышение частоты `input` отбрасывается молча, без `error`.
5. **Дубликаты.** Повтор уже использованного в соединении requestId получает `error INVALID` и не даёт второго эффекта.
6. **HTTP `/world/*`.** Клиент считает 401/403 потерей сессии и закрывает её. Поэтому 401/403 означают только отказ сессии. Ресурс вне допустимой области или неизвестный путь возвращают 404.
7. **Ответ входа.** `POST /api/auth/guest`, а также `register`, `login` и `password` (AUTH-006) возвращают ровно `{token, expiresAt}`: клиентский `parseServerSession` отклоняет лишние поля. Ошибки входа, выход и отзыв сессии — [AUTH](server-auth.md); отзыв доходит до игрового канала как `error {requestId: "server", code: "UNAUTHORIZED"}` с причиной.
Обязательный выбор облика передаётся отдельно через Bearer `GET /api/auth/state` → `{requiresAvatar:boolean}`; парольный аккаунт без облика не может выполнить join.

Детальное поведение сервера — [REALTIME](server-realtime.md), [AUTH](server-auth.md), [SERVER-WORLD](server-world.md), [NPC](server-npc-dialogue.md).

## Потоковый ответ NPC (PROTO-007)

| Направление | type | Данные и семантика |
|---|---|---|
| клиент → сервер | npc-question | requestId, targetId, text и необязательное `stream: boolean`. Без `stream` или с `false` — прежняя пара `npc-question` → `npc-answer`/`error`. |
| сервер → клиент | npc-partial | requestId вопроса, targetId, `seq` (целое ≥1, растёт внутри вопроса), `text` — **весь** текст, сгенерированный к этому моменту (≤4000), не дельта. Только для `stream: true`. |
| сервер → клиент | npc-answer / error | Терминальное сообщение вопроса, как без потока: полный финальный текст после записи в историю (NPC-003) либо ошибка NPC-001/002. |
| клиент → сервер | npc-cancel | requestId операции, `questionId` — requestId своего незавершённого вопроса. |
| сервер → клиент | npc-cancelled | requestId операции и questionId. После него по questionId ничего не приходит. |

Правила:

- **Временные снимки.** `npc-partial` уходит не чаще 10 раз в секунду на вопрос, через volatile-доставку Socket.IO: снимок может быть пропущен или заменён более новым, неизменённый текст не повторяется. Клиент заменяет временный текст снимком с бо́льшим `seq`, а не дописывает его. Сервер не хранит и не повторяет снимки после reconnect, ACK нет.
- **Терминальное сообщение.** `npc-answer` или `error` закрывает вопрос и авторитетнее любого снимка. После него `npc-partial` этого вопроса не приходит; запоздавший снимок с меньшим `seq` клиент всё равно игнорирует.
- **Дедлайн.** Потоковый вопрос ограничен `npc.streamTimeoutMs`, обычный — `npc.timeoutMs`: оба default 30000 мс, config 1–300000 мс. Явный Make/env/CLI override (целые секунды 1–300) задаёт оба effective значения одинаково; без override их отдельные config-значения сохраняются. Клиент, включивший поток, должен ждать терминальное сообщение по потоковому сроку, а не продлевать его каждым снимком. Существующий клиент пока не включает поток (TASK-041); длинный single-final pending этого не меняет.
- **Отмена.** `npc-cancel` отменяет только вопрос этого соединения: генерация получает abort, история не пишется; слот/квота освобождаются только после завершения вычисления (NPC-004), а не по факту отправки `npc-cancelled`. Ответ `npc-cancelled` приходит всегда, в том числе для неизвестного или уже завершённого questionId, — операция идемпотентна; если `npc-answer` уже был отправлен, он остаётся в силе.
- **Разрыв и перехват** отменяют вопрос, как NPC-004. После reconnect поток не восстанавливается: клиент задаёт вопрос заново.
- Все тексты отображаются как текст, не HTML. Квоты (≤4 незавершённых, ≤1 на игрока) и коды ошибок — NPC-001.

Прежний wire-черновик v2 (`npc.dialogue.*`: dialogueId, preferences, memoryRevision, чтение durable-результата после reconnect) не является реализованным протоколом. Эти возможности относятся к памяти и настройкам ИИ ([AI](server-ai.md), [STORE](server-persistence.md) STORE-006–010) и при необходимости добавляются к этому подконтракту новыми типами сообщений, без смены версии.

Серверный поток проверяется на `scripted`: он поддерживает `onPartial`, а realtime использует `PartialThrottle` и volatile-снимки. Настоящие Ollama/MLX workers сейчас выдают только приватный operational progress и финальный текст, не `npc-partial`. Наличие схем/очереди не квалифицирует LLM, backpressure или полный AI-ledger.

## Сценарии

- **S1 · PROTO-001–003, 006:** Given неверная версия/форма либо команда чужого игрока; When сообщение приходит; Then оно отклоняется без изменения мира.
- **S2 · PROTO-004–005:** Given пропуск revision и reconnect; When клиент возвращается; Then получает актуальный снимок AOI без повторного эффекта старых действий.
- **S3 · PROTO-006–007:** Given вопрос с `stream: true`; When ответчик выдаёт текст частями; Then клиент получает `npc-partial` с растущим `seq`, каждый текст — начало финального, затем один `npc-answer`, после которого снимков нет. Given вопрос без `stream`; Then снимков нет. Given `npc-cancel` во время генерации; Then приходит `npc-cancelled`, по вопросу больше ничего не приходит, история не записана, следующий вопрос игрока принимается.
- **S4 · PROTO-008:** Given сервер v3 и fixtures; When происходят занятые слоты, перехват управления, чат другого игрока, неподвижный мир, потерянная остановка и запрос чанка вне области; Then клиент получает `connect_error UNAVAILABLE`, `error` с `requestId: "server"`, корректный chat, отсутствие пустых delta, остановку через 250 ms и 404 без закрытия сессии.

## Ограничения и вне scope

NPC partial-снимки не меняют правила revision/delta для мира. Настройки транспорта и схемы обеих сторон фиксируются до реального сетевого обмена; TypeScript-типы не заменяют runtime-валидацию. Полный архив истории через этот streaming-контракт не пересылается.

## Оставшаяся интеграция

- Игровой envelope и handshake — v3; HTTP BABEL имеет собственный `v:2`. Старые игровые v1/v2 отклоняются.
- Пара `npc-question`/`npc-answer` сохраняет single-final маршрут; PROTO-007 — серверное opt-in дополнение. Клиентский поток и реальные LLM partial ещё не реализованы. Preferences/durable result/ledger — план AI, не часть текущего PROTO-007; отдельный сброс NPC в целевом поведении не предусмотрен.
- Настраиваемый NPC deadline и ожидание клиента +2 с не подтверждают цели LLM p95 ≤8 с или 4-player burst. Pending клиента ≤32 независим от GenerationQueue ≤4 unfinished и ≤1 на игрока.
- Bootstrap сохраняет ограничения отдельных полей `worldBytes/10` и `memory ≤32 MiB`; это не процентный лимит клиентского кеша. Окно ≤25 чанков и payload guard 64 MiB заданы MAP.
- Парольные формы и logout подключены; полная приёмка TASK-044 остаётся отдельной. Явный local LanguagePort использует общий NPC runtime; качество модели не квалифицировано.

## Живой мир: PROTO-010 (NEXT-006/010/011/013/014)

До реализации закреплён отдельный подконтракт `shared/world-life/`: Socket.IO событие `world-life` в том же авторизованном namespace `/game`, handshake остаётся `{version:3,token}`. Игровые пакеты `game` v3 и HTTP BABEL v2 не меняются. Версия новых пакетов — `v:1`; неизвестная версия даёт VERSION. Старый клиент может не слушать новый канал; новых полномочий это не даёт.

- Клиент: `{v:1,type:'scene-sync',requestId}`, `{v:1,type:'hand',requestId,action:'pickup',targetId}` или `{v:1,type:'hand',requestId,action:'place'}`. Лишние поля, playerId, итоговая позиция и роль запрещены. ID — 1–80 ASCII `[A-Za-z0-9_.:-]`; пакет ≤64 KiB, транспортный лимит частоты новых и повторных запросов 5/с с burst 5.
- Сервер: `{v:1,type:'scene-state',sceneId,revision,serverTimeMs,epochMs,definition,pots,apples}`. Полный ограниченный снимок активной карты: ≤128 экземпляров/64 заготовок, ровно 4 горшка, 5 яблок, 3 кошки. Опорное время и sceneId назначает сервер при старте; время Unix ms. Revision растёт при изменении RAM/durable состояния, не при каждом пакете. Смена sceneId разрешает сброс revision. После join/resync приходит полный снимок; декоративная фаза вычисляется из `serverTimeMs-epochMs`, seed и расписаний.
- Подтверждение: `{v:1,type:'hand-result',requestId,ok:true,action,apple}` после SQLite commit; отказ `{v:1,type:'hand-result',requestId,ok:false,code,message}`. Коды: INVALID, VERSION, UNAUTHORIZED, NOT_READY, FORBIDDEN, NOT_FOUND, TOO_FAR, BLOCKED, HANDS_FULL, HANDS_EMPTY, CONFLICT, RATE_LIMIT, UNAVAILABLE. Повтор receipt — историческое подтверждение, не актуальный снимок: следом приходит актуальный scene-state.
- Яблоко: `{id,mapId,state:'world',position:{x,y,z}}` либо `{id,mapId,state:'held',holderId}`. mapId — постоянная домашняя карта экземпляра; holderId — серверный playerId. Поза/привязка к кистям — клиентское представление. Один holderId встречается максимум 1 раз глобально. Отключение/выгрузка/смена карты не освобождает и не клонирует яблоко.
- Подъём выбирает ближайшее доступное яблоко без препятствия в радиусе 2 м; targetId должен совпасть с этим кандидатом (при равной дистанции — ID). Положить выбирает сервер: опора в 0,9 м перед авторитетным поворотом, без стены, горшка, другого яблока или игрока. Нельзя положить в воздухе или на другой карте. Все роли равноправны; BABEL inventory не меняется.
- Подъём/опускание сериализуются с durable receipt по `(playerId,requestId)`, нормализованному действию и карте. То же тело возвращает прежний результат, другое — CONFLICT. Сохранённые отказы тоже не становятся новым действием после reconnect; для нового нажатия нужен новый ID. Транспортные/авторизационные отказы и ошибка БД не объявляются durable.
- Горшок `{id,position}` сдвигается только проверенным касанием наземного движения; клиент не отправляет команду толкания. Полный путь и footprint проверяются по bitmap/опоре/ceiling, зоне карты, другим горшкам, яблокам и игрокам; заблокированное толкание блокирует проход через горшок. Положение только в RAM; reconnect сохраняет, restart сбрасывает.
- Изменившийся scene-state отправляется надёжно не чаще broadcastHz и до game delta. Неизменившееся состояние/время обновляется volatile не чаще 1 Гц, без offline-очереди. Один снимок карты строится для всех её игроков на broadcast-шаге; полная неизменная definition не перепарсивается на каждом шаге. Общий outbound budget обоих событий — максимум 32 ожидающих надёжных пакета и 1 MiB; превышение принудительно закрывает транспорт, а не теряет revision-dependent delta. Пропуск volatile полного снимка безопасен; scene-sync читает текущее состояние.

Техническое правило безопасного рестарта: footprint исходного горшка (±0,30 м XZ) остаётся зарезервированным для RAM-сброса. Backend отклоняет durable-опускание яблока в этот footprint даже после перемещения горшка. Горшки также не входят в footprint fallback spawn. При join сохранённая/начальная позиция проверяется по текущим горшкам дополнительно к static support; непригодная позиция использует существующий fallback spawn. Политика зон/ролей NEXT-002 не меняется. Динамические sweep-проверки используют квадратные footprints, включая диагональные углы.

Уточнение bounded transport v3: input дедуплицируется монотонным sequence мира, его requestId не записывается в connection-scoped Set и может повторяться. Прочие game-команды ограничены 5/с с burst 10; до 4096 уникальных ID на соединение, затем явный отказ/закрытие и новый join вместо неограниченного роста. Durable hand IDs живут отдельно в SQLite. Place требует именно authoritative motion.grounded=true; малая высота на первом rising-шаге не считается опорой.
