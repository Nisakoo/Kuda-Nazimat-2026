# PROTO — Общий контракт клиента и сервера

## Цель

Зафиксировать предварительный версионируемый контракт без привязки к реализации клиента или сервера. Игровой контракт и API MLX/Ollama — разные границы; браузер не обращается к inference напрямую.

## Требования

- **PROTO-001:** Типы и runtime-схемы находятся в `shared/protocol/` ([SHARED](shared-contracts.md)); сервер и клиент используют их напрямую без отдельных копий. Все сообщения имеют версию протокола и тип; запросы — requestId, снимки/обновления — revision или tick. Несовместимая версия отклоняется понятной ошибкой.
- **PROTO-002:** Клиент отправляет вход в мир, ввод/команды движения, взаимодействие с объектом или NPC, текстовое сообщение игрокам и другие разрешённые действия. Сервер отправляет подтверждение входа, playerId, начальный снимок, создание/изменение/удаление сущностей, игровые события, доставленные текстовые сообщения, коррелированные ответы NPC и ошибки.
- **PROTO-003:** Игровой ввод описывает намерение, не устанавливает авторитетную позицию, здоровье, инвентарь или владельца. Сервер проверяет структуру, принадлежность игроку, последовательность и допустимость команды.
- **PROTO-004:** Снимок и изменения ограничены областью интереса игрока (AOI); revision/sequence позволяют отбрасывать устаревшие данные и запрашивать новый снимок при разрыве последовательности. Полный мир не рассылается. Delta updates допускаются без обязательной сложной компрессии.
- **PROTO-005:** После переподключения клиент повторно подтверждает доступ и получает согласованный снимок. Повторы действий не создают двойной эффект; неограниченная очередь команд движения во время потери связи не воспроизводится.
- **PROTO-006:** Контракт определяет ограниченные размеры сообщений, коды ошибок, статусы соединения и корреляцию ответов NPC. Пользовательские данные не считаются доверенными ни на клиенте, ни на сервере.
- **PROTO-007:** *(v2, не входит в v1.)* В v1 NPC-диалог — одна пара `npc-question` → `npc-answer`/`error` с таймаутом клиента 10 с. Начиная с v2 NPC-диалог использует запрос, отмену, временные полные снимки текста и получение durable-результата, описанные ниже. Сервер назначает владельца по AUTH, проверяет npcId/dialogueId и доступ/дистанцию, не доверяет playerId из payload. Успешный финал содержит полный текст и persisted=true только после commit. Чужие/закрытые диалоги и устаревшие seq не меняют UI. Повтор requestId не создаёт второй эффект; reconnect читает результат/статус без повторной generation. Гонку completed/cancel/reset/access loss разрешает атомарный переход STORE-007, не порядок пакетов у клиента. Подтверждения каждого фрагмента и replay частичного текста не требуются.

- **PROTO-008:** Сервер, реализующий v1, соблюдает уточнения ниже. Они не меняют схемы клиента и проверяются fixtures в `shared/protocol/fixtures.json`.

## Игровое дополнение BABEL (PROTO-009)

- **PROTO-009:** `/api/babylon` — отдельный HTTP-подконтракт с собственной версией `v: 2`, типами и строгими парсерами в `shared/babylon/`. Он не меняет Socket.IO v1 и не реализует потоковый NPC v2 из PROTO-007. Оба клиента используют один исполняемый контракт.

`POST`, JSON до 256 KiB, `Authorization: Bearer <token>`, без redirect/cache. Запрос `{v:2, requestId, action:{type,...}}`. ID 1–128 символов `[A-Za-z0-9_.:-]`; лишние поля запроса отклоняются. Владелец назначается из сессии. Для buy/feed/npc/chat/carve требуется управляющее соединение, уже вошедшее в мир; после ожидания генерации сессия и управление проверяются снова.

| action.type | Поля | Результат |
|---|---|---|
| state | — | Личный снимок; клиент опрашивает раз в секунду |
| enroll | size: 1–4, native, learning | Группа, роль, языки; повторное вступление запрещено |
| languages | native, learning | Два разных доступных языка |
| intro-seen | — | Информационное окно просмотрено |
| buy / feed | targetId, item | Проверка роли, расстояния, инвентаря, шага задания |
| chat | text | Доставка группе с переводом по языкам получателей |
| npc | targetId, text | Личный ответ на изучаемом языке |
| carve | drawing | Неизменяемый камень группы |
| word-save | id?, word, translation, note | Создать/изменить собственную запись |
| word-delete | id | Удалить собственную запись |
| suggest | word | Предложение перевода на родной язык |

Успех `{v:2, requestId, state, notice?, suggestion?}` приходит после SQLite commit. Снимок содержит profile, party, task/goatGuide, inventory, fed, stones, words, messages, replies; чужой словарь, исходники чужих переведённых сообщений и личные диалоги не выдаются. Ответ клиент ограничивает 8 MiB и валидирует до отображения. Поздний polling-ответ не заменяет результат новой команды.

Лимиты коллекций и текста — BABEL. Камень: координаты 0–320, ≤64 штрихов, ≤256 точек/штрих, ≤4096 точек суммарно. Поля игрока, роли, прогресса и количества предметов не принимаются как команды. Все тексты отображаются без HTML.

Идемпотентность по `(playerId, requestId)` и SHA-256 нормализованного действия: тот же запрос возвращает сохранённое подтверждение и актуальный снимок без второго эффекта; другое тело даёт CONFLICT. Неудачный перевод разрешено повторить с тем же ID; успешные доставки не дублируются. После рестарта незавершённые доставки помечаются ошибкой. Для сообщения резервируется один слот общей очереди; уникальные целевые языки выполняются последовательно внутри него. Совпадающие языки не требуют генерации.

Ошибка `{v:2, requestId, error:{code,message}}`; до разбора запроса допускается общий `{error}` без requestId. HTTP: INVALID 400, UNAUTHORIZED 401, FORBIDDEN 403, CONFLICT/NOT_READY 409, RATE_LIMIT 429, UNAVAILABLE 503. Ошибка не подменяется исходным текстом или клиентским успехом. На карте market участник BABEL не может обойти этот контракт через старые chat-send/npc-question.

## Игровое движение v3 (MOVE-013)

Текущая согласованная поставка использует `auth.version: 3` и `v: 3` во всех игровых пакетах. Версии 1/2 отклоняются с VERSION; параллельная поддержка не требуется. Формы и лимиты прежнего контракта ниже сохраняются, кроме явно перечисленного:

- `input`: обязательные `sprint: boolean`, `jumpId: safe integer ≥0` дополнительно к sequence/direction/preparedChunks. Клиент не отправляет физическое состояние. jumpId монотонен в соединении; 0 — нет запроса; увеличенный ID обрабатывается один раз, даже при отказе в воздухе. Повтор ID не прыгает повторно. После join нового соединения счётчик и подтверждение обнуляются.
- Сущность игрока содержит `motion: {grounded,phase,verticalVelocity,locomotion,stamina,sprintBlocked,jumpAck}`. grounded/sprintBlocked — boolean; phase — grounded/rising/falling; locomotion — idle/walk/sprint; stamina ∈[0,100], verticalVelocity ∈[-100,100], jumpAck — safe integer ≥0. grounded согласован с phase и нулевой вертикальной скоростью. Поля обязательны для character.kind=player, NPC их не получает.
- При пропуске delta запрашивается snapshot. Resync не сбрасывает jumpAck или запас; новое соединение сбрасывает только ввод/ID. Никакого replay ввода.
- Авторитетные параметры и алгоритм — MOVE и SHARED. Сервер проверяет весь путь и след с preparedChunks; клиент передаёт исходное намерение, разрешённое скольжение не теряется.
- Подконтракт NPC остаётся npc-question/npc-answer; черновик потокового NPC ниже не реализуется этим переходом. HTTP BABEL сохраняет v2.

## Базовый контракт v1 (история форм, v3 наследует с изменениями выше)

Это клиентский контракт из ветки `feat-base-client`; исполняемая версия — `shared/protocol/`. Вход (mock по имени) описан в [AUTH](server-auth.md). Готовая серверная сессия передаётся приложению как `{token, expiresAt}` и хранится в памяти, без localStorage/URL/логов. Токен — непрозрачная строка 16–512 символов без пробельных и управляющих символов, `expiresAt` — Unix ms.

**Транспорт.** Socket.IO: namespace `/game`, path `<serverUrl pathname>/socket.io`; на клиенте autoConnect и reconnection отключены. Handshake: `auth: {version: 1, token}`. Все игровые данные идут одним событием `game`. HTTP-источник мира `<serverUrl>/world/` требует тот же `Authorization: Bearer <token>`; публичного fallback нет, redirect запрещён, `Cache-Control: no-store`.

**Пакеты.** Все пакеты — JSON-объекты `{v: 1, type, ...}`. Лимиты:

- пакет ≤256 KiB UTF-8;
- ≤256 сущностей в AOI, ≤256 upsert, ≤128 remove;
- ID 1–80 символов `[A-Za-z0-9_-]`;
- координаты ±1e6, скорость ≤20;
- имя ≤80, чат 1–500, вопрос NPC ≤240, ответ NPC ≤4000 символов.

Неизвестные поля, лишние компоненты и нечисловые координаты отклоняются.

| Направление | type | Данные |
|---|---|---|
| клиент → сервер | join | requestId, mapId |
| клиент → сервер | input | requestId, sequence, direction {x,z} (‖d‖ ≤ 1, намерение), preparedChunks[] (≤25 ID чанков) |
| клиент → сервер | interact | requestId, targetId |
| клиент → сервер | npc-question | requestId, targetId, text |
| клиент → сервер | chat-send | requestId, text |
| клиент → сервер | resync | requestId, revision |
| сервер → клиент | joined | requestId, playerId, revision, snapshot {tick, entities}, world (bootstrap) |
| сервер → клиент | snapshot | revision, snapshot |
| сервер → клиент | delta | revision, baseRevision, tick, upsert[], remove[] |
| сервер → клиент | interacted | requestId, targetId |
| сервер → клиент | npc-answer | requestId, targetId, text |
| сервер → клиент | chat | requestId, messageId, playerId, name, text |
| сервер → клиент | error | requestId, code, message |

`joined.snapshot` обязан содержать сущность `playerId` с `character.kind = player` и `transform`. Компоненты сущности: `transform {position, rotationY}`, `movement {direction, speed}`, `renderable {assetId}`, `interactable {radius, label}`, `character {kind: player|npc, name}`, `animationState {name}`. Bootstrap `world`: `manifestUrl` (путь относительно `/world/`), `worldBytes`, `manifestBytes ≤ worldBytes/10`, `assets` — до 128 записей `path → {bytes ≤ worldBytes/10, memory ≤ 32 MiB}`.

**Ошибки.** Коды: UNAUTHORIZED, VERSION, INVALID, FORBIDDEN, RATE_LIMIT, NOT_READY, UNAVAILABLE. Клиент закрывает сессию при UNAUTHORIZED и разрывает соединение без retry при VERSION.

**Запросы.** requestId уникален в рамках соединения; сервер не повторяет эффект дубликатов. Ответ без подтверждения за 10 секунд клиент считает ошибкой. Ожидающих запросов у клиента ≤32, сообщений в чате ≤50, всё отображается как текст, без HTML.

**Частоты и движение.** Симуляция сервера — 20 Hz, рассылка AOI — до 10 Hz. Клиент отправляет последнее намерение до 20 Hz, не очередь движения. sequence монотонен в соединении и начинается заново после нового join. Сервер проверяет принадлежность preparedChunks карте и не пускает игрока в неподготовленную область. Клиент при неготовой области отправляет нулевое движение и не меняет авторитетную позицию.

**Revision.** revision монотонен в подтверждённом потоке AOI. Delta применяется только при `baseRevision` = последней revision и `revision = baseRevision + 1`; старые пакеты игнорируются. При пропуске клиент очищает историю отображения и отправляет `resync`. Snapshot не откатывает revision/tick. Повторное соединение всегда делает join и получает новый снимок, без воспроизведения действий до разрыва. Клиент применяет обновления на шаге своей сессии; входная очередь — максимум восемь пакетов, переполнение вызывает resync. Удалённые объекты интерполируются с задержкой 100 ms по последним восьми снимкам.

**Подключение.** Retry клиента: 1/2/4 секунды, не более трёх попыток после потери связи; timeout подключения 5 секунд. При отказе авторизации или несовместимой версии retry прекращается. Сервер не доверяет присланным preparedChunks, requestId и sequence как доказательству полномочий.

### Уточнения для сервера (PROTO-008)

Клиент v1 уже реализован. Уточнения выбраны так, чтобы его поведение было корректным.

1. **Отказ handshake** — `connect_error` с `data: {code, message}`:
   - `UNAUTHORIZED` — нет, истёк или отозван токен;
   - `VERSION` — `auth.version ≠ 1`;
   - `UNAVAILABLE` — заняты все 4 слота игроков или сервер останавливается.

   На `UNAVAILABLE` клиент выполняет свои 3 retry и показывает «Сервер недоступен».
2. **Сообщения вне запроса.** `error`, не связанный с запросом клиента (перехват управления, истечение сессии), имеет `requestId: "server"`. Для `chat` другого игрока `requestId` — это requestId отправителя.
3. **Delta.** `upsert` содержит **полную** сущность со всеми текущими компонентами: клиент заменяет сущность целиком, отсутствующий компонент считается удалённым. Сервер отправляет delta только при изменениях, и revision растёт только с отправленными delta. Ответ на `resync` — `snapshot` с текущей (последней отправленной) revision. После него поток продолжается от этой revision.
4. **Ввод.** Сервер применяет последнее намерение до следующего `input`. Если `input` нет 250 ms, намерение обнуляется: клиент шлёт `input` через volatile emit, и потерянная «остановка» не должна двигать игрока бесконечно. `input` с `sequence` ≤ последнего принятого игнорируется. Превышение частоты `input` отбрасывается молча, без `error`.
5. **Дубликаты.** Повтор уже использованного в соединении requestId получает `error INVALID` и не даёт второго эффекта.
6. **HTTP `/world/*`.** Клиент считает 401/403 потерей сессии и закрывает её. Поэтому 401/403 означают только отказ сессии. Ресурс вне допустимой области или неизвестный путь возвращают 404.
7. **Ответ входа.** `POST /api/auth/guest` (mock-вход по имени, AUTH-006) возвращает ровно `{token, expiresAt}`: клиентский `parseServerSession` отклоняет лишние поля.

Детальное поведение сервера — [REALTIME](server-realtime.md), [AUTH](server-auth.md), [SERVER-WORLD](server-world.md), [NPC](server-npc-dialogue.md).

## NPC-подконтракт v2 (черновик)

Раздел — черновик следующей версии протокола. Он требует изменения клиента и в v1 не реализуется. Имена ниже фиксируют NPC-подконтракт; общий envelope и машинные схемы оформляются до реализации v2. Каждое сообщение имеет `version`, `type`, `requestId`; ID — непустые строки до 128 ASCII-символов (буквы, цифры, `_`, `-`, `.`, `:`). Seq — неотрицательный safe integer. Неверные типы, версия и защищённые поля отклоняются runtime-валидацией. Полный NPC-envelope ≤32 КиБ UTF-8, полный текст ответа ≤16 КиБ; ограничения проверяются до неограниченного выделения памяти. Токенные лимиты LLM применяются дополнительно.

| type | Направление | Данные и семантика |
|---|---|---|
| `npc.dialogue.request` | клиент → сервер | dialogueId, npcId, locale (`ru`, `en`, `es`) как ожидание сохранённой настройки, text: непустой текст ≤4096 UTF-8 байт. dialogueId получен при разрешённом взаимодействии, но не является доказательством права. |
| `npc.dialogue.cancel` | клиент → сервер | dialogueId, requestId отменяемого запроса. Идемпотентно; чужой запрос недоступен. Если completed уже committed, возвращается его результат/статус, а не второй cancelled. |
| `npc.dialogue.preferences` | клиент → сервер | dialogueId, locale (`ru`, `en`, `es`), responseStyle (`standard`, `simple_no_formulas`). Явная настройка, не извлечение моделью из текста. Уникальный requestId операции не совпадает с ID generation. |
| `npc.dialogue.preferences.result` | сервер → владелец | dialogueId, locale, responseStyle, persisted=true и memoryRevision после commit; при ошибке code/message без persisted=true. Действует для запросов, принятых после commit; уже принятые используют снимок настроек при приёме. |
| `npc.dialogue.event` | сервер → владелец | dialogueId, npcId, seq, kind: queued/running/partial/completed/cancelled/error. partial содержит **весь накопленный текст**, не delta; клиент заменяет временный текст. completed содержит полный text, finishReason, persisted=true и memoryRevision. error содержит ограниченный code и безопасное message. |
| `npc.dialogue.result` | клиент → сервер | dialogueId и requestId существующего запроса. Только чтение, без новой generation. |
| `npc.dialogue.result.response` | сервер → владелец | dialogueId, npcId, state. Для completed — полный text, finishReason, persisted=true и memoryRevision; для активного — статус без необходимости восстанавливать partial. Для failed — сохранённый code и безопасное message, для cancelled — причина отмены; для прерванного — interrupted, для очищенного текста — result_expired. Terminal-ответ заменяет временное состояние независимо от seq. Если terminal seq сохранён, ответ содержит lastSeq; для восстановленного interrupted после crash он может отсутствовать: сервер не выдумывает seq по потерянным partial. |

### Ограниченный streaming и восстановление

- Серверные события запроса имеют возрастающий seq. Снимки partial отправляются не чаще 10 раз/с, включают весь накопленный текст и могут пропускаться/объединяться. Клиент применяет только более новый снимок, заменяя текст, а не добавляя его. Пропуск seq безопасен для partial и сам по себе не отменяет generation. Completed и terminal result всегда авторитетнее partial независимо от seq; после terminal запоздалый partial не применяется. Идентичность/владелец/dialogueId по-прежнему проверяются: приоритет terminal не разрешает изменить чужой или закрытый диалог.
- Отдельного `npc.dialogue.ack` нет. Сервер не хранит историю временных фрагментов, не ждёт подтверждения каждого снимка и не воспроизводит их после reconnect. Seq нужен для устаревших событий, не для собственного надёжного транспорта поверх Socket.IO.
- Последний pending partial может заменяться новым до отправки. Лимит **64 КиБ на запрос** включает очереди приложения и транспорта согласно LLM-011, не только видимый массив в сервисе. Временные сообщения не должны попадать в неограниченную offline/retry-очередь Socket.IO. При отсутствии доступного места partial пропускается; при невозможности ограничить буфер активный запрос отменяется, соединение с медленным потребителем закрывается. Полный финал не копируется в бесконечную retry-очередь.
- Commit результата не зависит от клиентского ACK. Terminal seq сохраняется вместе с финалом; повторная доставка того же финала не создаёт новый эффект. Если committed-финал не удалось доставить, БД остаётся источником результата. Медленный клиент не переводит уже completed-запрос в cancelled.
- При disconnect queued/running-запрос отменяется по LLM-011, если completed ещё не победил в гонке. После reconnect сервер заново проверяет доступ; клиент читает result и заменяет временный текст полным результатом либо показывает cancelled/interrupted/error. Активный статус при ещё незавершённой отмене не означает восстановление потока. Чтение статуса ограничено 2 запросами/с на игрока, суммарно с других вкладок; автоматическая повторная generation отсутствует.
- Closed dialogue не получает поздний текст. Прочитать прошлый собственный результат после нового входа можно по проверенной принадлежности сохранённого dialogueId, без восстановления права управлять прежним активным диалогом. Если поток не завершился в ожидаемое время, UI читает result; нельзя навсегда ждать единственного потерянного terminal-события.
- Все ответы отображаются как текст, не HTML. Обозначение partial как временного означает отсутствие подтверждённого сохранения, а не гарантию проверки фактов или безопасности содержания.

### Настройки, идемпотентность и ошибки

Язык хранится в preferences (default ru). Для нового dialogue.request locale должен совпасть с сохранённой настройкой, иначе locale_mismatch. Сам запрос не меняет настройку. Для принятого запроса фиксируются locale/responseStyle и серверный профиль выхода 128/256 токенов; последующие изменения действуют только на новые запросы. responseStyle отвечает за стиль, а не разрешает клиенту менять ресурсы LLM.

После AUTH/проверки владельца существующий requestId и fingerprint разрешаются **до** проверки текущего locale, частоты новых запросов и вместимости очереди. Поэтому повтор ранее принятого запроса после смены настроек возвращает его прежний статус/результат. Другой тип операции или содержимое с тем же ID — request_conflict. Проверки допуска и ограничение всех незавершённых запросов **четырьмя**, по одному на игрока, атомарны; статус принятия не выдаётся запросу, который не зарезервировал квоту и не записан в БД. При ошибке durable-приёма резерв освобождается без запуска inference. Слот физически останавливающегося вычисления повторно не используется.

Коды NPC: invalid_request, forbidden, unsupported_locale, locale_mismatch, busy, queue_timeout, input_too_long, output_limit, model_unavailable, resource_limit, generation_timeout, slow_consumer, persistence_error, request_conflict, interrupted, result_expired. Отмена — отдельный terminal-kind. Ошибка БД не содержит persisted=true; persistence_error при отказе записи — предварительный статус, не доказательство durable failed. После восстановления result возвращает фактический committed terminal либо interrupted по STORE-007. State результата соответствует STORE-006 (accepted/queued/running/completed/cancelled/failed/interrupted); result_expired означает сохранённый terminal без уже очищенного текста. Event kind=error соответствует failed с code; interrupted при необходимости передаётся как error с code=interrupted. Ни браузер, ни LLM не задают backend URL, system prompt, source corpus, игровые права, лимиты generation или memoryRevision. Общая защита от flood применяется также к result/cancel/preferences: повторная операция не должна обходить транспортные лимиты даже при идемпотентности.

## Сценарии

- **S1 · PROTO-001–003, 006:** Given неверная версия/форма либо команда чужого игрока; When сообщение приходит; Then оно отклоняется без изменения мира.
- **S2 · PROTO-004–005:** Given пропуск revision и reconnect; When клиент возвращается; Then получает актуальный снимок AOI без повторного эффекта старых действий.
- **S3 · PROTO-006–007 (v2):** Given partial-снимки с пропусками/дублями, закрытие диалога, отмена и reconnect; When получен запоздалый снимок или результат после commit; Then текст заменяется без склейки/дубликатов, пропуск partial не требует replay/ACK, есть один durable terminal и нет чужого текста/повторной generation. Проверяются оба порядка cancel/reset/logout и commit, смена preferences до retry, медленный transport, polling результата и отсутствие скрытых offline-буферов.
- **S4 · PROTO-008:** Given сервер v1 и fixtures; When происходят занятые слоты, перехват управления, чат другого игрока, неподвижный мир, потерянная остановка и запрос чанка вне области; Then клиент v1 получает `connect_error UNAVAILABLE`, `error` с `requestId: "server"`, корректный chat, отсутствие пустых delta, остановку через 250 ms и 404 без закрытия сессии.

## Ограничения и вне scope

NPC partial-снимки не меняют правила revision/delta для мира. Настройки транспорта и схемы обеих сторон фиксируются до реального сетевого обмена; TypeScript-типы не заменяют runtime-валидацию. Полный архив истории через этот streaming-контракт не пересылается.

## Открытые вопросы

Решения по вопросам, оставленным клиентом после rebase:

- **Envelope, ID, лимиты.** v1 сохраняет `v`, ID до 80 символов `[A-Za-z0-9_-]`, пакеты до 256 KiB и лимиты в символах — так, как реализовано в клиенте. Вариант с `version`, ID до 128 символов и лимитами в UTF-8-байтах относится только к черновику v2 и будет согласован вместе с ним.
- **`npc-question`/`npc-answer`** — это NPC v1 ([NPC](server-npc-dialogue.md)), а не реализация PROTO-007. Переход на `npc.dialogue.*` — v2.
- **Таймаут 10 с.** Сервер v1 укладывается в него дедлайном 8–9 с (NPC-002). Цели LLM для четырёх игроков (до 32 с) требуют v2 с потоком и изменения клиента.
- **Квоты.** Pending-лимит клиента (32) и серверная квота NPC (≤4 незавершённых, ≤1 на игрока) независимы: сервер отклоняет лишний вопрос `RATE_LIMIT`/`UNAVAILABLE` (NPC-001).
- **Handshake, чат, bootstrap, preparedChunks.** Сервер поддерживает предложенные клиентом схемы без изменений, с уточнениями PROTO-008. Чат v1 — вся текущая карта. Вход — [AUTH](server-auth.md).

Открыто для v2: envelope (`v` или `version`), выдача dialogueId, ограничитель транспортных буферов, механики [BABEL](game-babylon.md)/[SCENE](demo-scene-market.md): перевод чата, камень, задания, инвентарь, словарь, языки игрока.

## Живой мир: PROTO-010 (NEXT-006/010/011/013/014)

До реализации закреплён отдельный подконтракт `shared/world-life/`: Socket.IO событие `world-life` в том же авторизованном namespace `/game`, handshake остаётся `{version:3,token}`. Игровые пакеты `game` v3 и HTTP BABEL v2 не меняются. Версия новых пакетов — `v:1`; неизвестная версия даёт VERSION. Старый клиент может не слушать новый канал; новых полномочий это не даёт.

- Клиент: `{v:1,type:'scene-sync',requestId}`, `{v:1,type:'hand',requestId,action:'pickup',targetId}` или `{v:1,type:'hand',requestId,action:'place'}`. Лишние поля, playerId, итоговая позиция и роль запрещены. ID — 1–80 ASCII `[A-Za-z0-9_.:-]`; пакет ≤64 KiB, транспортный лимит частоты новых и повторных запросов 5/с с burst 5.
- Сервер: `{v:1,type:'scene-state',sceneId,revision,serverTimeMs,epochMs,definition,pots,apples}`. Полный ограниченный снимок активной карты: ≤128 экземпляров/64 заготовок, ровно 4 горшка, 5 яблок, 3 кошки. Опорное время и sceneId назначает сервер при старте; время Unix ms. Revision растёт при изменении RAM/durable состояния, не при каждом пакете. Смена sceneId разрешает сброс revision. После join/resync приходит полный снимок; декоративная фаза вычисляется из `serverTimeMs-epochMs`, seed и расписаний.
- Подтверждение: `{v:1,type:'hand-result',requestId,ok:true,action,apple}` после SQLite commit; отказ `{v:1,type:'hand-result',requestId,ok:false,code,message}`. Коды: INVALID, VERSION, UNAUTHORIZED, NOT_READY, FORBIDDEN, NOT_FOUND, TOO_FAR, BLOCKED, HANDS_FULL, HANDS_EMPTY, CONFLICT, RATE_LIMIT, UNAVAILABLE. Повтор receipt — историческое подтверждение, не актуальный снимок: следом приходит актуальный scene-state.
- Яблоко: `{id,mapId,state:'world',position:{x,y,z}}` либо `{id,mapId,state:'held',holderId}`. mapId — постоянная домашняя карта экземпляра; holderId — серверный playerId. Поза/привязка к кистям — клиентское представление. Один holderId встречается максимум 1 раз глобально. Отключение/выгрузка/смена карты не освобождает и не клонирует яблоко.
- Подъём выбирает ближайшее доступное яблоко без препятствия в радиусе 2 м; targetId должен совпасть с этим кандидатом (при равной дистанции — ID). Положить выбирает сервер: опора в 0,9 м перед авторитетным поворотом, без стены, горшка, другого яблока или игрока. Нельзя положить в воздухе или на другой карте. Все роли равноправны; BABEL inventory не меняется.
- Подъём/опускание сериализуются с durable receipt по `(playerId,requestId)`, нормализованному действию и карте. То же тело возвращает прежний результат, другое — CONFLICT. Сохранённые отказы тоже не становятся новым действием после reconnect; для нового нажатия нужен новый ID. Транспортные/авторизационные отказы и ошибка БД не объявляются durable.
- Горшок `{id,position}` сдвигается только проверенным касанием наземного движения; клиент не отправляет команду толкания. Полный путь и footprint проверяются по bitmap/опоре/ceiling, зоне карты, другим горшкам, яблокам и игрокам; заблокированное толкание блокирует проход через горшок. Положение только в RAM; reconnect сохраняет, restart сбрасывает.
- Изменившийся scene-state отправляется надёжно не чаще broadcastHz и до game delta. Неизменившееся состояние/время обновляется volatile не чаще 1 Гц, без offline-очереди. Один снимок карты строится для всех её игроков на broadcast-шаге; полная неизменная definition не перепарсивается на каждом шаге. Общий outbound budget обоих событий — максимум 32 ожидающих надёжных пакета и 1 MiB; превышение принудительно закрывает транспорт, а не теряет revision-dependent delta. Пропуск volatile полного снимка безопасен; scene-sync читает текущее состояние.

Техническое правило безопасного рестарта: footprint исходного горшка (±0,30 м XZ) остаётся зарезервированным для RAM-сброса. Backend отклоняет durable-опускание яблока в этот footprint даже после перемещения горшка. Горшки также не входят в footprint fallback spawn. При join сохранённая/начальная позиция проверяется по текущим горшкам дополнительно к static support; непригодная позиция использует существующий fallback spawn. Политика зон/ролей NEXT-002 не меняется. Динамические sweep-проверки используют квадратные footprints, включая диагональные углы.

Уточнение bounded transport v3: input дедуплицируется монотонным sequence мира, его requestId не записывается в connection-scoped Set и может повторяться. Прочие game-команды ограничены 5/с с burst 10; до 4096 уникальных ID на соединение, затем явный отказ/закрытие и новый join вместо неограниченного роста. Durable hand IDs живут отдельно в SQLite. Place требует именно authoritative motion.grounded=true; малая высота на первом rising-шаге не считается опорой.
