# AUTH — Вход, сессии и аккаунты

## Цель

Дать браузеру серверную сессию `{token, expiresAt}` и защитить аккаунт игрока от входа под его именем другим человеком. Сессии хранятся на сервере, поэтому их можно отозвать в любой момент: выход, сброс пароля администратором, перехват. Способ передачи токена (handshake `auth.token`, `Authorization: Bearer`) и формат ответа входа не меняются, поэтому realtime, world и BABEL от способа входа не зависят.

Редакция 2026-11-01 реализована на сервере ([TASK-042](../tasks/042-server-auth-sessions.md)); поддержка в клиенте — [TASK-044](../tasks/044-client-auth-observability-handoff.md).

## Требования

### Режимы и аккаунты

- **AUTH-001 (режимы входа):** режим задаёт окружение ([SERVER](server-foundation.md) SERVER-009):
  - **production** — только регистрация и вход по имени и паролю. Пароль обязателен при регистрации. `POST /api/auth/guest` и `POST /api/auth/dev` отвечают `DISABLED`; конфигурация не может включить их в production — это ошибка запуска;
  - **development** и **test** — дополнительно вход по имени без пароля (`guest`, как раньше: одно имя — один игрок) и автовход `POST /api/auth/dev` (AUTH-016); регистрация и вход с паролем тоже работают, чтобы их можно было проверять. Вход без пароля разрешён только в аккаунт **без** пароля; аккаунт с паролем отвечает `PASSWORD_REQUIRED`.

  Имя — 1–32 символа после trim, без управляющих символов. Ключ аккаунта — имя в нижнем регистре; отображаемое имя сохраняется с регистрации или первого входа. Личность после входа устанавливается только по токену: playerId и имя из payload или handshake доказательством не являются.
- **AUTH-007 (пароль):** длина 6–128 символов Unicode после нормализации NFC, без управляющих символов; не совпадает с именем без учёта регистра. Требований к составу нет. Пароль не хранится, не логируется и не возвращается ни в одном ответе.
- **AUTH-008 (хранение пароля):** хеш scrypt из `node:crypto`: `N = 2^15`, `r = 8`, `p = 1`, соль 16 случайных байт на каждый пароль, ключ 32 байта. Хранится строка `scrypt$N$r$p$<соль base64url>$<хеш base64url>`, чтобы параметры можно было усилить позже. Если при успешном входе параметры записи слабее текущих, хеш пересчитывается и заменяется. Сравнение — `timingSafeEqual`. Хеширование асинхронное (вне игрового шага), одновременно выполняется не более 2 вычислений; лишние запросы ждут в очереди до 5 с, затем получают `UNAVAILABLE`. Для несуществующего имени вычисляется хеш-пустышка, чтобы время ответа не выдавало, есть ли аккаунт.
- **AUTH-011:** *(снято 2026-11-01.)* Перехода старых аккаунтов на пароли нет: данные до этой редакции тестовые. Production использует отдельный файл БД (SERVER-009) и начинается с чистой базы, где каждый аккаунт создан с паролем. Если в production всё же попал аккаунт без пароля, вход отвечает `CREDENTIALS`, а пароль ему выдаёт администратор (AUTH-010).
- **AUTH-016 (автовход разработчика):** только в development и test. `POST /api/auth/dev` с JSON-телом `{}` или `{name}` (`Content-Type: application/json`) выдаёт сессию `{token, expiresAt}` без пароля: без имени — аккаунт `dev`, с именем — аккаунт с этим именем (для проверки нескольких игроков в разных вкладках). Создаёт аккаунт без пароля при первом вызове. При старте в development сервер пишет в лог предупреждение, что вход без пароля включён.

### Сессии и отзыв

- **AUTH-002 (сессия):** токен — 32 байта `crypto.randomBytes`, base64url (43 символа). В БД — только SHA-256 токена и запись сессии: публичный `sessionId` (случайный, 12 символов base64url; используется в логах и на экране администратора, не даёт доступа), accountId, createdAt, expiresAt, IP входа, revokedAt и причина отзыва. Срок жизни — `sessionTtlMs` (12 ч) от входа, без продления. У аккаунта не больше `auth.maxSessions` (5) действующих сессий: новая сессия отзывает самую старую с причиной `limit`. Отозванные и истёкшие записи хранятся сутки для разбора и затем удаляются.
- **AUTH-003 (проверка):** Socket.IO-handshake `/game` проверяет `auth.version === 3` (иначе `VERSION`) и сессию: она существует, не истекла и не отозвана (иначе `UNAUTHORIZED`). Та же проверка выполняется для каждого защищённого HTTP-запроса (`/world/*`, `/api/babylon`, `/api/auth/logout`, `/api/auth/password`, `/api/telemetry/client`) — без кеширования положительного результата, чтобы отзыв действовал сразу. В момент `expiresAt` сервер отправляет соединению `error {requestId: "server", code: "UNAUTHORIZED"}` и закрывает его.
- **AUTH-012 (отзыв):** отзыв сессии — запись `revokedAt` и причины (`logout`, `password-changed`, `password-reset`, `operator`, `limit`) в одной транзакции. Отозванная запись — это и есть чёрный список: отдельного списка токенов нет, потому что сессии хранятся на сервере. Сразу после фиксации отзыва все Socket.IO-соединения этой сессии получают `error {requestId: "server", code: "UNAUTHORIZED", message}` с понятной причиной («Вы вышли из игры», «Пароль изменён», «Администратор завершил сессию») и закрываются; ожидающие NPC-запросы отменяются (NPC-004). Отзыв идемпотентен.
- **AUTH-009 (выход):** `POST /api/auth/logout` с `Authorization: Bearer` отзывает эту сессию (`logout`) и отвечает 204. Для неизвестной, истёкшей или уже отозванной сессии ответ тоже 204: выход не раскрывает состояние токена.
- **AUTH-005 (одно управляющее соединение):** у аккаунта одно управляющее игровое соединение. Новое соединение того же аккаунта, прошедшее handshake, **атомарно перехватывает управление**:
  1. прежнее соединение получает `error {requestId: "server", code: "UNAUTHORIZED", message: "Игра открыта в другом окне."}` и закрывается; клиент v3 на этот код не делает retry;
  2. его ожидающий NPC-запрос отменяется (NPC-004);
  3. сущность и playerId сохраняются, новое соединение после join продолжает с текущей позиции.

  Перехват закрывает соединение, но не отзывает сессию прежней вкладки. Сообщения прежнего соединения после перехвата не обрабатываются. Перехват не занимает второй слот (SERVER-006).

### Граница AUTH-сессии для планируемой памяти NPC

[NPC-AI](npc-character-behavior.md) использует существующий server-owned `sessionId` AUTH-002, а не отдельный gameId/команду администратора. Успешный новый login/guest/dev создаёт новую сессию и, после реализации NPC-AI, новое знакомство и исходное отношение каждого NPC к этому игроку. Предыдущая сессия может ещё действовать по AUTH-002, но её память не копируется новой. Scope — `(sessionId, playerId, npcId)`; знание публичного sessionId не является разрешением читать память.

Выход в меню без logout, reconnect и рестарт сервера сохраняют память только при повторном использовании **той же** ещё действующей сессии. Reload с утратой токена и новым входом не считается восстановлением прежнего scope. Истечение, logout и любой revoke закрывают прежний scope для чтения/prompt/result и отменяют pending-запросы; новая сессия не сбрасывает аккаунт, словарь, инвентарь, позицию или прогресс задания. Перехват соединения с тем же токеном сохраняет scope, с новой сессией — использует её новый scope. Квота generation остаётся ≤1/playerId, не умножается на разрешённые 5 AUTH-сессий.

Первый срез использует эту AUTH-семантику для ограниченной NPC-истории обоих путей: проверяет sessionId до model/retrieval/commit/delivery, исключает legacy без sessionId и чужую историю из BABEL snapshot/replay. Это не изменение TTL и не полный архив/компактная память. Предусмотренная миграция 009 с reconciliation прежней branch-схемы версии 4 не назначает старым текстам новую сессию и не выбирает политику очистки через AUTH FK cascade; интеграционная проверка ожидается. Прежние суммарные окна хранения остаются временной границей STORE-011/012; полный архив и очистка — STORE-006–010, объём реализации/проверок — TASK-070.

### Лимиты

- **AUTH-013 (лимиты попыток):** счётчики в памяти, сбрасываются при перезапуске:
  - **по имени** (ключ аккаунта): 5 неудачных входов или смен пароля за 15 мин → имя заблокировано на 15 мин; повторная блокировка в течение часа — на 60 мин. Успешный вход сбрасывает счётчик. Администратор может снять блокировку (AUTH-010);
  - **по IP**: не больше 30 запросов `/api/auth/*` в минуту и 10 регистраций в час. Loopback-адрес считается одним IP, поэтому в режиме одного компьютера основной защитой остаётся лимит по имени;
  - превышение — 429 `RATE_LIMIT` с `retryAfterSeconds`; заблокированное имя отвечает `RATE_LIMIT` и при верном пароле, чтобы перебор не узнал о совпадении.
- **AUTH-014 (лимиты защищённого HTTP):** token bucket на сессию: `/api/babylon` — 10 запросов/с, запас 20 (клиент опрашивает state раз в секунду); `/world/*` — 50 запросов/с, запас 300 (загрузка окна чанков при входе). Превышение — 429 без закрытия сессии. Срабатывания считаются метриками (OBS).

### HTTP API и администратор

- **AUTH-006 (HTTP API):** JSON до 1 KiB, неизвестные поля — 400. Успешный вход возвращает **ровно** `{token, expiresAt}`: клиент передаёт его в `GameApp.provideServerSession()` без преобразования.

  | Метод и путь | Режим | Тело | Успех |
  |---|---|---|---|
  | `POST /api/auth/guest` | development, test | `{name}` | 200 `{token, expiresAt}` |
  | `POST /api/auth/register` | все | `{name, password}` | 201 `{token, expiresAt}` |
  | `POST /api/auth/login` | все | `{name, password}` | 200 `{token, expiresAt}` |
  | `POST /api/auth/password` | все | `{name, password, newPassword}` | 200 `{token, expiresAt}`; все прежние сессии аккаунта отозваны (`password-changed`) |
  | `POST /api/auth/logout` | все | — (Bearer) | 204 |
  | `POST /api/auth/dev` | development, test | `{}` или `{name}` | 200 `{token, expiresAt}` (AUTH-016) |
  | `GET /api/auth/mode` | все | — | 200 `{password: true, guest: boolean, dev: boolean}` — какие способы входа включены, чтобы клиент выбрал форму или автовход |

  Ошибки — `{error: {code, message, retryAfterSeconds?}}`, сообщение — готовый текст для игрока:

  | code | HTTP | Когда |
  |---|---|---|
  | `INVALID` | 400 | имя, пароль или тело не проходят проверку; message называет, что именно |
  | `CREDENTIALS` | 401 | «Неверное имя или пароль»; одинаково для неизвестного имени и неверного пароля |
  | `NAME_TAKEN` | 409 | регистрация занятого имени |
  | `PASSWORD_REQUIRED` | 403 | гостевой вход в аккаунт с паролем |
  | `PASSWORD_CHANGE_REQUIRED` | 403 | вход временным паролем: нужно `POST /api/auth/password` |
  | `DISABLED` | 403 | способ входа выключен в этом окружении |
  | `RATE_LIMIT` | 429 | AUTH-013, с `retryAfterSeconds` |
  | `UNAVAILABLE` | 503 | очередь хеширования, ошибка БД, остановка сервера |

  Ответы на `/api/auth/*` с кодом 401 не означают потерю действующей сессии: это ответ формы входа, а не защищённого ресурса (PROTO-008 §6 относится к `/world/*`).
- **AUTH-010 (действия администратора):** только с loopback (OFFLINE-010), из экрана `/operator` (`POST /api/operator/actions/<действие>` с `{name}`) и из CLI `npm --prefix server run auth -- <команда> [--env production]`:
  - `reset-password <имя>` — генерирует временный пароль из 10 символов однозначного алфавита (без 0/O/1/l), показывает его администратору **один раз**, отзывает все сессии аккаунта (`password-reset`), помечает аккаунт «нужна смена пароля»; вход временным паролем отвечает `PASSWORD_CHANGE_REQUIRED`, пока игрок не задаст свой через `POST /api/auth/password`. Временный пароль действует 24 ч;
  - `revoke <имя>` — отзывает все сессии аккаунта (`operator`), игрок выходит из игры;
  - `unlock <имя>` — снимает блокировку AUTH-013;
  - `list` — аккаунты: имя, есть ли пароль, нужна ли смена, число действующих сессий, последний вход — без хешей и токенов.

  CLI меняет только БД: отозванная им сессия отклоняется при следующем запросе, а открытый сокет работающего сервера закрывает только экран администратора; блокировки AUTH-013 живут в памяти сервера, поэтому `unlock` выполняется с экрана. POST-запросы экрана администратора принимаются только с заголовком `Origin`, равным собственному origin сервера на loopback, и с заголовком `X-Operator: 1`: так посторонняя страница, открытая в браузере на том же компьютере, не может выполнить действие от имени администратора (CSRF).
- **AUTH-004 (секреты):** токены, их хеши, пароли, хеши паролей и временные пароли не пишутся в логи, метрики и ответы, кроме ответа входа (токен) и ответа администратору на сброс (временный пароль, один раз). В логах сессия обозначается `sessionId`. Секретов в репозитории нет.
- **AUTH-015 (хранение):** миграция БД добавляет к аккаунтам `password_hash` (NULL — пароля нет, допустимо только для аккаунтов development/test), `password_set_at`, `must_change_password`, `temp_password_expires_at`, к сессиям — `id` (sessionId), `created_ip`, `revoked_at`, `revoke_reason`. Миграция данных не удаляет ([STORE](server-persistence.md) STORE-002); чистая база production обеспечивается отдельным файлом БД окружения.

## Сценарии

- **S1 · AUTH-001, 003, 006:** Given development и вход «Аня»; When клиент подключается с токеном, без токена и с битым токеном; Then только первый проходит handshake и получает playerId «Ани», остальные — `connect_error UNAUTHORIZED`; `/world/` без токена — 401.
- **S2 · AUTH-001–002:** Given «Аня» уже входила и сервер перезапущен; When выполнен вход «аня»; Then тот же playerId, новый токен.
- **S3 · AUTH-003:** Given сессия с коротким TTL; When наступает `expiresAt`; Then соединение получает `error UNAUTHORIZED` и закрыто, повторный handshake отклонён.
- **S4 · AUTH-005:** Given игрок в мире с ожидающим NPC-вопросом; When тот же аккаунт подключается второй вкладкой; Then первая получает `UNAUTHORIZED` и отключена, её NPC-запрос отменён, во второй вкладке тот же playerId и позиция.
- **S5 · AUTH-004, 006–008:** Given production; When «Аня» регистрируется паролем «секрет 12»; Then 201 `{token, expiresAt}`, в БД строка `scrypt$…`, в логах и ответах нет ни пароля, ни токена, ни хеша. When второй игрок регистрирует «аня»; Then 409 `NAME_TAKEN`. When вход с неверным паролем и с несуществующим именем; Then оба — 401 `CREDENTIALS` с одинаковым сообщением.
- **S6 · AUTH-009, 012:** Given «Аня» в мире; When клиент вызывает logout; Then 204, её сокет получает `UNAUTHORIZED` «Вы вышли из игры» и закрыт, `/world/*` и `/api/babylon` с тем же токеном — 401, повторный logout — 204.
- **S7 · AUTH-013:** Given production; When пять неверных паролей «Ани» подряд; Then шестая попытка, даже с верным паролем, — 429 `RATE_LIMIT` с `retryAfterSeconds`, вход «Бориса» с того же IP работает; после `unlock Аня` вход с верным паролем проходит.
- **S8 · AUTH-010:** Given «Вера» забыла пароль в production; When администратор выполняет `reset-password Вера`; Then показан временный пароль; вход с ним — 403 `PASSWORD_CHANGE_REQUIRED`; `POST /api/auth/password` с новым паролем — 200 и сессия; старый временный пароль больше не подходит.
- **S9 · AUTH-010, 012:** Given «Аня» в мире в двух сессиях; When администратор выполняет `revoke Аня` с экрана `/operator`; Then все её сессии отозваны, сокет закрыт с сообщением «Администратор завершил сессию». When тот же POST приходит без `X-Operator` или с чужим `Origin`; Then 403 и ничего не отозвано.
- **S11 · AUTH-001, 016:** Given production; When вызваны `guest` и `dev`; Then оба — 403 `DISABLED`, `GET /api/auth/mode` — `{password: true, guest: false, dev: false}`; конфигурация, включающая вход без пароля в production, не запускается. Given development; When вызван `dev` без тела и с именем «Борис»; Then две сессии разных игроков без ввода пароля.
- **S10 · AUTH-002, 014:** Given шесть входов «Ани»; Then действует пять сессий, самая старая отозвана с причиной `limit`. Given 400 запросов `/world/*` за секунду одной сессией; Then лишние — 429, сессия остаётся действующей.

## Ограничения и вне scope

- HTTP без TLS в LAN: пароль можно перехватить в той же Wi-Fi-сети. Это принятый риск офлайн-режима (OFFLINE-015); снижается сетью роутера с WPA2/WPA3, устраняется HTTPS ([NEXT-009](world-next-stage.md)).
- Почта, восстановление пароля без администратора, внешние провайдеры, двухфакторный вход и роли кроме «игрок» и «администратор на loopback» — вне scope.
- Хранение токена на клиенте (память, sessionStorage) и экраны входа — клиентские решения ([ENTRY](client-auth-screens.md)).

## Передача клиенту

Функциональная форма клиента запрашивает `GET /api/auth/mode` и поддерживает `register`/`login`/`password`, `PASSWORD_CHANGE_REQUIRED`, гостевой и явный dev-вход только при разрешении сервера. Production больше не ограничен name-only UI. Выход очищает локальный токен и запрашивает `POST /api/auth/logout`; подтверждением считается HTTP 204, иначе UI предупреждает о неподтверждённом отзыве. Сообщение серверного `error UNAUTHORIZED` сохраняется. Токен остаётся только в памяти: reconnect/меню не создают новую сессию, reload с новым входом создаёт. Объём приёмки и оставшаяся работа — [TASK-044](../tasks/044-client-auth-observability-handoff.md); TASK-041 относится к NPC streaming.

## Открытые вопросы

- Минимальная длина пароля 6 выбрана ради простого входа в офлайн-игре; при необходимости повышается без изменения формата хранения.
