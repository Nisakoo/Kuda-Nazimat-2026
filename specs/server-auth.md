# AUTH — Регистрация, вход и серверная сессия

## Цель

Выдать браузеру серверную сессию `{token, expiresAt}` после регистрации или проверки пароля. Передача токена в handshake и Bearer сохраняет игровой PROTO v3. По явному разрешению пользователя реализуются пароли, регистрация, отзыв и ограничения попыток; прежнее исключение этих функций отменено. Старые гостевые аккаунты остаются доступными только через явно обозначенный demo-вход.

## Требования

- **AUTH-001:** Регистрация создаёт новый аккаунт, игрока и парольный credential атомарно. `name` — 1–32 UTF-16 единицы после trim, без управляющих символов U+0000–001F/U+007F–009F; ключ — имя в нижнем регистре. Отображаемое имя сохраняется при создании. Занятое имя, включая старый guest, нельзя присвоить регистрацией. Пароль — строка длиной 8–128 UTF-16 единиц и не более 512 UTF-8 байт; не обрезается, не нормализуется, не trim. Дополнительные правила состава не применяются. Парольный вход проверяет сохранённый credential и выдаёт новую сессию того же игрока. Ошибочный пароль, неизвестное имя и попытка password-login для guest дают одинаковый `INVALID_CREDENTIALS`. Legacy/demo `guest` создаёт только guest или возвращает существующий guest; для password account он никогда не выдаёт сессию. Старые guest не получают автоматически пароль и не требуют first-avatar.
- **AUTH-002:** Сессия — случайный токен из 32 байт `crypto.randomBytes`, base64url (43 символа), срок `sessionTtlMs` (12 ч), без продления. В SQLite хранится только SHA-256-хеш токена с accountId, createdAt и expiresAt. Клиент хранит токен только в памяти. `logout` удаляет текущую сессию из БД; другие сессии того же аккаунта не отзываются. Отозванный токен немедленно непригоден для HTTP, повторного handshake и игровых действий. Активный transport отозванной сессии закрывается, ожидающий NPC-запрос отменяется. Клиентское забывание токена не заменяет серверный отзыв.
- **AUTH-003:** Socket.IO-handshake `/game` проверяет `auth.version === 3` (иначе `VERSION`) и существующий неистёкший токен (иначе `UNAUTHORIZED`). Личность берётся только из сессии, не из payload. В `expiresAt` сервер отправляет `error {requestId: "server", code: "UNAUTHORIZED"}` и закрывает соединение. `/world/*`, `/api/avatar`, `/api/auth/state` и защищённые игровые HTTP API требуют действующий Bearer, иначе 401. Новый password account имеет устойчивое состояние `requiresAvatar=true`, пока `players.avatar_id IS NULL`. Наличие credential и NULL avatar — сохранённый marker, не переменная процесса. `/api/auth/state` возвращает это состояние; разрешённые handshake и avatar API не дают права join. Сервер отклоняет join до сохранения разрешённого avatarId. После сохранения marker снимается; перезапуск/повторный вход не меняет это правило. Legacy guest с NULL avatar сохраняет прежнее право играть.
- **AUTH-004:** Пароль хешируется асинхронным `node:crypto.scrypt`: версия `scrypt-v1`, N=32768, r=8, p=1, длина результата 64 байта; для каждого аккаунта новая случайная соль 16 байт, в БД hex. `maxmem` одного вызова 64 MiB; сравнение через `timingSafeEqual`. Для неизвестного имени/guest выполняется такой же KDF с dummy credential. Одновременно не более 2 KDF, очереди нет; перегрузка — `RATE_LIMIT`. Общий для guest/register/login фиксированный интервал 60 с: не более 20 попыток с адреса TCP-соединения и 10 с name_key; оба ограничения действуют вместе. X-Forwarded-For не считается доверенным. Хранилище лимитов содержит не более 2048 ключей фиксированной длины; активные записи не вытесняются для обхода, переполнение даёт `RATE_LIMIT`. Лимиты process-local, после перезапуска сбрасываются. Plaintext-пароли, credential, токены и хеши токенов не пишутся в логи и не возвращаются, кроме исходного токена в успешном auth-ответе. Секретов в репозитории нет.
- **AUTH-005:** У аккаунта одно управляющее игровое соединение. Новое соединение того же аккаунта после handshake атомарно перехватывает управление: прежнее получает `error {requestId: "server", code: "UNAUTHORIZED", message: "Игра открыта в другом окне."}` и закрывается; его NPC-запрос отменяется; playerId и позиция сохраняются. Старые сообщения не меняют мир; второй слот не занимается (SERVER-006). Проверка вместимости выполняется перед выдачей новой сессии; при заполнении guest/register/login возвращают 503 FULL. Новый account не создаётся при заполнении; после асинхронного KDF регистрация проверяет вместимость повторно до записи. Уже допущенный account может получить сессию для reconnect/перехвата при заполнении. Проверка при игровом attach остаётся авторитетной: выдача токена не резервирует слот.
- **AUTH-006:** Закрытый HTTP API; JSON-тела не более 1 KiB, неизвестные поля отклоняются. Все ответы `Cache-Control: no-store`.

  | Метод и путь | Тело / авторизация | Успех | Ошибки |
  |---|---|---|---|
  | `POST /api/auth/register` | `{name,password}` | 201 `{token,expiresAt}` | 400 INVALID; 409 NAME_TAKEN; 429 RATE_LIMIT; 503 FULL |
  | `POST /api/auth/login` | `{name,password}` | 200 `{token,expiresAt}` | 400 INVALID; 401 INVALID_CREDENTIALS; 429 RATE_LIMIT; 503 FULL |
  | `POST /api/auth/guest` | `{name}`; только demo guest | 200 `{token,expiresAt}` | 400 INVALID; 401 INVALID_CREDENTIALS; 429 RATE_LIMIT; 503 FULL |
  | `POST /api/auth/logout` | без тела или `{}`; действующий Bearer | 204, без тела | 400 INVALID; 401 UNAUTHORIZED |
  | `GET /api/auth/state` | действующий Bearer | 200 `{requiresAvatar:boolean}` | 401 UNAUTHORIZED |

  Ошибка — `{error:{code,message}}`, сообщение не содержит секретов; ошибка хранения — общий 503 UNAVAILABLE без внутренних подробностей. Успешный auth-ответ содержит **ровно** `{token,expiresAt}`: строгий клиентский парсер не расширяется ради marker. Identity берётся из авторизованного запроса; state не принимает чужие accountId/playerId. Неправильный метод не выполняет действие. После асинхронного чтения тела защищённая запись повторно проверяет сессию.

## Сценарии

- **S1 · AUTH-001, 003, 006:** Given guest «Аня»; When handshake с токеном, без него и с битым токеном; Then только первый получает playerId «Ани»; `/world/` без токена — 401.
- **S2 · AUTH-001–002:** Given существующий guest и перезапуск; When guest-вход по имени в другом регистре; Then тот же playerId и новый токен, пароль не присвоен.
- **S3 · AUTH-002–003:** Given короткий TTL или logout; When последующее HTTP/игровое действие, повторный handshake; Then отозванная/истёкшая сессия отклонена и активный transport закрыт.
- **S4 · AUTH-005:** Given игрок с pending NPC; When второе управляющее соединение; Then первое закрыто с UNAUTHORIZED, NPC отменён, playerId/позиция сохранены, старые сообщения не меняют мир.
- **S5 · AUTH-004, 006:** Given пустое/слишком длинное/управляющее имя, короткий/слишком длинный пароль, лишнее поле; When auth-запрос; Then 400 без создания аккаунта. Ответ успеха содержит только token/expiresAt. Логи не содержат секретов.
- **S6 · AUTH-001, 004:** Given новый password account; When правильный/неверный пароль, неизвестное имя, регистрация того же имени и guest-вход в него; Then правильный пароль возвращает тот же playerId, остальные отклоняются; две одинаковые парольные строки разных аккаунтов имеют разные salt/hash. Guest имя нельзя захватить регистрацией, включая гонку во время KDF.
- **S7 · AUTH-001, 003:** Given регистрация без avatar; When повторный вход/рестарт и join до/после сохранения avatar; Then state остаётся pending и join запрещён до подтверждения; после сохранения state=false, join разрешён. Legacy guest остаётся playable.
- **S8 · AUTH-004:** Given исчерпанные лимиты по имени/адресу, 2048 активных ключей или 2 KDF; When новая попытка; Then 429 без неограниченного накопления памяти/работы; после 60 с истёкшие записи освобождаются.
- **S9 · AUTH-001, 002:** Given старая БД с guest и позицией; When миграции и новые password-регистрации; Then guest identity/позиция не меняются, credential не появляется у guest, ошибочная запись credential откатывает account/player, отзыв сохраняется после перезапуска.

## Ограничения и вне scope

Восстановление/смена пароля, преобразование guest в password account, внешние провайдеры, remember-me и долговременные cookie отсутствуют. HTTP без TLS в LAN остаётся принятым риском демо: KDF не защищает пароль от перехвата сети. Лимиты за общим NAT разделяются; распределённого rate-limit и сохранения счётчиков между перезапусками нет. Аппаратная LAN-проверка не подменяется localhost.
