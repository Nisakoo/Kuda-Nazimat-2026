# AUTH — Вход (mock по имени)

## Цель

Дать браузеру серверную сессию `{token, expiresAt}` минимальным способом, без паролей. Способ передачи токена в handshake и Bearer для `/world` сохраняется в игровом PROTO v3. Mock-вход — сознательное упрощение офлайн-демо. Настоящий вход по паролю подключается позже за тем же `AuthService`, без изменения realtime, world и клиента.

## Требования

- **AUTH-001:** Mock-вход по имени. `name` — 1–32 символа после trim, без управляющих символов. Ключ — имя в нижнем регистре: одно имя всегда даёт одного и того же игрока (при первом входе сервер создаёт аккаунт и игрока, playerId выдаёт сервер). Личность после входа устанавливается только по токену: playerId и имя из payload/handshake не являются доказательством. Подтверждения личности нет — любой может войти под любым именем; это принятый риск офлайн-демо, записанный в README.
- **AUTH-002:** Сессия — случайный токен из 32 байт `crypto.randomBytes`, base64url (43 символа). Срок жизни — `sessionTtlMs` (12 ч), без продления и без серверного logout. Токен хранится только как SHA-256-хеш вместе с accountId, createdAt и expiresAt. Повторный вход под тем же именем создаёт новую сессию для того же игрока. Клиентский «Выйти» лишь забывает токен локально; старая сессия истекает сама.
- **AUTH-003:** Socket.IO-handshake `/game` проверяет `auth.version === 3` (иначе `VERSION`) и токен: он должен существовать и не истечь (иначе `UNAUTHORIZED`). Проверка проходит до допуска к игровым событиям. В момент `expiresAt` сервер отправляет соединению `error {requestId: "server", code: "UNAUTHORIZED"}` и закрывает его. `/world/*` требует `Authorization: Bearer` действующей сессии, иначе 401. Без токена соединение не получает данных игроков и мира.
- **AUTH-004:** Токены и их хеши не пишутся в логи и ответы, кроме ответа входа. Секретов в репозитории нет.
- **AUTH-005:** У аккаунта одно управляющее игровое соединение. Новое соединение того же аккаунта, прошедшее handshake, **атомарно перехватывает управление**:
  1. прежнее соединение получает `error {requestId: "server", code: "UNAUTHORIZED", message: "Игра открыта в другом окне."}` и закрывается; клиент v3 на этот код не делает retry;
  2. его ожидающий NPC-запрос отменяется (NPC-004);
  3. сущность и playerId сохраняются, новое соединение после join продолжает с текущей позиции.

  Сообщения прежнего соединения после перехвата не обрабатываются. Перехват не занимает второй слот (SERVER-006). Тот же механизм обслуживает переподключение, когда старый сокет ещё не признан мёртвым.
- **AUTH-006:** HTTP API:

  | Метод и путь | Тело | Успех | Ошибки |
  |---|---|---|---|
  | `POST /api/auth/guest` | `{name}` (JSON, ≤1 KiB) | 200 `{token, expiresAt}` | 400 `{error: {code: "INVALID", message}}` |

  Ответ содержит **ровно** `{token, expiresAt}`: клиент v3 передаёт его в `GameApp.provideServerSession()` без преобразования. Неизвестные поля тела — 400. Отображаемое имя персонажа и имя в чате — `name` в том виде, в каком он был при первом входе.

## Сценарии

- **S1 · AUTH-001, 003, 006:** Given вход под именем «Аня»; When тестовый клиент подключается с полученным токеном, без токена и с битым токеном; Then только первый проходит handshake и после join получает playerId «Ани», остальные получают `connect_error UNAUTHORIZED`; `/world/` без токена — 401.
- **S2 · AUTH-001–002:** Given «Аня» уже входила и сервер перезапущен; When выполнен вход под именем «аня»; Then возвращается тот же playerId, а токен новый.
- **S3 · AUTH-003:** Given сессия с коротким TTL; When наступает `expiresAt`; Then соединение получает `error UNAUTHORIZED` и закрыто, повторный handshake с тем же токеном отклонён.
- **S4 · AUTH-005:** Given игрок в мире с ожидающим NPC-вопросом; When тот же аккаунт подключается второй вкладкой; Then первая вкладка получает `error UNAUTHORIZED` и отключена, её NPC-запрос отменён, во второй вкладке тот же playerId и позиция; сообщения первого сокета после перехвата не меняют мир.
- **S5 · AUTH-004, 006:** Given пустое имя, имя из 33 символов и лишнее поле; When выполняется вход; Then 400 и аккаунт не создан. Тело успешного ответа содержит только `token` и `expiresAt`, в логах токена нет.

## Ограничения и вне scope

- Пароли, регистрация, logout с отзывом, rate limit входа, внешние провайдеры — следующий этап. Тогда добавится `POST /api/auth/login` с тем же форматом ответа.
- Клиентская интеграция по NET-007: при старте в режиме `online` запросить имя, вызвать `POST <serverUrl>/api/auth/guest` и передать ответ в `GameApp.provideServerSession()`.
- HTTP без TLS в LAN — принятый риск офлайн-демо.
