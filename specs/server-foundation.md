# SERVER — Основа отдельного сервера

## Цель

Обеспечить единственный локальный сервер для браузерных клиентов.

## Требования

- **SERVER-001:** Сервер разрабатывается отдельным проектом, не внутри client/. Он размещает Socket.IO, SQLite, авторизацию, данные мира, состояние игроков и локальный ИИ на одном ноутбуке. Игровая часть — модульное приложение, не набор микросервисов; тяжёлый inference работает отдельно от игрового цикла, операции SQLite не блокируют его.
- **SERVER-002:** Модули bootstrap/config, auth, realtime, world, players, persistence и ai имеют явные интерфейсы; транспорт не содержит игровые правила, а хранилище не управляет сокетами.
- **SERVER-003:** Сервер обслуживает локальный HTTP для готового клиента и ресурсов либо документирует локальный способ их раздачи. Публично доступны оболочка приложения и форма входа; данные реального мира выдаются с проверками AUTH и SERVER-WORLD. Браузерный клиент не требует установки ПО.
- **SERVER-004:** Адрес прослушивания, порт, пути БД/мира/моделей и лимиты задаются конфигурацией. Для LAN доступен сетевой интерфейс, для автономного режима — loopback; отсутствуют внешние runtime-зависимости. AI-конфигурация задаёт backend mlx/ollama, локальный snapshot/digest и квалифицированный профиль LLM с maxConcurrentGenerations=1 либо 2, ограничением threads/буферов и общим бюджетом 4 GB; inference endpoint не публикуется в LAN, запуск двух моделей/backend одновременно запрещён. MLX-worker может требовать локальный Python независимо от языка игрового сервера.
- **SERVER-005:** При запуске проверяются конфигурация и обязательные ресурсы; ошибки понятны. Корректная остановка прекращает приём команд, завершает сохранение, закрывает БД и соединения. Сбой/перезапуск AI runtime переводит затронутые запросы в контролируемые terminal-статусы по LLM-011, не останавливает игровой мир и не запускает второй экземпляр модели поверх зависшего.
- **SERVER-006:** MVP рассчитан на максимум 4 одновременно активных playerId; целевая приёмка включает всех четверых. Новый пятый игрок получает server_full без создания второй сущности/активной сессии мира. Дополнительная вкладка того же пользователя не создаёт playerId и не расширяет его игровые/AI-квоты; выбор единственного управляющего соединения описывается AUTH. Освобождение/резервирование места при disconnect/reconnect атомарно и согласовано с REALTIME; число активных игроков не подменяется числом TCP-соединений.

## Сценарии

- **S1:** SERVER-001–004: Given подготовленный ноутбук; When сервер запущен; Then 4 браузерных игрока LAN открывают клиент, серверные модули находятся в одном приложении с локально управляемым inference; долгие ответы не блокируют игровой шаг.
- **S2:** SERVER-004–005: Given недоступный путь БД/мира или остановка; When выполняется запуск/завершение; Then ошибка диагностируется либо состояние корректно сохраняется.

- **S3:** SERVER-005–006: Given 4 активных игрока и генерация NPC; When пятый игрок/дублирующая вкладка пытаются войти, а AI зависает или перезапускается; Then нет пятой сущности/добавочных квот, результат входа понятен, затронутые запросы получают статусы, остальные игровые функции продолжаются.

## Ограничения и вне scope

Без микросервисов, облачной БД и внешнего ИИ. Клиентский репозиторий содержит серверные спеки, но не создаёт серверный код.

## Открытые вопросы

Выбрать runtime/язык сервера и версии зависимостей при создании отдельного проекта. Socket.IO и SQLite заданы пользователем.
