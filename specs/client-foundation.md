# CLIENT — Базовая структура клиента

## Цель

Подготовить минимальную основу браузерного клиента учебного многопользовательского 3D-мира: запуск приложения, сцена three.js, UI и границы подключения к серверу. Структура должна позволять добавлять игру по отдельным спекам без смешивания рендеринга, сетевого обмена и интерфейса.

Один Vite-проект в `client/`: TypeScript strict, Svelte 5 + CSS, Three.js, Socket.IO Client, Vitest. Основа определяет запуск, техническую сцену и конфигурацию; игровые модули добавляются по отдельным спекам.

## Требования

- **CLIENT-001:** Клиент находится в отдельном каталоге `client/`; исходники, статические ресурсы и конфигурация сборки принадлежат клиенту. Серверный код, БД, секреты и ИИ-модели не включаются в клиентскую поставку.
- **CLIENT-002:** Клиент запускается в браузере без установки ПО на клиентский ноутбук. Готовая сборка и её ресурсы раздаются локальным сервером; во время работы не требуются интернет, CDN, внешние шрифты, аналитика или облачные API.
- **CLIENT-003:** У клиента есть явная точка запуска и освобождения ресурсов: повторное создание/завершение приложения не оставляет обработчики, циклы рендеринга или ресурсы three.js от предыдущего экземпляра.
- **CLIENT-004:** Базовая сцена three.js содержит камеру и простой видимый объект, корректно меняет размер вместе с областью просмотра и показывает понятное сообщение, если 3D-рендеринг недоступен. Это техническая сцена, а не полный игровой мир.
- **CLIENT-005:** Ответственности разделены: `app` собирает приложение и управляет жизненным циклом; `core` — за игровые данные и системы; `session` — за LocalSession/OnlineSession; `render` — за Three.js; `map` — за чанки и ресурсы; `multiplayer` — за транспорт; `input` — за команды ввода; `ui` — за Svelte. UI и сцена не создают соединения напрямую. Границы описаны в architecture.md; циклические импорты запрещены. Модули появляются по мере реализации своих этапов; foundation не требует пустых реализаций всех перечисленных модулей.
- **CLIENT-006:** Адрес сервера не привязан к IP разработчика или к `localhost`. По умолчанию клиент использует адрес узла, с которого загружен, чтобы одна сборка могла открываться на серверном ноутбуке и с другого ноутбука в LAN. Публичный serverUrl задаётся конфигурацией отдельно от игровых данных и секретов.
- **CLIENT-007:** Сетевой модуль имеет явные состояния «не авторизован», «подключается», «подключён» и «соединение потеряно». Попытка открыть игровой двунаправленный канал до успешной авторизации не выполняется. UI отображает состояние соединения; серверная проверка доступа обязательна в отдельной реализации сервера.
- **CLIENT-008:** Основа не загружает полный игровой мир в стартовый пакет или кеш и не содержит скрытой предварительной загрузки мира. Загрузка по положению игрока и лимит 10% определены в [MAP](client-world-streaming.md); приёмка основы не доказывает соблюдение лимита для ещё не реализованного мира.
- **CLIENT-009:** После реализации README содержит реальные команды подготовки, запуска, сборки и выбранных проверок, а также расположение клиентских модулей. Команды проверены на фактическом проекте; неподтверждённые шаги явно отмечены.
- **CLIENT-010:** Корневой Makefile предоставляет `make client` для запуска и `make client-test` для тестов. До реализации клиента ненастроенные команды завершаются с ошибкой и объяснением; после настройки выполняют соответствующие команды и не скрывают их ошибки. `make client-test` входит в приёмку изменений клиентского кода в AGENTS.md.

- **CLIENT-011:** GameApp — единственное место сборки зависимостей без DI-контейнера. Создаются только реально используемые модули и минимальные порты; пустые классы/каталоги ради структуры не нужны.
- **CLIENT-012:** Конфигурация содержит session (local/online), serverUrl, mapId, chunkRadius и debug. Рендерер всегда Three.js, поля renderer и переключения движков нет. Foundation определяет форму конфигурации; local/online становятся рабочими по мере реализации соответствующих сессий. До этого недоступный режим явно обозначен, а не имитирует готовую функциональность. Изменение режима сессии не требует переписывания модулей.
- **CLIENT-013:** Используются TypeScript strict, Svelte 5, Vite и Vitest. SvelteKit, монорепозиторий, полноценный ECS и необоснованный any не добавляются.

## Сценарии

- **S1 · CLIENT-001, 002, 004:** Given готовая сборка на локальном сервере и отключённый интернет; When пользователь открывает страницу; Then видит интерфейс и 3D-объект, все необходимые ресурсы загружаются локально.
- **S2 · CLIENT-003, 004:** Given запущенный клиент; When меняется размер области просмотра и приложение повторно создаётся после завершения; Then пропорции сцены корректны, работает один цикл рендеринга, ресурсы предыдущего экземпляра освобождены.
- **S3 · CLIENT-004:** Given браузер без доступного 3D-контекста; When открывается клиент; Then отображается понятная ошибка вместо пустого экрана.
- **S4 · CLIENT-006:** Given одна и та же сборка на локальном сервере; When страница открывается с другого ноутбука по LAN, а затем на серверном ноутбуке с выключенным Wi-Fi; Then адрес сетевого модуля указывает на нужный сервер без пересборки клиента.
- **S5 · CLIENT-005, 007:** Given управляемый тестовый транспорт; When до авторизации запрашивается подключение, затем подтверждается авторизация, затем теряется соединение; Then первая попытка не открывает канал, последующие состояния отображаются в UI, а сцена не управляет транспортом.
- **S6 · CLIENT-001, 008:** Given клиентская сборка и наблюдение за её запросами; When открывается стартовая сцена; Then поставка не содержит серверные файлы или полный игровой мир, запросов полной загрузки мира нет.
- **S7 · CLIENT-009:** Given чистая среда разработки с указанными prerequisites; When выполняются команды README; Then клиент запускается и собирается, а результаты выбранных проверок зафиксированы в задаче.
- **S8 · CLIENT-010:** Given Makefile; When вызывается ненастроенная команда запуска или тестов; Then возвращается ненулевой код и объяснение. When команда настроена; Then она выполняется, а её ошибка приводит к ошибке Make.

- **S9 · CLIENT-011–013:** Given подготовленный проект; When собирается GameApp с локальной конфигурацией; Then реализованные модули связаны через порты, UI поверх canvas, используется только Three.js, strict-проверки проходят. Полное переключение local/online проверяется на этапе OnlineSession.

## Ограничения и вне scope

- Технологии заданы новым ТЗ; Three.js — единственный движок. Svelte 5 и остальные технологии сохранены.
- Подготовка зависимостей и сборки может проходить до демонстрации; готовая игра работает без интернета.
- Заглушка транспорта допустима для проверки основы, но не считается рабочим мультиплеером или доказательством безопасности сервера.
- Вне этой спеки: сервер и реальная авторизация, синхронизация игроков, сохранения, потоковая загрузка мира и полный контроль лимита кеша, диалоги и память ИИ, игровой контент, полноценный UX и измеримые игровые бюджеты производительности.
- VR-шлем и WebXR не добавляются автоматически: исходная цель здесь — 3D-мир в обычном браузере; необходимость иммерсивного режима обсуждается отдельно.
