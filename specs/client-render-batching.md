# RBATCH — Объединение геометрии и экземпляров

## Цель

Уменьшить измеренные draw calls и обходы сцены. Начинать после RPERF; уже существующее объединение геометрии в генераторе и WindInstances учитываются как baseline.

## Требования

- **RBATCH-001:** Перед изменением составляется инвентаризация реально отрисованных групп: asset/chunk, материал, геометрия, анимация, shadow flags, visibility и число команд. По RPERF выбираются наиболее дорогие совместимые группы; наличие многих mesh nodes в GLB само по себе не доказывает, что все они видны или допускают merging.
- **RBATCH-002:** Статическое объединение выполняется внутри ограниченной пространственной группы, без пересечения lifecycle чанков. Различия только цвета по возможности сохраняются vertex colors. Поворотные/анимируемые узлы, кости, ветер, интерактивные части, управляемые символы и отличающиеся material/shadow/layer состояния сохраняют независимое поведение. Семантические имена, нужные коду, не исчезают без эквивалентного отображения.
- **RBATCH-003:** Для повторов одной geometry/material оценивается InstancedMesh; для разных геометрий одного совместимого материала — BatchedMesh либо подготовленное объединение. Выбор подтверждается реальным браузером, включая fallback без ускоряющих расширений. Группы имеют консервативные компактные bounds; один экземпляр у края не делает весь город единой неотсекаемой группой.
- **RBATCH-004:** Камера, прицеливание и следы попаданий пересекают эквивалентные поверхности после объединения. Генератор сохраняет исходные collision/ceiling данные; общая геометрия не освобождается раньше последнего владельца. Не дублировать всю сцену для raycast без обоснования и учёта памяти. Сравнить ускоренный и исходный raycast на одинаковых лучах, включая скрытые исходные wind-поверхности.
- **RBATCH-005:** Если следы выстрелов дают измеримую нагрузку, они объединяются по совместимым владельцам/чанкам с прежними ограничениями числа и времени жизни. След на движущемся объекте следует его transform; выгрузка владельца удаляет след, переполнение переиспользует ограниченное хранилище. Стрельба четырёх игроков не накапливает отдельные неосвобождаемые материалы/геометрии.
- **RBATCH-006:** Дополнительные буферы учитываются по ROPT-001, отменённая загрузка не оставляет batch/instance ссылок. Изменения генерации воспроизводимы: повторный запуск не меняет ассеты без изменения входных данных. Приёмка включает draw calls и CPU/GPU по RPERF, одинаковые контрольные кадры, unload/reload и пять входов. Не снижать детализацию или дальность для доказательства эффекта batching.

## Сценарии

- **S1 · RBATCH-001–003/006:** Given повторяющийся декор и прежний ракурс; When сравниваются реализации; Then видно уменьшение целевой стоимости, сохраняются число видимых предметов, материалы и тени.
- **S2 · RBATCH-002/004:** Given ветер, символы здания и движение камеры вплотную к стене; When работают анимации и raycast; Then pivots, видимость, расстояния пересечений и физические данные сохраняются.
- **S3 · RBATCH-004–006:** Given общий ассет в двух чанках и следы на движущихся мишенях; When один чанк выгружается, другой остаётся, затем сессия завершается; Then нет исчезновения живых ресурсов и утечек.
- **S4 · RBATCH-003/006:** Given экземпляры на границе обзора и браузер без multi-draw ускорения; When камера вращается; Then нет выпадения экземпляров, fallback проверен и замерен отдельно.

## Ограничения и вне scope

Не объединять скелетных персонажей в статический меш. Не менять серверную стрельбу, состав рынка или расстановку моделей. Если после инвентаризации подходящих групп нет, результат этапа — отчёт об отказе с доказательствами, а не фиктивная реализация batching.
