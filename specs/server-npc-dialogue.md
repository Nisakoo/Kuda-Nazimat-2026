# NPC — Диалог с NPC через порт ответчика (v1)

## Цель

Клиент v1 отправляет `npc-question` и ждёт один целый `npc-answer` не дольше 10 с. Сервер проверяет право задать вопрос, ставит его в ограниченную очередь и получает текст ответа через порт `NpcResponder`. В MVP подключена детерминированная заглушка. Адаптер локальной модели реализуется отдельно (владелец — разработчик LLM-части) и подключается конфигурацией без изменения realtime/game.

## Требования

- **NPC-001 (допуск):** `npc-question {targetId, text}` принимается при выполнении всех условий:
  1. отправитель — управляющее соединение игрока в мире;
  2. цель — NPC из SERVER-WORLD-008 на карте игрока;
  3. 3D-расстояние ≤ `interactionRadius + 0.5`;
  4. текст после trim — 1–240 символов;
  5. у игрока нет другого незавершённого вопроса;
  6. незавершённых вопросов на сервере меньше `npc.maxUnfinished` (4).

  Ошибки:

  | Нарушено | Ответ |
  |---|---|
  | условие 2 | `error FORBIDDEN` «Собеседник недоступен» |
  | условие 3 | `error FORBIDDEN` «Подойдите ближе» |
  | условие 5 | `error RATE_LIMIT` «Дождитесь ответа» |
  | условие 6 | `error UNAVAILABLE` «Собеседники заняты» |

  Квота резервируется атомарно при допуске (в одном потоке событий) и освобождается только после завершения вызова NpcResponder (NPC-004).
- **NPC-002 (планировщик):** FIFO-очередь. Одновременно выполняется не более `npc.maxConcurrent` вызовов NpcResponder (по умолчанию 1, допустимо 2 по LLM-010). Каждый запрос имеет общий дедлайн `npc.timeoutMs` (по умолчанию 8000 мс, максимум 9000 мс — меньше таймаута клиента 10 с) от момента приёма; ожидание в очереди входит в дедлайн. По истечении дедлайна вызов отменяется через `AbortSignal`, игрок получает `error UNAVAILABLE` «Собеседник не успел ответить». Планировщик и NpcDialogueService не блокируют игровой шаг.
- **NPC-003 (ответ):** Текст ответчика нормализуется: trim, `\r\n` заменяется на `\n`, управляющие символы кроме `\n` удаляются, длина обрезается до 4000 символов. Пустой результат считается ошибкой. Успешный ответ записывается в историю (STORE-011), затем отправляется владельцу как `npc-answer {requestId, targetId, text}`. Ошибка ответчика или записи даёт `error UNAVAILABLE` с безопасным текстом, без деталей исключения. Ответ доставляется только тому соединению, которое задало вопрос, и только если оно ещё управляющее.
- **NPC-004 (отмена):** Разрыв управляющего соединения, перехват управления (AUTH-005), истечение сессии и штатная остановка отменяют queued- и running-запросы игрока через `AbortSignal`. Отменённый запрос не пишет историю и не доставляется. Квота и слот исполнения освобождаются, когда промис ответчика завершился (resolve или reject). Если ответчик не завершился через 2 с после abort, слот считается зависшим: он остаётся занятым, а в лог пишется ошибка. Это нужно, чтобы не превысить `maxConcurrent` поверх незавершённого вычисления (LLM-011).
- **NPC-005 (порт):** `NpcResponder` объявлен в `server/src/npc/` — единственный контракт, который реализует адаптер модели:

  ```ts
  export interface NpcResponder {
    /** Готовность и прогрев; вызывается при старте до открытия порта. */
    start(): Promise<void>;
    /** Один ответ. Обязан завершиться (resolve/reject) вскоре после signal.abort. */
    answer(request: NpcAnswerRequest, signal: AbortSignal): Promise<{ text: string }>;
    /** Освобождение ресурсов при остановке сервера. */
    stop(): Promise<void>;
  }
  export interface NpcAnswerRequest {
    readonly requestKey: string;      // уникален на сервере: `${connectionId}:${requestId}`
    readonly playerId: string;
    readonly playerName: string;
    readonly npc: { readonly id: string; readonly name: string; readonly topic: string; readonly persona: string; readonly greeting: string };
    readonly question: string;        // 1–240 символов, уже проверен
    readonly history: readonly { readonly question: string; readonly answer: string }[]; // ≤6, старые первыми
    readonly locale: 'ru';            // v1; языки игрока — PROTO v2
    readonly deadlineAt: number;      // Unix ms
  }
  ```

  Адаптер выбирается `npc.adapter` из реестра `name → (options, deps) => NpcResponder` в `server/src/npc/adapters/`. Опции `npc.options` проверяет сам адаптер при создании. Адаптер получает только переданные данные. Он не обращается к БД, игровому миру и внешней сети и не меняет игровое состояние; тяжёлое вычисление выполняет вне игрового потока (отдельный процесс по LLM-005). Ошибка `start()` при выбранном реальном адаптере не мешает запуску мира: NPC-запросы получают `error UNAVAILABLE`, `/api/health` сообщает `npc: "unavailable"`.
- **NPC-006 (заглушка):** Адаптер `scripted` детерминированно отвечает по профилю NPC без модели и показывает путь памяти по SERVER-DEMO-006:
  - на первый вопрос — `greeting` и ответ по теме в манере `persona`;
  - на последующие — ссылка на предыдущий вопрос из `history` и один из нескольких заготовленных ответов по теме, выбранный по числу записей истории; повтор вопроса получает другую формулировку.

  Опции: `delayMs` (по умолчанию 300) — искусственная задержка для проверки очереди и таймаутов; `failEvery` (по умолчанию 0) — каждый N-й вызов завершается ошибкой, для тестов. Abort соблюдается. Заглушка не подтверждает приёмку AI/LLM и не выдаётся за адаптивный ИИ.
- **NPC-007 (контрактный тест):** В `server/` есть общий набор тестов `NpcResponder`, который обязан пройти любой адаптер:
  - ответ — непустой текст;
  - abort до и во время вызова завершает промис за ≤2 с;
  - соблюдается `deadlineAt`;
  - нет обращений к сети вне loopback;
  - повторный `start`/`stop` безопасен.

  Заглушка проходит его в MVP. Адаптер модели подключается вместе со своим прогоном этих тестов.

## Сценарии

- **S1 · NPC-001, 003, 006:** Given игрок рядом с «Леей»; When он отправляет вопрос; Then получает `npc-answer` с тем же requestId и targetId, запись в истории создана до отправки. When он отходит на 5 м и спрашивает; Then получает `error FORBIDDEN`.
- **S2 · NPC-001–002:** Given `maxConcurrent: 1`, заглушка с `delayMs: 3000` и 4 игрока; When все одновременно задают вопрос, а первый сразу задаёт второй; Then первому второй вопрос отклонён `RATE_LIMIT`, ответы приходят по FIFO, 4-й получает `UNAVAILABLE` по дедлайну 8 с, шаг мира в это время не задерживается.
- **S3 · NPC-004:** Given running-запрос; When игрок закрывает вкладку или перехватывает управление второй вкладкой; Then вызов получает abort, ответ не записан и не доставлен ни одной вкладке, слот освобождён после завершения промиса.
- **S4 · NPC-003, 005:** Given ответчик вернул 5000 символов с управляющими символами либо бросил исключение; When запрос завершается; Then клиент получает текст ≤4000 символов без управляющих символов либо `error UNAVAILABLE` без деталей исключения. Given `start()` реального адаптера упал; Then сервер запущен, движение и чат работают, NPC отвечают `UNAVAILABLE`.
- **S5 · NPC-007:** Given заглушка; When запущен контрактный набор; Then все проверки проходят.

## Ограничения и вне scope

- Потоковые ответы, отмена с клиента, preferences, языки, память и ledger — PROTO-007 и STORE-006–010, этап v2.
- Grounding, PromptBuilder, KnowledgeSource и выбор модели — [AI](server-ai.md) и [LLM](server-llm-runtime.md). Это внутренности адаптера или следующего этапа, а не NpcDialogueService v1.

## Открытые вопросы

- Реальная LLM в лимит v1 укладывается только для одиночных вопросов (LLM-014: p95 стандартного ответа ≤8 с на свободном сервисе). При одновременных вопросах четырёх игроков часть получит `UNAVAILABLE` по дедлайну. Полноценное решение — PROTO v2 с потоком и долгим ожиданием, и оно требует изменения клиента.
