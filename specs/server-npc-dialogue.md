# NPC — Диалог с NPC и модельные порты

## Цель

Клиент отправляет `npc-question` и ждёт один целый `npc-answer` до effective серверного deadline +2 с; остальные pending-запросы, включая чат, ограничены 10 с. Сервер дополнительно поддерживает opt-in поток PROTO-007 (`stream: true`), но клиентский TASK-041 ещё не реализован. Сервер проверяет право задать вопрос, ставит его в ограниченную очередь и получает текст ответа через порт `NpcResponder`. В реестре есть детерминированная `scripted` и явно выбираемые `ollama`/`mlx`. Реальные workers выдают только приватный operational progress и один финал, не игровые partial; регистрация адаптера не квалифицирует модель.

## Требования

- **NPC-001 (допуск):** `npc-question {targetId, text}` принимается при выполнении всех условий:
  1. отправитель — управляющее соединение игрока в мире;
  2. цель — NPC из SERVER-WORLD-008 на карте игрока;
  3. 3D-расстояние ≤ `interactionRadius + 0.5`;
  4. текст после trim — 1–240 символов;
  5. у игрока нет другого незавершённого generation-запроса в общей очереди NPC/BABEL;
  6. незавершённых generation-запросов в общей очереди меньше `npc.maxUnfinished` (4).

  Ошибки:

  | Нарушено | Ответ |
  |---|---|
  | условие 2 | `error FORBIDDEN` «Собеседник недоступен» |
  | условие 3 | `error FORBIDDEN` «Подойдите ближе» |
  | условие 5 | `error RATE_LIMIT` «Дождитесь ответа» |
  | условие 6 | `error UNAVAILABLE` «Собеседники заняты» |

  Квота резервируется атомарно при допуске (в одном потоке событий) и освобождается только после завершения вызова NpcResponder (NPC-004).
- **NPC-002 (планировщик):** Единая `GenerationQueue` обслуживает NPC и языковые операции BABEL (NPC-009), без второй независимой очереди. Порядок FIFO. Одновременно выполняется не более `npc.maxConcurrent` вызовов NpcResponder (по умолчанию 1, допустимо 2 по LLM-010). Каждый запрос имеет общий дедлайн `npc.timeoutMs` (default 30000 мс, допустимо 1–300000 мс; Make `NPC_TIMEOUT` задаёт целые секунды 1–300 на один запуск). Для opt-in потока используется `npc.streamTimeoutMs` (default 30000 мс, config 1–300000 мс). Явный Make/env/CLI override задаёт оба effective deadline одним значением; без него отдельные config-значения сохраняются. Текущий клиент получает только non-stream effective `npcTimeoutMs` от фактического сервера через `/api/game-config` при подключении/переподключении и ждёт NPC этот срок плюс 2000 мс; остальные pending — 10 с. Настройка, полученная после смены/закрытия соединения, игнорируется. Без достоверной настройки real-online NPC запрос не отправляется с выдуманным коротким сроком; движение/чат могут работать. Отсчёт начинается в момент приёма; ожидание в очереди входит в дедлайн. По истечении дедлайна вызов отменяется через `AbortSignal`, игрок получает `error UNAVAILABLE` «Собеседник не успел ответить». Планировщик и NpcDialogueService не блокируют игровой шаг.
- **NPC-003 (ответ):** Текст ответчика нормализуется: trim, `\r\n` заменяется на `\n`, управляющие символы кроме `\n` удаляются, длина обрезается до 4000 символов. Пустой результат считается ошибкой. Успешный ответ записывается в историю (STORE-011), затем отправляется владельцу как `npc-answer {requestId, targetId, text}`. Ошибка ответчика или записи даёт `error UNAVAILABLE` с безопасным текстом, без деталей исключения. Ответ доставляется только тому соединению, которое задало вопрос, и только если оно ещё управляющее.
- **NPC-004 (отмена):** Разрыв управляющего соединения, перехват управления (AUTH-005), истечение сессии, штатная остановка и `npc-cancel` своего вопроса (NPC-008) отменяют queued- и running-запросы игрока через `AbortSignal`. Отменённый запрос не пишет историю и не доставляется. Квота и слот исполнения освобождаются, когда промис ответчика завершился (resolve или reject). Если ответчик не завершился через 2 с после abort, слот считается зависшим: он остаётся занятым, а в лог пишется ошибка. Это нужно, чтобы не превысить `maxConcurrent` поверх незавершённого вычисления (LLM-011).
- **NPC-005 (порт):** `NpcResponder` объявлен в `server/src/npc/` — контракт ответчика обычного NPC; отдельная граница LanguagePort описана в NPC-009:

  ```ts
  export interface NpcResponder {
    /** Готовность и прогрев; вызывается при старте до открытия порта. */
    start(): Promise<void>;
    /** Один ответ. Обязан завершиться (resolve/reject) вскоре после signal.abort.
     *  onPartial (необязателен для адаптера) получает весь текст на данный момент, не дельту;
     *  не вызывается после завершения промиса или abort. */
    answer(request: NpcAnswerRequest, signal: AbortSignal, onPartial?: (text: string) => void): Promise<{ text: string }>;
    /** Освобождение ресурсов при остановке сервера. */
    stop(): Promise<void>;
    /** Текущая доступность backend без IO и безопасный фиксированный код отказа. */
    status?(): 'ready' | 'unavailable';
    lastFailure?(): string | undefined;
    /** Приватная bounded числовая диагностика, не игровой partial. */
    diagnostics?(): { stage: 'preparing' | 'prefill' | 'decoding' | 'complete'; elapsedMs: number; promptTokens?: number; firstTokenMs?: number; outputChunks?: number } | undefined;
  }
  export interface NpcAnswerRequest {
    readonly requestKey: string;      // уникален на сервере: `${connectionId}:${requestId}`
    readonly playerId: string;
    readonly playerName: string;
    readonly npc: { readonly id: string; readonly name: string; readonly topic: string; readonly persona: string; readonly greeting: string };
    readonly question: string;        // 1–240 символов, уже проверен
    readonly history: readonly { readonly question: string; readonly answer: string }[]; // ≤6, старые первыми
    readonly locale: 'ru';            // обычный NPC; preferences — план AI
    readonly deadlineAt: number;      // Unix ms
  }
  ```

  Адаптер выбирается `npc.adapter` из реестра `name → (options, deps) => NpcResponder` в `server/src/npc/adapters/`. Опции `npc.options` проверяет сам адаптер при создании. Адаптер получает только переданные данные. Он не обращается к БД, игровому миру и внешней сети и не меняет игровое состояние; тяжёлое вычисление выполняет вне игрового потока (отдельный процесс по LLM-005). Ошибка `start()` при выбранном реальном адаптере не мешает запуску мира: NPC-запросы получают `error UNAVAILABLE`, `/api/health` сообщает `npc: "unavailable"`. Для реального ответчика с `status()` health учитывает последующие отказы. После failed/aborted вызова сервис отклоняет оставшиеся queued NPC-запросы, не чужие языковые операции BABEL. После подтверждённого освобождения общей очереди он может однократно запустить восстановление через 2 с, без повторения вопроса. Если восстановление не удалось, NPC остаётся unavailable; автоматические повторные попытки в этом периоде недоступности не выполняются. При ещё занятом/зависшем слоте восстановление запрещено. Остановка сервера отменяет отложенное восстановление. Статический scripted не обязан реализовывать `status()`.
- **NPC-006 (заглушка):** Адаптер `scripted` детерминированно отвечает по профилю NPC без модели и показывает путь памяти:
  - на первый вопрос — `greeting` и ответ по теме в манере `persona`;
  - на последующие — ссылка на предыдущий вопрос из `history` и один из нескольких заготовленных ответов по теме, выбранный по числу записей истории; повтор вопроса получает другую формулировку.

  При переданном `onPartial` заглушка выдаёт три растущих префикса ответа по словам на 1/4, 2/4 и 3/4 задержки — этого достаточно, чтобы клиент отладил поток без модели. Опции: `delayMs` (по умолчанию 300) — искусственная задержка для проверки очереди и таймаутов; `failEvery` (по умолчанию 0) — каждый N-й вызов завершается ошибкой, для тестов. Abort соблюдается. Заглушка не подтверждает приёмку AI/LLM и не выдаётся за адаптивный ИИ.
- **NPC-007 (контрактный тест):** В `server/` есть общий набор тестов `NpcResponder`, который обязан пройти любой адаптер:
  - ответ — непустой текст;
  - abort до и во время вызова завершает промис за ≤2 с;
  - соблюдается `deadlineAt`;
  - нет обращений к сети вне loopback;
  - повторный `start`/`stop` безопасен;
  - `onPartial` не вызывается после завершения промиса и после abort;
  - набор различает запрещённую внешнюю сеть и разрешённый literal loopback; Node-перехват не наблюдает сеть subprocess и не заменяет OS/offline gate. Fixture-тест worker не является прогоном настоящей модели.

  Заглушка проходит его в MVP. Адаптер модели подключается вместе со своим прогоном этих тестов.
- **NPC-008 (поток и отмена):** при `npc-question` со `stream: true` NpcDialogueService передаёт ответчику `onPartial`. Снимки нормализуются как ответ (NPC-003); пустые и пришедшие после abort или дедлайна отбрасываются. Realtime ограничивает их частоту и порядок по PROTO-007 и отправляет только владельцу. Финал, история и ошибки — без изменений, NPC-003. `npc-cancel` отменяет конкретный вопрос (`connectionId` + `requestId`) этого соединения; чужой или завершённый вопрос не затрагивается. Квоты NPC-001 общие для потоковых и обычных вопросов.
- **NPC-009 (порт переводчика BABEL):** `LanguagePort` в `server/src/babylon/ports.ts` — вторая модельная граница: перевод сообщений группы и подсказок словаря (`translate`) и личные ответы NPC рынка на изучаемом языке (`answer`) по [BABEL](game-babylon.md). Как и NpcResponder, он имеет `start()`/`stop()`, выбирается `language.adapter` из реестра `server/src/babylon/adapters.ts` (по умолчанию `test` — фиксированные фразы, без модели) с опциями `language.options`, получает `AbortSignal` и вызывается через ту же очередь генераций. Неизвестный адаптер останавливает запуск понятной ошибкой. Ошибка `start()` не мешает запуску: остальная игра работает, языковые действия BABEL получают `UNAVAILABLE`; `stop()` вызывается при остановке сервера. Ответы BABEL не стримятся (PROTO-009); `queue.generate` использует общий `npc.timeoutMs`. Отказ NpcResponder не отключает отдельный явно выбранный test LanguagePort, который продолжает использовать ту же очередь. Реальный адаптер должен реализовать оба порта поверх одной загруженной модели; эта интеграция ещё не выполнена.

## Сценарии

- **S1 · NPC-001, 003, 006:** Given игрок рядом с «Леей»; When он отправляет вопрос; Then получает `npc-answer` с тем же requestId и targetId, запись в истории создана до отправки. When он отходит на 5 м и спрашивает; Then получает `error FORBIDDEN`.
- **S2 · NPC-001–002:** Given `maxConcurrent: 1`, явно уменьшенный `timeoutMs: 8000`, заглушка с `delayMs: 3000` и 4 игрока; When все одновременно задают вопрос, а первый сразу задаёт второй; Then первому второй вопрос отклонён `RATE_LIMIT`, ответы приходят по FIFO, 4-й получает `UNAVAILABLE` по дедлайну 8 с, шаг мира в это время не задерживается.
- **S3 · NPC-004:** Given running-запрос; When игрок закрывает вкладку или перехватывает управление второй вкладкой; Then вызов получает abort, ответ не записан и не доставлен ни одной вкладке, слот освобождён после завершения промиса.
- **S4 · NPC-003, 005:** Given ответчик вернул 5000 символов с управляющими символами либо бросил исключение; When запрос завершается; Then клиент получает текст ≤4000 символов без управляющих символов либо `error UNAVAILABLE` без деталей исключения. Given `start()` реального адаптера упал; Then сервер запущен, движение и чат работают, NPC отвечают `UNAVAILABLE`.
- **S5 · NPC-007:** Given заглушка; When запущен контрактный набор; Then все проверки проходят.
- **S6 · NPC-008:** Given заглушка с `delayMs: 600`; When игрок задаёт вопрос со `stream: true`; Then приходят растущие снимки и затем `npc-answer` с полным текстом, записанным в историю. When он отменяет следующий потоковый вопрос; Then `npc-cancelled`, ответа и записи нет, новый вопрос принимается.
- **S7 · NPC-009:** Given `LanguagePort`, чей `start()` падает; When игрок BABEL просит подсказку словаря и сохраняет слово; Then подсказка — `UNAVAILABLE`, сохранение работает, при остановке вызван `stop()`.

## Ограничения и вне scope

- Preferences, языки ответа v3-NPC, durable-результат после reconnect, память и ledger — STORE-006–010 и [AI](server-ai.md). Адаптеры MLX/Ollama для NPC-005 интегрированы частично по [LLM](server-llm-runtime.md); реальный MLX, Windows, OS isolation, RAM и скорость не квалифицированы. Для NPC-009 пока используется явно выбранный `test`, не автоматический fallback.
- Grounding, PromptBuilder, KnowledgeSource и выбор модели — [AI](server-ai.md) и [LLM](server-llm-runtime.md). Это внутренности адаптера или следующего этапа, а не доказанные возможности текущего NpcDialogueService.

## Открытые вопросы

- Обычный timeout настраивается оператором (default 30 с, hard max 300 с), но качество, скорость и обслуживание 4 игроков ещё не квалифицированы. FIFO расходует тот же срок; увеличение timeout не выполняет p95 ≤8 с и не реализует streaming.
- Серверная опция `npc.streamTimeoutMs` задаёт deadline потока (default 30000 мс, config 1–300000 мс). Явный Make/env/CLI override одинаково заменяет оба deadline; без override отдельные значения сохраняются. Полная клиентская поддержка потока — TASK-041.
- Полный AI-ledger/preferences/reset/result и qualified concurrency 2 не входят в реализованный PROTO-007. Историческое название «этап v2» относится к плану AI, не к текущему игровому wire v3.
