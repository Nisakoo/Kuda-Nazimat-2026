# STORE — SQLite и состояние игроков

## Цель

Сохранять игроков и память взаимодействий на сервере между запусками.

## Требования

### Этап v1 (MVP)

- **STORE-001:** SQLite (`node:sqlite`, файл `dbPath`) находится только на сервере. Схема v1:

  | Таблица | Поля | Ограничения |
  |---|---|---|
  | accounts | id, name, name_key, created_at | `name_key` = имя в нижнем регистре, UNIQUE (mock-вход AUTH-001) |
  | sessions | token_hash, account_id, created_at, expires_at | PK token_hash; FK accounts |
  | players | id, account_id, map_id, x, y, z, rotation_y, updated_at | PK id (формат ID PROTO, `p_` + 16 base36); account_id UNIQUE |
  | npc_dialogue | id, player_id, npc_id, question, answer, created_at | индекс (player_id, npc_id, created_at); FK players |
  | schema_migrations | version, applied_at | — |

  Аккаунт и его игрок создаются одной транзакцией при первом входе под новым именем. Позиция `NULL` означает «ещё не входил», при join используется spawn.
- **STORE-002:** Схема создаётся и меняется нумерованными SQL-миграциями из `server/src/persistence/migrations/`, применяемыми при старте в транзакции. Неизвестная (более новая) версия БД — ошибка запуска. Включены `foreign_keys = ON` и `journal_mode = WAL`. Связанные изменения фиксируются одной транзакцией; некорректные данные не создают частичную запись.
- **STORE-003:** Позиция и карта игрока сохраняются:
  - каждые `saveIntervalMs` (10 с), если изменились;
  - при удалении сущности из мира после grace;
  - при штатной остановке.

  Сохранения выполняются пакетно, одной транзакцией. После входа восстанавливается последняя сохранённая позиция. Окно потери при аварии — не более `saveIntervalMs` плюс длительность записи. Сессии, истёкшие больше суток назад, удаляются при старте и раз в час.
- **STORE-004:** SQLite открывается через `DatabaseSync` в основном процессе. Для MVP (≤4 игрока, запросы доли миллисекунды, пакетное сохранение раз в 10 с) отдельный worker не нужен. Игровой шаг не обращается к БД: сохранение позиций выполняется вне шага по таймеру. Все запросы параметризованы, SQL — только константы. Ошибка записи возвращается вызывающему, а не маскируется. Store-порты (`AccountStore`, `SessionStore`, `PlayerStore`, `DialogueStore`) реализованы поверх одного соединения. Сервисы тестируются с in-memory реализациями портов, адаптер — на временной БД. Если замер tick (REALTIME S7) покажет влияние записи, её выносят в worker; до замера — нет.
- **STORE-005:** README сервера описывает локальный backup/restore: для согласованной копии при работающем сервере используется `VACUUM INTO`, при остановленном — копирование файла с `-wal`/`-shm`. Восстановление проверяется на отдельной копии и не разрушает текущие данные.
- **STORE-011:** История NPC v1. Каждый завершённый ответ NPC записывается в `npc_dialogue` (вопрос и ответ) **до** отправки `npc-answer`. Ошибка записи даёт игроку `error UNAVAILABLE`, а не ответ (NPC-003). На пару player/NPC хранится не более 50 последних записей: старые удаляются той же транзакцией. История читается только для владельца, последние ≤6 записей передаются в NpcResponder как контекст. Тексты не дублируются в логах.

### Этап v2 (PROTO v2, AI)

Требования STORE-006–010 описывают ledger запросов и компактную память для потокового NPC-подконтракта PROTO-007. Они реализуются вместе с AI/LLM и в v1 не применяются. Таблица `npc_dialogue` v1 при переходе мигрирует в их схему.
- **STORE-006:** История диалогов хранится отдельно от компактной памяти. Запрос содержит server-owned playerId, npcId, dialogueId, requestId, текст/язык, время, fingerprint входа и состояние accepted/queued/running/completed/cancelled/failed/interrupted. Для completed сохраняются финальный текст, finish reason, source IDs/редакции, model/profile/template версии, token counts и terminal seq. Для failed сохраняется ограниченный code причины из PROTO-007, для cancelled — безопасная причина отмены; terminal-метаданные входят в идемпотентный ledger. Восстановленный interrupted не требует восстановления seq потерянных partial: terminal result авторитетнее временного текста независимо от lastSeq по PROTO-007. Ledger хранит тип операции (generation/preferences/reset): повтор ID с иным типом/содержимым — request_conflict, повтор завершённой настройки возвращает прежнее подтверждение без второго изменения revision. Временные накопительные partial-снимки не пишутся в БД по каждому обновлению; для них нет durable-архива или ACK-ledger. Сохраняется один полный финал и его seq, чтобы result/replay не создавал второй эффект; thinking не сохраняется. Уникальность `(playerId, requestId)` предотвращает повторную generation/запись; повтор с другим содержимым отклоняется.
- **STORE-007:** До durable-принятия запроса GenerationScheduler атомарно резервирует per-player и общую квоту (всего ≤4, включая останавливающееся вычисление), затем фиксирует запрос в БД. При ошибке допуска/записи резерв освобождается, inference не начинается; повтор requestId только для чтения не резервирует новую квоту. Финальный ответ, completed-статус и детерминированное изменение памяти фиксируются одной короткой транзакцией до успешного terminal-события. Транзакция не остаётся открытой во время inference. Сбой записи возвращает `persistence_error` как предварительный несохранённый статус (без persisted=true); частичный streamed-текст не считается сохранённым ответом. При восстановлении БД запрос без committed terminal становится interrupted; если commit всё же состоялся до сбоя подтверждения, читается его исходный terminal. Нельзя объявлять provisional-ошибку durable или повторять generation из-за неопределённого результата записи. При рестарте незавершённые состояния переводятся в interrupted, без автоматического воспроизведения generation. После commit и потери доставки повтор читает тот же сохранённый результат. Разрыв/переполнение транспортного буфера не требует rollback уже completed-запроса. Статус запроса в БД отделён от занятости вычислительного слота: cancelled/error не освобождает слот, пока вычисление физически не остановлено. Общий restart runtime сохраняет cancelled/failed для известных причин по LLM-011, а остальные запросы без committed terminal переводит в interrupted; он не затирает ранее committed результаты и не запускает их снова. Терминализация использует атомарный compare-and-set: только running → completed при актуальном reset epoch, действующем доступе, подтверждённом соблюдении deadline первого текста/конца inference и неистёкшем общем deadline LLM-010; проверка deadline и commit сериализуются с timeout, как cancel; результат, committed до deadline, не откатывается из-за поздней доставки; cancel может перевести accepted/queued/running → cancelled. Проверка доступа/эпохи и отзыв доступа сериализуются с финальным commit в одном per-player lifecycle-контуре/транзакционном порядке; одной проверки перед inference недостаточно. Если cancel/reset/отзыв доступа первым зафиксирован, completed не создаётся; если первым зафиксирован completed, последующая отмена не переписывает его в cancelled. Reset после completed очищает память и границу prompt-истории, но не делает исторический completed новым ответом. Logout после completed запрещает доставку до нового разрешённого входа; результат остаётся в БД. Уже показанный временный текст нельзя считать отозванным физически — UI лишь меняет его статус.
- **STORE-008:** Компактная память имеет ключ `(playerId, npcId)`, тип/значение, provenance (topic/source/game event или явная настройка), время и revision/reset epoch. Ограничения AI-010 проверяются при записи, не только при сборке prompt. Языковая настройка игрока хранится отдельно; предпочтение responseStyle задаётся только валидированной явной операцией PROTO-007 (standard/simple_no_formulas), без свободного извлечения LLM. Настройки фиксируются отдельной короткой транзакцией с идемпотентным подтверждением; завершение generation обновляет только допустимые обсуждавшиеся темы и не затирает более новую настройку. AI-диалог не назначает подтверждённый прогресс. При reset увеличивается epoch, исключаются старые реплики из будущего prompt и инвалидируются персональные кеши; финальная запись со старым epoch не восстанавливает память и получает отмену.
- **STORE-009:** По умолчанию тексты диалогов сохраняются не более 30 дней и не более 1000 последних запросов на пару player/NPC; применяется более строгая граница. Очистка выполняется малыми порциями вне игрового шага. Компактная память живёт до reset/удаления игрока с ограничениями AI-010; очистка архива сама по себе не отменяет память и не выдумывает новые факты. Минимальный ledger requestId/fingerprint/типа операции/terminal-статуса/кода ошибки или причины отмены/terminal seq (если сохранён) без пользовательских текстов сохраняется до удаления игрока для идемпотентности. Для preferences/reset в ledger сохраняется также небольшой исходный confirmation (locale/responseStyle при наличии, memoryRevision/reset epoch), чтобы повтор вернуть без второго изменения; текстовые квоты диалога не удаляют этот confirmation. Для generation повтор очищенного результата возвращает `result_expired`, а не запускает LLM снова. Удаление игрока удаляет его историю, ledger и память. Политика/результат очистки резервных копий документируются отдельно: удаление из живой БД не объявляется удалением из старого backup.
- **STORE-010:** Чтение истории и памяти всегда ограничено серверной идентичностью и владельцем диалога; игрок не получает чужие записи по ID. Полные тексты не дублируются в operational-логах, токены доступа не сохраняются. SQLite и backups доступны только разрешённому локальному оператору; локальное хранение не означает шифрование. Политика хранения сообщается оператору и пользователям; экспорт/удаление выполняются через авторизованный серверный интерфейс, не SQL от модели. Эти операции не требуют отдельного сложного UI в клиентском MVP.

### Состояние BABEL

- **STORE-012:** Миграция 002 добавляет `babel_parties` (группа и общее задание), `babel_profiles` (FK игрока и группы, языки, словарь, личные ответы) и `babel_operations` (ключ игрок/requestId, SHA-256 fingerprint без исходного действия, статус, подтверждение). Ограниченные JSON-агрегаты изменяются сервисом в короткой транзакции вместе с receipt операции. Ошибка записи откатывает инвентарь, прогресс и receipt целиком. Отправленные камни неизменяемы; профиль читается только для серверного владельца. На старте pending-операции и незавершённые переводы помечаются failed/error, повтор не создаёт дубликатов. Политика расширенной памяти NPC из STORE-006–010 остаётся отдельной работой.

## Сценарии

- **S1 · STORE-001–003, 011:** Given игрок сдвинулся и задал NPC вопрос; When сервер штатно перезапущен и игрок входит снова; Then позиция и история восстановлены, аккаунт и игрок не задублированы.
- **S2 · STORE-002, 004:** Given ошибка записи посреди первого входа; When операция завершается; Then частичной записи нет, вызывающий получил ошибку.
- **S3 · STORE-003, 005:** Given аварийное завершение (kill) через 5 с после движения и отдельная копия `VACUUM INTO`; When сервер запущен снова и копия открыта; Then БД целостна (`PRAGMA integrity_check`), потеряно не больше `saveIntervalMs`, копия читается.
- **S7 · STORE-011:** Given 51 ответ одному NPC и сбой записи на 52-м; When запрашивается история и задаётся 52-й вопрос; Then хранится 50 последних записей, на 52-й игрок получает `error UNAVAILABLE`, а не ответ.
- **S4:** STORE-006–007: Given 4 принятых запроса, профиль 1/2 и partial-снимки; When приходят дубли, отказывает БД либо процесс падает до/после commit; Then нет превышения квоты, повторной generation/частичного completed, сохранённый ответ восстанавливается, незавершённый отмечен interrupted. Проверяются освобождение резерва при отказе записи, cancel до физической остановки, общий restart при другом активном запросе и commit без доставки финала.
- **S5:** STORE-008: Given память и активный запрос; When выполняется reset; Then старый epoch не может записать память, прежние реплики не возвращаются в prompt из архива или кеша. Отдельно проверяются оба порядка cancel/commit, reset/commit и logout/commit: существует один durable terminal, право доставки проверяется заново.
- **S6:** STORE-009–010: Given больше 1000 запросов, старые тексты и другой игрок; When выполняется очистка, чтение, экспорт или удаление; Then сроки/квоты и права соблюдаются, очищенный requestId не генерируется заново, ограничения backup явно видны.

## Ограничения и вне scope

Инвентарь и другие игровые системы добавляются только по отдельным требованиям; их наличие не требуется для MVP.

## Открытые вопросы

v1 закрыт: схема, миграции, интервал сохранения и backup выбраны. Для v2 нужно спроектировать миграцию `npc_dialogue` в ledger STORE-006–010; это зависит от утверждения PROTO v2. `node:sqlite` в Node 24 помечен как развивающийся API: TASK-011 проверяет его на закреплённой версии, включая наличие FTS5 для будущего AI-008.
