# STORE — SQLite и состояние игроков

## Цель

Сохранять игроков и память взаимодействий на сервере между запусками.

## Требования

### Текущее хранение и базовая схема

- **STORE-001:** SQLite (`node:sqlite`, файл `dbPath`) находится только на сервере. Базовые поля миграции 001 (не полный перечень актуальной БД):

  | Таблица | Поля | Ограничения |
  |---|---|---|
  | accounts | id, name, name_key, created_at, password_hash, password_set_at, must_change_password, temp_password_expires_at | UNIQUE name_key; пароль хранится как scrypt с параметрами (AUTH-008) |
  | sessions | token_hash, account_id, created_at, expires_at, id, created_ip, revoked_at, revoke_reason | PK token_hash; FK accounts; публичный id для журналов; logout отмечает отзыв текущей сессии |
  | account_credentials | account_id, algorithm, salt, password_hash | Исторические scrypt-v1 записи ветки клиента; миграция переносит их в accounts без удаления исходных данных |
  | players | id, account_id, map_id, x, y, z, rotation_y, updated_at | PK id (формат ID PROTO, `p_` + 16 base36); account_id UNIQUE |
  | npc_dialogue | id, player_id, npc_id, question, answer, created_at | индекс (player_id, npc_id, created_at); FK players |
  | schema_migrations | version, applied_at | — |

  Аккаунт и его игрок создаются одной транзакцией при первом разрешённом guest-входе под новым именем. Password-регистрация создаёт account с хешем и player одной транзакцией для свободного имени. Парольный аккаунт с `players.avatar_id IS NULL` требует выбора облика до join. Позиция `NULL` означает «ещё не входил», при join используется spawn.
- **STORE-002:** Схема создаётся и меняется нумерованными SQL-миграциями из `server/src/persistence/migrations/`, применяемыми при старте в транзакции. Неизвестная (более новая) версия БД — ошибка запуска. Включены `foreign_keys = ON` и `journal_mode = WAL`. Связанные изменения фиксируются одной транзакцией; некорректные данные не создают частичную запись.
  Для известных старых dev-баз с пересекающимися номерами миграций дополнительно проверяется фактическое наличие avatar_id, equipped_tool и account_credentials, а также nullable party_id в babel_profiles. Недостающие части восстанавливаются в той же транзакции без удаления игроков, предметов и данных чужих расширений. История с пропусками/неизвестной версией по-прежнему отклоняется; SQL-причина ошибки запуска видна оператору. Миграция 006 разрешает профиль языков с party_id = NULL до создания/присоединения к игре.
  Миграция 007 объединяет поля паролей/отзыва сессий из main, проверяя каждую колонку отдельно. Старые account_credentials переносятся с прежними scrypt-параметрами и без изменения Unicode-семантики пароля; облики, экипировка, позиции и игровой прогресс сохраняются. Базы обеих веток допускают повторный запуск без повторного ALTER.

- **STORE-003:** Позиция и карта игрока сохраняются:
  - каждые `saveIntervalMs` (10 с), если изменились;
  - при удалении сущности из мира после grace;
  - при штатной остановке.

  Сохранения выполняются пакетно, одной транзакцией. После входа восстанавливается последняя сохранённая позиция. Окно потери при аварии — не более `saveIntervalMs` плюс длительность записи. Сессии, истёкшие больше суток назад, удаляются при старте и раз в час.
- **STORE-004:** SQLite открывается через `DatabaseSync` в основном процессе. Для MVP (≤4 игрока, запросы доли миллисекунды, пакетное сохранение раз в 10 с) отдельный worker не нужен. Игровой шаг не обращается к БД: сохранение позиций выполняется вне шага по таймеру. Все запросы параметризованы, SQL — только константы. Ошибка записи возвращается вызывающему, а не маскируется. Store-порты (`AccountStore`, `SessionStore`, `PlayerStore`, `DialogueStore`) реализованы поверх одного соединения. Сервисы тестируются с in-memory реализациями портов, адаптер — на временной БД. Если замер tick (REALTIME S7) покажет влияние записи, её выносят в worker; до замера — нет.
- **STORE-005:** README сервера описывает локальный backup/restore: для согласованной копии при работающем сервере используется `VACUUM INTO`, при остановленном — копирование файла с `-wal`/`-shm`. Восстановление проверяется на отдельной копии и не разрушает текущие данные.
- **STORE-011:** Текущая история NPC, общая для single-final и серверного opt-in потока PROTO-007. Каждый завершённый ответ NPC записывается в `npc_dialogue` (вопрос и ответ) **до** отправки `npc-answer`. Ошибка записи даёт игроку `error UNAVAILABLE`, а не ответ (NPC-003). На пару player/NPC хранится не более 50 последних пар вопрос/ответ: старые удаляются той же транзакцией. История читается только для владельца, последние ≤6 завершённых пар передаются в NpcResponder как контекст. Тексты не дублируются в логах.

### План расширенного AI-ledger и компактной памяти

Требования STORE-006–010 — будущая работа AI/LLM, исторически названная «этап v2», не текущая версия игрового протокола. Сейчас PROTO-007 реализует только opt-in partial/финал/отмену поверх Socket.IO v3: без durable-принятия, целевой сессионной памяти/отношений, чтения result после reconnect и ledger-идемпотентности. Прежний план пользовательского reset NPC отменён: новый scope появляется при новой AUTH-сессии, отдельной кнопки reset нет. Серверная GenerationQueue и запись завершённой пары до доставки по STORE-011 не заменяют этот план. Дубликаты requestId в текущем соединении отклоняются по PROTO-008, а не читают сохранённый AI-result.

Новые операции и их runtime-схемы должны быть согласованы в PROTO до реализации; снятый `npc.dialogue.*` автоматически не возвращается. Планируемая миграция сохраняет действующие данные, миграции BABEL и AUTH. Старым записям без достоверного sessionId нельзя выдумать принадлежность к текущей сессии: они остаются legacy-архивом и не подмешиваются в новый prompt. Требуется согласовать миграцию, срок хранения и чтение такого архива; реализованной миграции полного AI-ledger пока нет. Сценарии S4–S6, S8–S11 ниже относятся к плану, не к подтверждённой приёмке текущего сервера.
- **STORE-006 (план, архив и receipt):** Завершённая история текущей AUTH-сессии отделена от компактной памяти. Полный scope диалога — `(sessionId, playerId, npcId)`, все составляющие назначает/проверяет сервер. Архив хранит завершённые сообщения с role/видом и порядком; сгенерированное приветствие — самостоятельная NPC-реплика, без фиктивного вопроса игрока. Фиксированное окно последних 50 пар не является целевой политикой памяти. Доступ/хранение ограничиваются STORE-009–010; весь архив не загружается в RAM или prompt.

  Запрос/receipt содержит scope, dialogueId, requestId, тип операции, текст/снимок языка, время, fingerprint входа и состояние accepted/queued/running/completed/cancelled/failed/interrupted. Типы будущих операций согласуются в PROTO; пользовательского reset нет. Для completed сохраняются принятый финальный текст, finish reason, source IDs/редакции, версии model/profile/template, token counts и terminal seq, если поток используется. Для failed/cancelled/interrupted — только допустимый code/причина и необходимые метаданные. Событие показа игровой fallback-фразы не является completed-ответом LLM и не пополняет содержательную историю.

  Уникальность будущего ledger — `(sessionId, playerId, requestId)`; fingerprint включает NPC/тип/содержимое. Повтор с другим targetId или действием отклоняется, повтор в том же scope не запускает generation или изменение отношения заново. Другая сессия того же аккаунта не читает прежний result. Временные partial-снимки не архивируются по каждому обновлению; thinking не сохраняется. Восстановленный terminal авторитетнее потерянных временных снимков. Конкретная wire-форма receipt/result пока не реализована.
- **STORE-007 (план, атомарность):** До durable-принятия общая GenerationQueue атомарно резервирует квоты ≤4unfinished суммарно и ≤1 на playerId независимо от числа его AUTH-сессий/NPC, затем фиксирует запрос. При отказе допуска/БД резерв освобождается без inference. Чтение прежнего receipt не резервирует новый слот; приветствие и возможная модельная обработка памяти/намерения учитываются в том же бюджете, не создают вторую очередь или незаметный вызов.

  Принятый ответ, completed-статус и разрешённое изменение памяти фиксируются одной короткой транзакцией до успешной доставки; во время inference транзакция закрыта. Изменение отношения сервер валидирует по карточке и текущей revision. Его trigger, момент фиксации и влияние на этот же ответ должны быть согласованы до реализации; нельзя независимо повторять переход, применять его после cancel либо ухудшать отношение из-за fallback. Модель не пишет произвольное состояние напрямую.

  Финализация сериализована с timeout/cancel/отзывом доступа: running → completed допустим только при действующей исходной AUTH-сессии, актуальном управляющем соединении и revision памяти, соблюдении монотонного бюджета. Одной проверки до inference недостаточно. Если сначала зафиксированы cancel/expiry/revoke, поздний результат не создаёт completed/память/отношение и не переносится в новую сессию. Если первым committed completed, последующий logout не переписывает историю результата, но запрещает доступ и доставку по старой сессии; новый login не разрешает чтение старого результата. Потеря доставки после commit в той же разрешённой сессии восстанавливается чтением result без нового ответа.

  Сбой записи не объявляется сохранённым ответом: безопасный технический статус остаётся failed/provisional до установления факта commit; UI может показать игровую фразу как неудачную попытку. При неопределённом commit сначала проверяется receipt, generation не повторяется. После рестарта незавершённые записи становятся interrupted; committed результаты не затираются. Потеря/переполнение transport не требует rollback completed. Статус запроса в БД не освобождает физический слот: abort/quarantine сохраняют квоты до подтверждённой остановки. Уже показанный текст нельзя физически отозвать; поэтому неподтверждённые partial не должны обходить проверки будущего NPC-поведения.
- **STORE-008 (план, память и отношения):** Компактная память и отношение имеют ключ `(sessionId, playerId, npcId)`, тип/значение, provenance, исходный receipt/source/game event, время и revision. Память включает полезные темы, знакомство, разрешённые договорённости и явно сообщённые сведения; player-claim отделён от подтверждённого game-fact. Отношение хранится явно как обычное/недовольное/дружелюбное с ограниченным основанием и revision, не выводится заново из случайной сводки. Характер и постоянная биография — авторские данные профиля, не личная память.

  Архив, компактная память, FTS/retrieval-индекс, личный cache и восстановление result имеют один scope. Новая AUTH-сессия того же аккаунта начинает без их данных и с исходным отношением. Reconnect/меню/рестарт с той же ещё действующей сессией сохраняют её состояние; новый POST login/guest/dev создаёт новый scope, даже если прежняя сессия ещё действует. Истечение/отзыв закрывают прежний scope для prompt и UI. Нет кнопки сброса отдельного NPC, отдельного gameId или команды ведущего «новая игра» для этого механизма. Новая сессия не сбрасывает аккаунт, задания, словарь, инвентарь или языковые настройки.

  При закрытии сессии её pending-запросы отменяются и личные runtime-кеши инвалидируются; поздняя работа не пишет в новую сессию. Технический уход соединения отменяет запрос, но сам по себе не очищает сохранённую память действующей AUTH-сессии. Язык и другие разрешённые настройки игрока отделены от памяти; generation получает снимок и не затирает более новую настройку. Слова модели/игрока не назначают прогресс, чувствительные характеристики и оценку владения языком. Алгоритм отбора/сжатия, предел компактной памяти и происхождение новых записей требуют проекта и проверки до включения.
- **STORE-009 (план, ограниченное хранение):** Цель — завершённая история текущей AUTH-сессии, а не обязательное окно последних 50 пар. Хранение не безлимитное: до реализации должны быть утверждены пределы записей/байтов на диалог, сессию и сервер, предел компактной памяти, срок удаления закрытых scope/ledger и поведение при достижении квоты. Прежний проектный default30 дней/1000 запросов на player/NPC не является согласованной политикой нового сессионного архива. Нельзя молча обещать «весь разговор», а удалять действующую историю по неописанному лимиту; если нужен отказ в новых записях, он видим и не маскируется успешным запоминанием.

  Логическое закрытие scope при expiry/revoke немедленно запрещает использование памяти; физическая очистка отдельно выполняется малыми порциями вне игрового шага. Уникальные receipt/признаки очистки живут достаточно для дедупликации в допустимом окне чтения; удалённый результат не вызывает повторную generation. Удаление аккаунта охватывает его архив, память, отношения, индексы и ledger. Очистка живой БД не означает удаления старых backups; политика их хранения документируется отдельно. Проект миграции учитывает удаление AUTH-записей спустя сутки, не использует сырые токены как ключ памяти и не создаёт потерянные FK/бессрочные orphan-записи.
- **STORE-010 (план, доступ):** История, память, отношения, retrieval, result и cache проверяются по серверной действующей идентичности и полному scope `(sessionId, playerId, npcId)`. SessionId не секрет и сам по себе не разрешение; клиент не назначает scope. Фильтрация чужих игроков/NPC/сессий и ролевых знаний выполняется до поиска/выдачи кандидатов и до LLM. Другая действующая сессия того же аккаунта не получает старую историю под видом restore. Общие события мира могут быть видны по игровым правилам, чужие беседы автоматически в них не превращаются.

  Тексты и сырые токены не дублируются в operational-логах; диагностические причины не содержат prompt/произвольный stderr. SQLite/backups доступны только разрешённому оператору; локальность не означает шифрование. Политика сообщается оператору/пользователям. Административные экспорт/удаление по подтверждённым правам — отдельная граница, не интерфейс восстановления старой памяти новой AUTH-сессией и не пользовательская кнопка reset NPC. Модель не выполняет SQL, экспорт или удаление.

### Состояние BABEL

- В `babel_profiles` поля записи словаря `learned`, `example`, `exampleTranslation` хранятся отдельно от `note`. При чтении старого JSON отсутствующие поля получают false и пустые строки без удаления остальных данных; явное сохранение обновляет профиль и receipt одной транзакцией. Словарь и изменения доступны только владельцу.
- **STORE-012:** Миграция 002 добавляет `babel_parties` (группа и общее задание), `babel_profiles` (FK игрока и группы, языки, словарь, личные ответы) и `babel_operations` (ключ игрок/requestId, SHA-256 fingerprint без исходного действия, статус, подтверждение). Ограниченные JSON-агрегаты изменяются сервисом в короткой транзакции вместе с receipt операции. Ошибка записи откатывает инвентарь, прогресс и receipt целиком. Отправленные камни неизменяемы; профиль читается только для серверного владельца. На старте pending-операции и незавершённые переводы помечаются failed/error, повтор не создаёт дубликатов. Политика расширенной памяти NPC из STORE-006–010 остаётся отдельной работой.

## Профиль облика

Миграция 003 добавляет `players.avatar_id`: nullable TEXT с ограничением четырёх ID `lukas`, `nic`, `dan`, `ksu`. Старые записи получают null и остаются играбельными. POST настройки сохраняет только собственный ID в SQLite до успешного HTTP-ответа; периодическое сохранение позиции не перезаписывает облик. Null не означает регистрацию или обязательный выбор.

## Сценарии

- **S1 · STORE-001–003, 011 (текущий срез):** Given игрок сдвинулся и задал NPC вопрос; When сервер штатно перезапущен и игрок входит снова; Then позиция и нынешняя player/NPC-история восстановлены, аккаунт и игрок не задублированы. Это не проверка нового session scope; для цели действует S8.
- **S2 · STORE-002, 004:** Given ошибка записи посреди первого входа; When операция завершается; Then частичной записи нет, вызывающий получил ошибку.
- **S3 · STORE-003, 005:** Given аварийное завершение (kill) через 5 с после движения и отдельная копия `VACUUM INTO`; When сервер запущен снова и копия открыта; Then БД целостна (`PRAGMA integrity_check`), потеряно не больше `saveIntervalMs`, копия читается.
- **S7 · STORE-011:** Given 51 ответ одному NPC и сбой записи на 52-м; When запрашивается история и задаётся 52-й вопрос; Then хранится 50 последних записей, на 52-й игрок получает `error UNAVAILABLE`, а не ответ.
- **S4:** STORE-006–007: Given 4 принятых запроса, профиль 1/2 и partial-снимки; When приходят дубли, отказывает БД либо процесс падает до/после commit; Then нет превышения квоты, повторной generation/частичного completed, сохранённый ответ восстанавливается, незавершённый отмечен interrupted. Проверяются освобождение резерва при отказе записи, cancel до физической остановки, общий restart при другом активном запросе и commit без доставки финала.
- **S5 · STORE-007–008:** Given активный запрос/память; When происходят logout/expiry/revoke и новый вход; Then late commit не переносит ответ/отношение/память в новый scope. Проверить оба порядка cancel/commit и revoke/commit, а также старую действующую сессию при перехвате новой: terminal один, доступ и управление проверяются снова, физический слот удержан.
- **S6 · STORE-009–010:** Given архив у каждой границы согласованных квот и другая сессия/игрок; When выполняются очистка, retrieval/result или разрешённый операторский экспорт/удаление; Then границы и права соблюдены, очищенный результат не генерируется заново, повтор не создаёт новую запись/отношение, backup-ограничения явны. До выбора квот этот сценарий не считается готовым к выполнению.
- **S8 · STORE-008–010:** Given две одновременно действующие AUTH-сессии одного playerId и второй игрок; When один говорит с двумя NPC, возвращается из меню, переподключается и сервер перезапускается; Then восстановление есть только в том же действующем scope. Новый login получает исходные отношения и пустую NPC-память, но прежний словарь/инвентарь/прогресс. Ни FTS, ни summary, ни cache, ни result не открывают чужой scope.
- **S9 · STORE-006–008:** Given явное открытие разговора; When generation приветствия успешна и окно переоткрыто; Then сохранена одна NPC-only реплика, нет фиктивного user-вопроса/нового вызова. Given ошибка или fallback; Then нет completed-содержательного ответа или ложного факта памяти; технический отказ сам по себе не меняет отношение. Сочетание оскорбления/извинения с неуспехом генерации проверяется после решения о trigger/атомарности NPC-AI-009.
- **S10 · STORE-002, 008–010:** Given legacy player/NPC-история без sessionId; When выполняется будущая миграция и новый login; Then старым текстам не приписан текущий scope. AUTH expiry/очистка записей спустя сутки не оставляют доступного FTS/cache или orphan-ссылок; миграция/restore проверяются на отдельной копии.

- **S11 · STORE-008–010, 012:** Given сохранённый NPC-ответ BABEL и receipt старой AUTH-сессии; When другая действующая или новая сессия того же аккаунта читает HTTP snapshot/polling либо повторяет прежний NPC requestId; Then старый NPC-текст не виден ни в `replies`, ни в replay операции. Словарь, инвентарь и задания остаются доступными по обычным правам. Повтор в исходной действующей сессии не генерирует второй ответ. Проверить обе HTTP-поверхности после согласования миграции/scope; действующий PROTO-009 пока не считается соответствующим этому сценарию.

## Опорная позиция MOVE

STORE-003 сохраняет последнюю подтверждённую безопасную опорную позицию при прыжке/падении. После рестарта Y вычисляется по общей поверхности карты, verticalVelocity и незавершённый jump не восстанавливаются из SQLite. Существующая схема позиции сохраняется. В живом world reconnect/перехват сохраняет запас и вертикальную фазу; выход grace-сущности не даёт бесплатного заполнения запаса.

## STORE-013 — Подбираемые яблоки и руки

Миграция 008 добавляет `world_apples` (PK устойчивый id, map_id, состояние world/held, координаты либо holder_id FK players) и `world_hand_receipts` (PK player_id/request_id, fingerprint, JSON результата, created_at). CHECK запрещает одновременные world/held поля; UNIQUE partial index holder_id гарантирует 1 слот глобально. Данные не смешиваются с inventory BABEL.

При старте каталог карты добавляет только отсутствующие ID яблок, одной транзакцией; повторная генерация карты не сбрасывает владение и не дублирует сохранённые экземпляры. Изменение состава устойчивых ID при существующих яблоках — ошибка конфигурации, а не удаление сохранённых объектов. Владелец остаётся владельцем при disconnect/reconnect/restart; отсутствующий игрок не создаёт наземную копию. Сохранённые world-позиции проверяются по текущей геометрии; небезопасные данные дают явную ошибку запуска, а не молчаливую потерю.

Проверка состояния, переход яблока, уникальность слота и receipt выполняются в одной короткой BEGIN IMMEDIATE транзакции вне tick. Ошибка commit откатывает все изменения, результат успеха не отправляется. Одинаковый fingerprint возвращает сохранённый receipt, конфликтующий payload — CONFLICT. Геометрические отказы сохраняются как receipts; ошибки авторизации/формы/частоты и недоступность БД не считаются сохранёнными. Минимальные receipts сохраняются до удаления игрока; неограниченной очереди RAM нет. Горшки, расписание и декоративные фазы в SQLite не записываются.

Исходные footprints горшков зарезервированы от durable-размещения яблок: RAM-сброс после рестарта не создаёт пересечения. Некорректное сохранённое яблоко в таком footprint вызывает явный отказ старта; молчаливого переноса нет. Восстановление игрока дополнительно проверяет текущие RAM-горшки и применяет существующий безопасный spawn fallback. Сам spawn исключён из перемещений горшков.

Startup сверяет все сохранённые apple IDs/maps с полным ожидаемым каталогом всех загруженных сцен. Неожиданный сохранённый экземпляр, в том числе после удаления всего worldLife/пустого каталога, вызывает отказ старта и rollback seed; тихого принятия осиротевших яблок нет.

После интеграции UI и main каноническая последовательность: 003 — avatar_id, 004 — исторические account_credentials, 005 — equipped_tool, 006 — nullable party_id, 007 — поля авторизации accounts, 008 — world_apples/world_hand_receipts. При старте проверяется фактическая схема известных dev-баз: main auth 003/world-life 004, ранняя world-life 003 и UI 003–007. Недостающие аддитивные поля добавляются в общей startup-транзакции; существующие таблицы предметов и receipts сохраняются. Исходные записи schema_migrations и applied_at не перенумеровываются; новые версии получают время первого обновления. Неизвестная история отклоняется. Проверены обновление, повторный старт, сохранение владельцев, receipts, аккаунтов и NPC-истории в TASK-062.
