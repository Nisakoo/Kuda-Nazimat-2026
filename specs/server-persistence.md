# STORE — SQLite и состояние игроков

## Цель

Сохранять игроков и память взаимодействий на сервере между запусками.

## Требования

- **STORE-001:** SQLite находится только на сервере. Схема хранит идентичность пользователя, состояние игрока (карта, позиция, необходимый прогресс) и индивидуальную историю/память взаимодействий с NPC.
- **STORE-002:** Схема версионируется миграциями. Связь пользователя и игрока уникальна; связанные изменения фиксируются транзакционно, некорректные данные не создают частичную запись.
- **STORE-003:** Сохранение выполняется периодически, при значимых изменениях, выходе и штатной остановке. После входа восстанавливается последний подтверждённый снимок; после аварии допустимое окно потери соответствует документированному интервалу.
- **STORE-004:** Запросы параметризованы; ошибки записи не маскируются успешным сохранением. Доступ к SQLite и очередь записи не блокируют игровой цикл непредсказуемо.
- **STORE-005:** Документирован локальный backup/restore согласованной БД, включая используемый режим журнала. Восстановление проверяется на отдельной копии, не разрушает текущие данные.

## Сценарии

- **S1:** STORE-001–003: Given игрок изменил позицию/прогресс и говорил с NPC; When сервер штатно перезапущен; Then состояние и индивидуальная память восстановлены без дубликата.
- **S2:** STORE-002, 004: Given ошибка записи в середине изменения; When транзакция завершается; Then частичная запись отсутствует и ошибка видна.
- **S3:** STORE-003, 005: Given аварийное завершение и отдельная резервная копия; When выполняется восстановление; Then БД целостна, окно потери измерено, backup читается.

## Ограничения и вне scope

Инвентарь и другие игровые системы добавляются только по отдельным требованиям; их наличие не требуется для MVP.

## Открытые вопросы

Определить схему, интервал сохранения и допустимую потерю при аварии; политику хранения/очистки истории NPC.
