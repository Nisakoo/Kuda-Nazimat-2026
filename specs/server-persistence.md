# STORE — SQLite и состояние игроков

## Цель

Сохранять игроков и память взаимодействий на сервере между запусками.

## Требования

- **STORE-001:** SQLite находится только на сервере. Схема хранит идентичность пользователя, состояние игрока (карта, позиция, необходимый прогресс) и индивидуальную историю/память взаимодействий с NPC.
- **STORE-002:** Схема версионируется миграциями. Связь пользователя и игрока уникальна; связанные изменения фиксируются транзакционно, некорректные данные не создают частичную запись.
- **STORE-003:** Сохранение выполняется периодически, при значимых изменениях, выходе и штатной остановке. После входа восстанавливается последний подтверждённый снимок; после аварии допустимое окно потери соответствует документированному интервалу.
- **STORE-004:** Запросы параметризованы; ошибки записи не маскируются успешным сохранением. Доступ к SQLite и очередь записи не блокируют игровой цикл непредсказуемо.
- **STORE-005:** Документирован локальный backup/restore согласованной БД, включая используемый режим журнала. Восстановление проверяется на отдельной копии, не разрушает текущие данные.
- **STORE-006:** История диалогов хранится отдельно от компактной памяти. Запрос содержит server-owned playerId, npcId, dialogueId, requestId, текст/язык, время, fingerprint входа и состояние accepted/queued/running/completed/cancelled/failed/interrupted. Для завершённого запроса сохраняются финальный текст, finish reason, source IDs/редакции, model/profile/template версии, token counts и terminal seq. Ledger хранит тип операции (generation/preferences/reset): повтор ID с иным типом/содержимым — request_conflict, повтор завершённой настройки возвращает прежнее подтверждение без второго изменения revision. Ограниченные фрагменты streaming не пишутся в БД по каждому токену; thinking не сохраняется. Уникальность `(playerId, requestId)` предотвращает повторную generation/запись; повтор с другим содержимым отклоняется.
- **STORE-007:** До постановки в очередь фиксируется запрос; при недоступной БД inference не начинается. Финальный ответ, completed-статус и детерминированное изменение памяти фиксируются одной короткой транзакцией до успешного terminal-события. Транзакция не остаётся открытой во время inference. Сбой записи возвращает `persistence_error`; частичный streamed-текст не считается сохранённым ответом. При рестарте незавершённые состояния переводятся в interrupted, без автоматического воспроизведения generation. После commit и потери доставки повтор читает тот же сохранённый результат. Терминализация использует атомарный compare-and-set: только running → completed при актуальном reset epoch и действующем доступе; cancel может перевести accepted/queued/running → cancelled. Проверка доступа/эпохи и отзыв доступа сериализуются с финальным commit в одном per-player lifecycle-контуре/транзакционном порядке; одной проверки перед inference недостаточно. Если cancel/reset/отзыв доступа первым зафиксирован, completed не создаётся; если первым зафиксирован completed, последующая отмена не переписывает его в cancelled. Reset после completed очищает память и границу prompt-истории, но не делает исторический completed новым ответом. Logout после completed запрещает доставку до нового разрешённого входа; результат остаётся в БД. Уже показанный временный текст нельзя считать отозванным физически — UI лишь меняет его статус.
- **STORE-008:** Компактная память имеет ключ `(playerId, npcId)`, тип/значение, provenance (topic/source/game event или явная настройка), время и revision/reset epoch. Ограничения AI-010 проверяются при записи, не только при сборке prompt. Языковая настройка игрока хранится отдельно; предпочтение responseStyle задаётся только валидированной явной операцией PROTO-007 (standard/simple_no_formulas), без свободного извлечения LLM. Настройки фиксируются отдельной короткой транзакцией с идемпотентным подтверждением; завершение generation обновляет только допустимые обсуждавшиеся темы и не затирает более новую настройку. AI-диалог не назначает подтверждённый прогресс. При reset увеличивается epoch, исключаются старые реплики из будущего prompt и инвалидируются персональные кеши; финальная запись со старым epoch не восстанавливает память и получает отмену.
- **STORE-009:** По умолчанию тексты диалогов сохраняются не более 30 дней и не более 1000 последних запросов на пару player/NPC; применяется более строгая граница. Очистка выполняется малыми порциями вне игрового шага. Компактная память живёт до reset/удаления игрока с ограничениями AI-010; очистка архива сама по себе не отменяет память и не выдумывает новые факты. Минимальный ledger requestId/fingerprint/типа операции/terminal-статуса/terminal seq без пользовательских текстов сохраняется до удаления игрока для идемпотентности. Для preferences/reset в ledger сохраняется также небольшой исходный confirmation (locale/responseStyle при наличии, memoryRevision/reset epoch), чтобы повтор вернуть без второго изменения; текстовые квоты диалога не удаляют этот confirmation. Для generation повтор очищенного результата возвращает `result_expired`, а не запускает LLM снова. Удаление игрока удаляет его историю, ledger и память. Политика/результат очистки резервных копий документируются отдельно: удаление из живой БД не объявляется удалением из старого backup.
- **STORE-010:** Чтение истории и памяти всегда ограничено серверной идентичностью и владельцем диалога; игрок не получает чужие записи по ID. Полные тексты не дублируются в operational-логах, токены доступа не сохраняются. SQLite и backups доступны только разрешённому локальному оператору; локальное хранение не означает шифрование. Политика хранения сообщается оператору и пользователям; экспорт/удаление выполняются через авторизованный серверный интерфейс, не SQL от модели. Эти операции не требуют отдельного сложного UI в клиентском MVP.

## Сценарии

- **S1:** STORE-001–003: Given игрок изменил позицию/прогресс и говорил с NPC; When сервер штатно перезапущен; Then состояние и индивидуальная память восстановлены без дубликата.
- **S2:** STORE-002, 004: Given ошибка записи в середине изменения; When транзакция завершается; Then частичная запись отсутствует и ошибка видна.
- **S3:** STORE-003, 005: Given аварийное завершение и отдельная резервная копия; When выполняется восстановление; Then БД целостна, окно потери измерено, backup читается.
- **S4:** STORE-006–007: Given streaming и один requestId; When приходит дубль, БД отказывает либо сервер падает до/после commit; Then нет второй generation/частичного completed, сохранённый ответ восстанавливается, незавершённый отмечен interrupted.
- **S5:** STORE-008: Given память и активный запрос; When выполняется reset; Then старый epoch не может записать память, прежние реплики не возвращаются в prompt из архива или кеша. Отдельно проверяются оба порядка cancel/commit, reset/commit и logout/commit: существует один durable terminal, право доставки проверяется заново.
- **S6:** STORE-009–010: Given больше 1000 запросов, старые тексты и другой игрок; When выполняется очистка, чтение, экспорт или удаление; Then сроки/квоты и права соблюдаются, очищенный requestId не генерируется заново, ограничения backup явно видны.

## Ограничения и вне scope

Инвентарь и другие игровые системы добавляются только по отдельным требованиям; их наличие не требуется для MVP.

## Открытые вопросы

Определить физическую схему/миграции, интервал сохранения игрового состояния и допустимую потерю при аварии. Для NPC политика истории и памяти выбрана в STORE-006–010; durable-завершение диалога не откладывается до периодического сохранения игрока. Конкретный backup/retention-процесс зависит от серверного runtime и условий демонстрации.
