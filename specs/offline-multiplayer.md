# OFFLINE — Офлайн-мультиплеер: LAN, Wi-Fi и один компьютер

Спека заменяет `system-offline-demo.md` (retired) и удалённую `server-demo.md`. Ориентир — продукт, которым администратор пользуется без разработчика, а не разовая демонстрация. ИИ и LLM сюда не входят: NPC работают через порт `NpcResponder` по [NPC](server-npc-dialogue.md), квалификация модели — [LLM-QA](npc-llm-evaluation.md).

## Продукт

### Цель
Группа до 4 человек играет в одном общем мире без интернета: дома, в поездке, в закрытой сети. Администратор готовит всё на одном компьютере, игрокам ничего не нужно устанавливать — только браузер.

### Роли
- **Администратор (хост)** — тот, кто запускает сервер для группы; не обязательно программист. Один раз готовит компьютер-сервер, перед игрой запускает его и сообщает игрокам адрес. Во время игры видит, кто подключён.
- **Игрок** — человек со своим ноутбуком или с общим компьютером. Открывает адрес, вводит имя, играет. Возвращаясь, входит под тем же именем и продолжает с того же места.

### Ценность
- **Работает там, где нет интернета или он недоступен:** поездки, закрытые сети, дом. Данные игроков не покидают компьютер администратора.
- **Нулевая установка у игроков:** любой современный браузер на ноутбуке.
- **Предсказуемость:** одна команда запуска, понятный адрес, понятные сообщения об ошибках.

### Три режима сети

| Режим | Когда | Как подключаются | Ограничения |
|---|---|---|---|
| **R1. Свой роутер** (рекомендуемый) | администратор приносит недорогой Wi-Fi-роутер или точку доступа без интернета | все устройства в Wi-Fi роутера; игроки открывают `http://<IP сервера>:8080` | нужен роутер; IP сервера лучше закрепить в настройках роутера |
| **R2. Существующая сеть** | на месте есть общая Wi-Fi или проводная сеть | так же, по IP сервера в этой сети | в гостевых и публичных сетях бывает изоляция клиентов — устройства не видят друг друга; тогда режим неприменим, переход на R1 |
| **R3. Один компьютер** | нет сети или игроки сидят за одним компьютером по очереди | `http://localhost:8080`, каждый игрок — своё окно браузера под своим именем | Wi-Fi можно выключить; браузеры и сервер делят ресурсы одного компьютера |

Раздачу Wi-Fi самим компьютером-сервером («мобильная точка доступа») продукт не поддерживает. Windows обычно требует для неё действующего подключения к интернету, macOS — проводного входа, поведение зависит от драйвера. Для R1 нужен отдельный роутер.

### Путь администратора
1. **Один раз, с интернетом:** подготовить компьютер-сервер одной командой (`make prepare`). Ставит зависимости, собирает клиент, готовит мир, проверяет Node.
2. **Перед игрой, без интернета:** подключить компьютер к сети режима R1/R2 или ни к чему (R3) и запустить `make start`.
3. **Сообщить адрес:** сервер печатает его крупно в консоли и показывает на экране администратора `http://localhost:8080/operator`.
4. **Во время игры:** на экране администратора видны подключённые игроки и состояние сервера.
5. **После игры:** остановить сервер (Ctrl+C). Прогресс сохраняется и будет на месте в следующий раз.

### Путь игрока
1. Открыть адрес в браузере.
2. Ввести имя и нажать «Войти».
3. Играть. При кратком обрыве Wi-Fi игра сама переподключается. При долгом — кнопка «Повторить» и тот же вход по имени: игрок возвращается в то же место с той же историей.

### Метрики успеха
- От включения подготовленного компьютера до двух игроков в мире — **≤ 5 минут**, включая ввод адреса.
- Подключение одного игрока после того, как он узнал адрес, — **≤ 30 секунд**.
- Обрыв Wi-Fi до 7 секунд — игрок возвращается автоматически, без потери позиции.
- **Ноль** запросов в интернет во время игры.
- Администратор может определить причину «не открывается» по таблице диагностики **без** разработчика.

### Вне продукта этой спеки
- Игра через интернет на хостинге и домене, HTTPS, настоящие аккаунты с паролями — отдельная спека онлайн-развёртывания.
- Больше 4 игроков и несколько групп одновременно («комнаты») — открытое продуктовое решение (см. «Открытые вопросы»).
- Имя вместо IP (mDNS `*.local`) и QR-код с адресом — отложено; см. «Открытые вопросы».

## Техника

### Топология
```
   R1/R2                                   R3
 ┌──────────┐   Wi-Fi/LAN   ┌──────────┐   ┌──────────────────────────┐
 │ браузер  │◀────────────▶│  роутер  │   │ один компьютер           │
 │ игрока   │               │ (без     │   │  браузер ×N ─┐           │
 └──────────┘               │ интернета)│   │              ▼ loopback  │
 ┌──────────┐               └────┬─────┘   │  сервер :8080            │
 │ браузер  │◀───────────────────┤         │  SQLite, мир, NPC        │
 └──────────┘                    ▼         └──────────────────────────┘
                     ┌──────────────────────────┐
                     │ компьютер-сервер :8080   │
                     │ HTTP: клиент, /config,   │
                     │ /api, /world, Socket.IO  │
                     │ SQLite, мир, NPC         │
                     └──────────────────────────┘
```
Один процесс Node на одном порту отдаёт клиент, `/config.json`, вход `/api/auth/guest`, файлы мира `/world/*` (Bearer) и Socket.IO `/game` ([SERVER](server-foundation.md)). Клиент обращается к тому же адресу, с которого загружен (`serverUrl: null`), поэтому одна сборка работает на `localhost` и на любом IP без настройки и без CORS.

### Требования

**Подготовка и запуск**
- **OFFLINE-001 (офлайн-пакет):** `make prepare` при наличии интернета:
  1. проверяет Node 24.15+;
  2. выполняет `npm ci` клиента и сервера;
  3. собирает клиент (`client/dist`) и генерирует мир (`client/public/maps/*`);
  4. запускает самопроверку сервера: конфигурация, мир, миграции БД.

  После этого запуск, вход, игра, сохранение и NPC-заглушка работают без интернета. Повторный `make prepare` идемпотентен и не трогает БД игроков.
- **OFFLINE-002 (запуск):** `make start` (нынешний `make demo` — его синоним) запускает сервер, который слушает `host:port` из конфигурации (по умолчанию `0.0.0.0:8080`). При готовности сервер печатает **блок подключения**:
  - адрес для этого компьютера: `http://localhost:8080/`;
  - адреса для других устройств — по одному на каждый не-loopback IPv4 с именем интерфейса. Частные диапазоны `192.168/16`, `10/8`, `172.16/12` идут первыми; link-local `169.254/16` помечены «нет сети»;
  - адрес экрана администратора;
  - предупреждения:
    - нет ни одного сетевого интерфейса — «доступен только режим одного компьютера»;
    - `host` = `127.0.0.1` — «другие устройства не подключатся»;
    - напоминание про брандмауэр с короткой инструкцией для текущей ОС (OFFLINE-006).
- **OFFLINE-003 (порт и повторный запуск):** если порт занят, сервер завершается с понятной ошибкой: какой порт, вероятная причина «сервер уже запущен в другом окне», как сменить порт (`--port <номер>`, `make start PORT=<номер>` или `port` в конфигурации). Windows сообщает о порте, занятом другой программой, как `EACCES`: это тоже понятная ошибка с тем же способом смены порта. Повторный запуск после Ctrl+C работает сразу, без «залипшего» порта и без потери данных.

**Подключение игроков**
- **OFFLINE-004:** *(снято 2026-11-01.)* Поддержка браузеров и сообщение без WebGL 2 — требования к клиенту, они ведутся в клиентских спеках. Серверная часть: всё отдаётся по обычному HTTP на IP-адресе, без требований HTTPS.
- **OFFLINE-005 (вход):** вход по имени или, в режиме `auth.mode: password`, по имени и паролю ([AUTH](server-auth.md)). Одно имя — один игрок; забытый пароль администратор заменяет временным с экрана `/operator` (AUTH-010); повторный вход под тем же именем возвращает того же персонажа, позицию и историю NPC. Пятый игрок при занятых четырёх местах видит «Сервер заполнен: в мире уже 4 игрока» ([SERVER](server-foundation.md) SERVER-006). Вторая вкладка с тем же именем забирает управление у первой, первая видит «Игра открыта в другом окне».
- **OFFLINE-006 (брандмауэр и ОС):** README и блок подключения дают инструкцию для каждой ОС:
  - **Windows:** при первом запуске разрешить Node.js для **частных** сетей; сеть роутера должна иметь профиль «Частная» — в «Общественной» входящие подключения блокируются;
  - **macOS:** разрешить входящие подключения для Node в «Системные настройки → Сеть → Брандмауэр»;
  - **Linux:** открыть TCP-порт (например, `ufw allow 8080/tcp`).

  Сервер не меняет настройки брандмауэра сам.
- **OFFLINE-007 (сетевые требования):**
  - входящий TCP на `port` сервера из сети игроков;
  - устройства в одной IP-сети без изоляции клиентов;
  - DNS и интернет не нужны;
  - IP сервера стабилен на время игры — рекомендуется резервирование DHCP на роутере.

  Ожидаемая нагрузка на сеть: игровой канал — до ~10 KB/s на игрока (delta до 10 раз в секунду, только изменения поблизости); вход в мир — порядка 2 MB данных карты на игрока, затем подгрузка по мере движения. Рабочая сетевая задержка — до 150 ms; в LAN обычно меньше 20 ms.

**Диагностика и экран администратора**
- **OFFLINE-008 (самопроверка):** `npm --prefix server run lan:check` без запуска игры печатает:
  - версию Node;
  - сетевые интерфейсы с IPv4 и признаком private/link-local;
  - свободен ли порт;
  - найдены ли сборка клиента и мир;
  - открывается ли БД;
  - инструкцию по брандмауэру для текущей ОС.

  Код выхода ненулевой, если запуск невозможен.
- **OFFLINE-009 (проверка с устройства игрока):** Публичный health разрешает GET с любого origin (`Access-Control-Allow-Origin: *`), без credentials; это позволяет проверить IP/порт и версию до навигации к целевому серверу. Авторизованные API сохраняют отдельные ограничения CORS. `GET /api/health` открывается в браузере игрока и возвращает `{"status":"ok","protocol":3,"npc":"ready"|"unavailable"}`. В README есть таблица «симптом → причина → действие»:

  | Симптом | Причина | Действие |
  |---|---|---|
  | адрес не открывается | брандмауэр / профиль «Общественная» / изоляция клиентов / не тот IP / разные сети | OFFLINE-006, проверить IP в блоке подключения, перейти на R1 |
  | открывается `/api/health`, но не игра | нет сборки клиента | `make prepare` |
  | «Сервер заполнен» | 4 игрока уже в мире | дождаться выхода одного (место освобождается через 10 с после ухода) |
  | «Игра открыта в другом окне» | то же имя во второй вкладке | закрыть лишнюю вкладку |
  | «Связь потеряна» | обрыв Wi-Fi или сервер остановлен | «Повторить», проверить сервер |
  | после смены сети ничего не открывается | IP сервера сменился | взять новый адрес из блока подключения |
- **OFFLINE-010 (экран администратора):** `GET /operator` отдаётся **только** запросам с loopback-адреса (`127.0.0.1`, `::1`); с других адресов — 404. Это простая страница сервера без игрового клиента. Она показывает:
  - адреса подключения из блока OFFLINE-002, крупно — их можно вывести на проектор;
  - игроков в мире: имя, карта, «подключён» или «вышел, место удержано N с»;
  - число занятых мест из 4;
  - состояние NPC (`ready`/`unavailable`) и время работы сервера.

  Страница обновляется раз в 2 секунды. Токены, тексты чата и вопросы к NPC на ней не показываются. Данные — из `GET /api/operator/status`, который тоже доступен только с loopback. Общее состояние, RTT и FPS игроков, последние события, графики и действия администратора (пароли, сессии, отчёт) — расширение [OBS](server-observability.md) OBS-010, OBS-014.

**Устойчивость**
- **OFFLINE-011 (обрывы):** клиент переподключается сам — до трёх попыток через 1, 2 и 4 секунды ([PROTO](protocol.md)). Сервер удерживает игрока в мире 10 секунд после разрыва (REALTIME-006): при возврате в этот срок другие игроки не видят исчезновения и повторного появления. После более долгого обрыва игрок нажимает «Повторить» и входит под тем же именем — позиция и история восстанавливаются из SQLite.
- **OFFLINE-012 (перезапуск и сбой сервера):** штатная остановка сохраняет позиции всех игроков; аварийная теряет не больше 10 секунд движения ([STORE](server-persistence.md) STORE-003). После перезапуска игроки входят под теми же именами и продолжают. Если перезапуск сменил IP (другая сеть), игроки открывают новый адрес — данные те же.
- **OFFLINE-013 (появление игроков):** новые игроки и игроки без сохранённой позиции не появляются в одной точке: сервер выбирает свободное проходимое место рядом со spawn карты ([REALTIME](server-realtime.md) REALTIME-010).

**Поставка, безопасность, наблюдаемость**
- **OFFLINE-014 (только онлайн в серверной поставке):** сервер отдаёт клиенту `/config.json` с `session: "online"` вместо файла из сборки. Публичный обходной доступ к `maps/` и `assets/models/` закрыт (SERVER-003), поэтому локальные режимы клиента в серверной поставке не загружают мир. Скрытие этих режимов в настройках — клиентская задача, вне этой спеки.
- **OFFLINE-015 (безопасность в LAN):** HTTP без шифрования (пароль и токен можно перехватить в той же сети) и, в режиме `guest`, вход по имени без пароля — принятые риски офлайн-режима, явно описанные в README. Рекомендация: сеть роутера R1 под паролем WPA2/WPA3; не запускать сервер в публичных сетях. Данные мира отдаются только с токеном и только вокруг игрока (SERVER-WORLD-006). Управляющие функции (`/operator`) — только с loopback. Токены и тексты сообщений не пишутся в логи.
- **OFFLINE-016 (наблюдаемость):** минимум для офлайн-поставки; полные требования к логам, метрикам и дампам — [OBS](server-observability.md).
  - в лог сервера пишутся вход в мир, отключение, перехват, освобождение места — с playerId и IP устройства, без токенов и текстов;
  - раз в 60 с — длительность шага;
  - `npm --prefix server run inspect` показывает игроков, позиции, сессии и диалоги без секретов (бывший SERVER-DEMO-003);
  - `logWorldAccess` включает лог выдачи `/world/*` (бывший SERVER-DEMO-004).

**Ёмкость и производительность**
- **OFFLINE-017 (ёмкость):** до 4 игроков в одном мире на сервер. Каждый целевой режим держит 4 игроков с движением, чатом и вопросами NPC:
  - p95 шага сервера ≤ 5 ms;
  - p95 интервала рассылки ≤ 120 ms;
  - без ошибок сервера.

  Для R3 (сервер и до 4 окон браузера на одном компьютере) дополнительно измеряются FPS клиента и загрузка CPU. Цифры снимаются отчётом `npm --prefix server run report` ([OBS](server-observability.md) OBS-017) по журналу прогона; FPS — из отчётов клиента OBS-011.

**Проверка**
- **OFFLINE-018 (автотесты):**
  - интеграционный тест запускает настоящий сервер на `0.0.0.0` и подключает два `socket.io-client` по **не-loopback** IPv4 машины, если такой есть: вход, синхронизация движения, чат, `/world` с Bearer. Отсутствие такого адреса фиксируется как пропуск, а не как успех;
  - unit-тесты блока подключения: сортировка интерфейсов, предупреждения, link-local;
  - тесты `/operator` и `/api/operator/status`: 404 с не-loopback, отсутствие секретов;
  - тест занятого порта.

  Тесты проходят на Windows, macOS и Linux — без POSIX-путей, symlink и `SIGTERM` в Windows. Где Windows не позволяет symlink (без режима разработчика) или не доставляет `SIGTERM` дочернему процессу, тест проверяет то же поведение доступным там способом, а не пропускает его.
- **OFFLINE-019 (приёмка на устройствах):** ручной протокол на реальных устройствах, результаты записываются в задачу:
  - **R1:** сервер плюс минимум два физических ноутбука по Wi-Fi своего роутера без интернета;
  - **R2:** если доступна общая сеть — то же; при изоляции клиентов фиксируется «неприменимо»;
  - **R3:** один компьютер с выключенным Wi-Fi.

  В каждом режиме проверяются:
  - вход двух игроков, взаимная видимость и движение, чат, вопрос NPC;
  - обрыв Wi-Fi на 5 с и на 30 с;
  - перезапуск сервера и повторный вход под тем же именем;
  - пятый игрок или вторая вкладка;
  - отсутствие запросов в интернет — DevTools Network или отключённый внешний доступ.

  Для R1 и R3 — замеры OFFLINE-017: таблица `npm --prefix server run report -- --markdown` вставляется в задачу. Неисполненный режим записывается как непроверенный.

## Сценарии

- **S1 · OFFLINE-001–003, 008:** Given чистый компьютер с интернетом; When выполнены `make prepare`, затем интернет выключен и выполнен `make start`; Then сервер запущен, блок подключения показывает localhost- и LAN-адреса с предупреждением про брандмауэр, `lan:check` проходит. Повторный `make start` при запущенном сервере даёт понятную ошибку занятого порта.
- **S2 · OFFLINE-005–007, 011, 013 (R1):** Given сервер и два ноутбука в Wi-Fi роутера без интернета; When оба игрока открывают LAN-адрес и входят под разными именами; Then оба в мире, появились в разных точках, видят движение друг друга, чат и NPC работают. When у второго выключить Wi-Fi на 5 с; Then он возвращается сам, первый не видит исчезновения. When на 30 с; Then после «Повторить» и входа тот же персонаж на том же месте.
- **S3 · OFFLINE-009 (R2):** Given общая сеть с изоляцией клиентов; When игрок открывает LAN-адрес и `/api/health`; Then оба не открываются, и таблица диагностики приводит администратора к переходу на R1.
- **S4 · OFFLINE-005, 012 (R3):** Given один компьютер с выключенным Wi-Fi; When в двух окнах входят «Аня» и «Борис», затем сервер перезапускается; Then оба продолжают с тех же мест; пятое окно при четырёх игроках видит «Сервер заполнен».
- **S5 · OFFLINE-010, 015–016:** Given двое в мире; When администратор открывает `/operator` на сервере, а игрок пытается открыть `/operator` со своего ноутбука; Then у администратора видны оба игрока и 2/4 мест, у игрока — 404. В логе есть входы с IP, нет токенов и текстов.
- **S6 · OFFLINE-014:** Given клиент открыт с сервера; When запрошены `/config.json`, `/maps/market/manifest.json` и `/world/...` без токена; Then конфигурация — `session: "online"`, публичные файлы мира — 404, защищённые — 401.
- **S7 · OFFLINE-017–019:** Given 4 игрока в R1 и R3; When 60 с движения, чата и вопросов NPC; Then замеры укладываются в пороги OFFLINE-017, ручной протокол записан для каждого режима.

## Ограничения и вне scope

- Онлайн-развёртывание (хостинг, домен, HTTPS, обратный прокси, аккаунты с паролями) — отдельная спека; этот режим не предполагает выход сервера в интернет.
- Компьютер-сервер как точка доступа Wi-Fi не поддерживается (см. «Три режима сети»).
- Мобильные браузеры и сенсорное управление не входят: игра рассчитана на клавиатуру и мышь.
- ИИ и LLM — [AI](server-ai.md), [LLM](server-llm-runtime.md), [LLM-QA](npc-llm-evaluation.md).

## Открытые вопросы

- **Комнаты и число игроков.** Продукт пока держит одну группу до 4 человек на сервер. Несколько групп одновременно меняют модель мира, слоты и задания — решается до спеки совместных заданий v2.
- **Адрес без IP.** mDNS (`babylon.local`) удобен, но на части Windows `.local` резолвится ненадёжно и требуется дополнительная зависимость; QR-код с адресом на экране администратора проще и надёжнее — кандидат на следующую итерацию OFFLINE-010.
