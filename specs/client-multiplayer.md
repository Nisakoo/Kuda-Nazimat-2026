# NET — OnlineSession и Socket.IO

## Цель

Подготовить клиент к серверу `server/` и проверить сетевые сценарии без него.

## Требования

- **NET-001:** NetworkAdapter предоставляет connect, disconnect, send, subscribe, статус и ошибки. Socket.IO Client импортируется только внутри SocketIOAdapter; транспорт подключается явно, без автоматического соединения при создании.
- **NET-002:** OnlineSession реализует GameSession, отправляет команды и применяет авторитетные обновления согласно [PROTO](protocol.md). Буферизует и интерполирует визуальные transform всех игроков, включая своего, с задержкой 100 мс; камера следует за сглаженным визуалом. Снимок сессии остаётся авторитетным, экстраполяции и локального расчёта позиции нет.
- **NET-003:** Статусы включают неавторизован, подключается, подключён, связь потеряна и ошибка. Реальный игровой канал открывается только с предоставленной серверной сессией; в online без сессии текущий UI показывает форму имени по NET-007. Она работает с guest-входом development/test, но не с production: сервер уже требует пароль. Клиентские формы register/login/password, dev-autologin и серверный logout ещё требуют [TASK-044](../tasks/044-client-auth-observability-handoff.md); отсутствие этих форм не означает отсутствие серверной авторизации.
- **NET-004:** Автопереподключение имеет ограниченную частоту, отменяется при logout/dispose; отказ авторизации не вызывает бесконечный retry. После восстановления выполняется повторный вход и синхронизация. Для текущего single-final NPC по PROTO v3 вопрос без ответа до разрыва завершается ошибкой и автоматически не переотправляется. Effective `npcTimeoutMs` клиент получает через `/api/game-config` фактического serverUrl при connect/reconnect; NPC pending ждёт срок +2000 мс, остальные pending/чат — 10 с. Настройка старого соединения игнорируется, без достоверной настройки NPC недоступен без блокировки мира/чата. Серверный срок default 30000 мс, config 1–300000 мс, Make/CLI — целые секунды 1–300; очередь включена. Буферы транспорта не сохраняют действия для повтора после разрыва; input допускает потерю пакета, join/chat/NPC отправляются только при действующем соединении и переживают переключение polling → WebSocket.
- **NET-005:** MockNetworkAdapter позволяет проверять снимки, события, задержки, ошибки, разрыв и переподключение без реального сервера. Тестовая авторизация существует только в mock и не отключает защиту реального адаптера.
- **NET-006:** Отсутствующий сервер не приводит к зависанию или падению. Адрес берётся из конфигурации, по умолчанию same-origin; при завершении закрываются соединения, таймеры, подписки и буферы.

- **NET-007:** На этапе интеграции с реальным сервером браузерный UI получает серверную сессию выбранным способом локального входа, передаёт её сетевому и HTTP-адаптерам и выполняет выход. Текущий клиент использует `POST <serverUrl>/api/auth/guest {name}` → `{token, expiresAt}` и передаёт ответ в `GameApp.provideServerSession()`; выход пока закрывает обмен и забывает токен локально. Сервер [AUTH](server-auth.md) уже реализует парольные register/login/password, отзыв сессий и `POST /api/auth/logout`: guest разрешён в development/test, запрещён в production. Подключение этих серверных возможностей к клиенту — TASK-044, не выполненная часть текущего UI. Ошибки/истечение сессии возвращают пользователя к входу и закрывают игровой обмен; ручная подстановка токена разработчиком не заменяет демонстрационный вход.

Текущее поведение guest-формы NET-007 (development/test, не готовый production-вход):
- Одно поле имени (1–32 символа после trim, без управляющих символов), кнопка входа и состояние ожидания. Текст поясняет, что имя сохраняет игрока, но не защищено паролем; обычные пользователи не вводят токены.
- POST идёт только на настроенный serverUrl, с JSON `{name}`. Ответ валидируется общим parseServerSession. Ошибка API отображается текстом; ошибка сети, неверный ответ и timeout 10 с оставляют форму доступной для повтора. До успешного ответа нет /game и /world.
- Одновременно выполняется один запрос входа. Смена настроек/сервера, выход, перезапуск и dispose отменяют его; поздний ответ старого запроса не создаёт сессию. Нет автоматического повторного POST.
- Токен хранится только в памяти GameApp/адаптеров, не в URL, конфигурации, localStorage или sessionStorage. Выход доступен до начала прогулки и в меню, закрывает соединение и освобождает мир. Reload снова требует входа.
- Истечение сессии, 401 мира и UNAUTHORIZED игрового канала закрывают старый обмен и возвращают форму. Причина сервера при перехвате управления показывается текстом. При сетевом разрыве действующая сессия остаётся доступной для ограниченного reconnect по NET-004.

## Сценарии

- **S1:** NET-001, 003, 005: Given нет серверной сессии; When запрошено реальное подключение; Then канал не открывается. Given mock; When предоставлен тестовый контекст; Then сценарии проверяются без сервера.
- **S2:** NET-002: Given снимки двух удалённых игроков; When приходят обновления; Then состояние обновляется по контракту, отображение интерполируется.
- **S3:** NET-004–006: Given недоступный сервер, разрыв или отказ авторизации; When соединение восстанавливается либо приложение завершается; Then статус понятен, retry контролируется, после dispose нет подписок и попыток соединения. Для single-final NPC по v3 ожидающий вопрос получает ошибку без повтора; пропавшие действия не воспроизводятся автоматически.

- **S4:** NET-003–004, 007: Given реальный сервер и браузер; When пользователь входит, открывает мир, выходит и пытается использовать старую сессию; Then вход даёт доступ к каналу и данным мира, текущий logout UI закрывает обмен и удаляет локальный токен, но ещё не вызывает реализованный сервером `POST /api/auth/logout`. Без отдельного отзыва серверная сессия может оставаться действующей до expiresAt; серверный отзыв по AUTH-012 немедленно закрывает её игровой канал. После истечения/отзыва UI предлагает вход заново. Production-вход и вызов серверного logout из UI проверяются после TASK-044, не считаются выполненными этим сценарием guest-формы.

- **S5 · NET-007:** Given online без сессии; When отправлено пустое/невалидное имя, API вернул ошибку или ответ не пришёл за 10 с; Then видна понятная ошибка, повтор возможен, игровой обмен не открыт. При двойном submit выполняется один POST.
- **S6 · NET-006–007:** Given запрос входа выполняется; When изменён сервер/режим или приложение завершено; Then запрос отменён, поздний ответ не подключает старый сервер.
- **S7 · NET-004, 007:** Given действующая сессия; When приходит 401 мира, expiresAt или UNAUTHORIZED с причиной перехвата; Then закрыты канал и мир, показаны форма и причина, автоматического guest-входа нет.

## Ограничения и вне scope

Prediction/reconciliation — будущая возможность, не обязательная реализация. Настоящий сервер внутри клиента не создаётся. NET-001–006 входят в клиентский MVP, NET-007 реализуется клиентом после готовности AUTH; полный игровой S4 выполняется с готовым набором A в TASK-026/016. Операторские inspect/backup остаются CLI сервера и не выдаются браузеру.

## Открытые вопросы

Handshake и ограничения определены в игровом PROTO v3. Серверный production-вход уже парольный; текущая клиентская форма имени подходит только для development/test ([AUTH](server-auth.md)). Клиентская интеграция парольных форм, dev-autologin и серверного logout остаётся TASK-044. Серверная реализация — TASK-010–014, интеграция — TASK-016; реальное end-to-end подключение не считается проверенным по mock.


- **NET-004, серверный PROTO-007 и клиентский TODO:** сервер v3 уже поддерживает opt-in `stream: true`, partial/cancel/terminal, `PartialThrottle` и scripted-поток. Клиентский [TASK-041](../tasks/041-client-npc-stream.md) ещё не выполнен; реальные LLM-workers выдают только приватный operational progress и финал, не игровые partial. После реализации клиент заменяет временный текст полным снимком, не воспроизводит фрагменты и игнорирует поздние снимки после terminal. PROTO-007 не предоставляет durable result/preferences/reset: чтение прежнего requestId без повторной generation — будущий AI/STORE-план с отдельными согласованными операциями, не реализованный «PROTO v2». Буферы Socket.IO не должны автоматически переотправлять новые вопросы/старые отмены или неограниченно копить сообщения во время offline; состояние диалога и retry контролирует сессия.
- *(решено)* **Local/mock из серверной поставки:** в клиенте, открытом с сервера, доступен только `online`; локальная прогулка и тестовая сеть — режимы разработки (Vite) и в серверной поставке недоступны с пояснением ([OFFLINE](offline-multiplayer.md) OFFLINE-014). Публичный fallback к картам не добавляется.
- **Разделение текущего UI и серверной авторизации:** guest-форма и локальное забывание токена — существующее клиентское поведение NET-007. Пароли, сессии с отзывом и удалённый logout уже реализованы сервером; их клиентская поддержка не завершена (TASK-044). Это не основание включать guest в production или считать парольный UI готовым.

## Расширение NET для MOVE

NET-001–004 используют игровой Socket.IO v3 по PROTO. Последний jumpId удерживается между отправками до обработки, короткий Space не теряется; clear-input отменяет неотправленный прыжок без переиспользования ID. Новое соединение обнуляет счётчик, не воспроизводит ввод. Guard сохраняет исходную диагональ, если готов полный путь или допустимая касательная; конечную авторитетную позицию клиент не исправляет. motion приходит в полном upsert/snapshot; пропуск revision вызывает resync и сброс визуальной истории.
