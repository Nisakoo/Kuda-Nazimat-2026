# OBS — Наблюдаемость сервера

## Цель

По логам и метрикам после игровой сессии разработчик восстанавливает, что произошло, включая ошибки, которые не воспроизводятся. Администратор во время игры видит, всё ли в порядке, понимает причину, если нет, и видит на графиках, как менялись игроки, ping, FPS, шаг сервера и NPC за последние часы. Всё работает офлайн, на компьютере-сервере, без внешних сервисов и без утечки данных игроков. Нагрузка наблюдаемости не мешает игровому шагу.

Внешний стек Prometheus/Grafana снят (OBS-009): его роль — история метрик и графики — выполняет сам сервер (OBS-013–015, 017) на том же реестре метрик. Реализованы OBS-001–008, 010–012 ([TASK-043](../tasks/043-server-observability.md)); история, графики, минутная запись, отчёт и сбор FPS — [TASK-080](../tasks/080-server-metrics-history.md), клиентская часть — [TASK-081](../tasks/081-client-perf-telemetry-handoff.md).

## Требования

### Логи

- **OBS-001 (формат):** каждое событие — JSON-объект в одну строку:
  - `ts` (ISO 8601 с мс), `seq` (монотонный номер в процессе), `runId` (случайный ID запуска процесса), `level` (`debug`, `info`, `warn`, `error`, `fatal`), `module`, `event` (стабильный машинный идентификатор вида `auth.login.failed`), `msg` (короткий текст по-русски);
  - контекст, когда он есть: `playerId`, `accountId`, `sessionId` (AUTH-002), `connectionId`, `requestId`, `mapId`, `ip`, `durationMs`;
  - ошибка — `error: {name, message, stack, code}`; stack только для ошибок сервера, не для ошибок ввода игрока.

  Имена `event` перечислены в каталоге OBS-003 и не переименовываются без правки спеки: по ним строятся фильтры, отчёт OBS-017 и нагрузочный профиль.
- **OBS-002 (куда пишутся):**
  - **файл** `data/logs/server-<дата>-<runId>.jsonl` — всё от уровня `logs.fileLevel` (по умолчанию `debug`, кроме событий высокой частоты OBS-012). Новый файл — при старте и по достижении 20 МБ. Общий объём каталога ≤ `logs.maxTotalMb` (200 МБ) и срок ≤ `logs.retentionDays` (14): при превышении удаляются самые старые файлы. Запись асинхронная через ограниченный буфер (1 МБ); при переполнении события отбрасываются, считаются, и раз в 10 с пишется `log.dropped` с числом потерь. При `error`, `fatal` и штатной остановке буфер сбрасывается на диск до продолжения;
  - **консоль** — человекочитаемая строка от `logs.consoleLevel` (по умолчанию `info`) для администратора; формат консоли не является интерфейсом.

  Ошибка записи файла (нет места, нет прав) не останавливает игру: событие `log.sink.failed` уходит в консоль, файловый вывод повторяется раз в минуту.
- **OBS-003 (каталог обязательных событий):** перечень — минимум; новые подсистемы добавляют свои события в каталог этой спеки.

  | Область | События (уровень) |
  |---|---|
  | Процесс | `app.start` (info: окружение, версия сервера, git-коммит если доступен, Node, ОС, итоговая конфигурация без секретов), `app.start.failed` (error/fatal), `app.ready`, `app.signal`, `app.stop`, `app.stop.phase` (info: фаза и длительность), `app.stop.done`, `app.stop.failed`, `app.stop.timeout`, `auth.passwordless.enabled` (warn), `process.uncaught` и `process.unhandled_rejection` (fatal, со стеком и дампом OBS-004), `process.warning` (warn), `process.event_loop_lag` (warn: p99 задержки > 50 мс за минуту), `process.memory` (debug раз в минуту: rss, heapUsed, external) |
  | Конфигурация и мир | `config.invalid` (fatal), `world.loaded` (info на карту: чанки, worldBytes, время), ошибка мира — `app.start.failed`, `world.file.read_failed` (error), `world.access` (info при `logWorldAccess`) |
  | HTTP | `http.request` (debug для `/world/*` и state BABEL, info для остальных API: метод, шаблон пути без параметров, статус, длительность, байты, ip, sessionId), `http.failed` (error: необработанная ошибка обработчика), `http.rate_limited` (warn, агрегировано OBS-012) |
  | Вход | `auth.guest`, `auth.register`, `auth.login` (info: accountId, имя, ip, sessionId), `auth.login.failed` (warn: ключ имени, ip, причина `credentials` / `not_set` / `required` / `locked`), `auth.locked` (warn), `auth.password.changed`, `auth.logout`, `auth.session.revoked` (info: причина, число), `auth.operator.action` (info: действие, имя аккаунта), `auth.operator.rejected` (warn: действие без защиты CSRF) |
  | Realtime | `realtime.handshake.rejected` (info: код, причина, ip), `realtime.handshake.failed` (error), `realtime.connect` (info: ip, sessionId), `realtime.join` (info: mapId, ip), `realtime.disconnect` (info: причина Socket.IO и итоги соединения — отброшенный ввод, неверные пакеты, RTT), `realtime.closed_by_server` (info: причина), `realtime.packet.invalid` (debug: тип, код), `realtime.packet.flood` (warn: отключение за флуд), `realtime.rate_limited` (debug, чат) |
  | Игра | `game.seat.attach` (info: перехват, число переподключений), `game.seat.detach`, `game.seat.release` (info), `game.spawn` (debug), `game.spawn.fallback` (warn: нет свободной точки), `game.motion.recovered` (warn: recoveryReason MOVE), `game.aoi.truncated` (warn: больше 256 сущностей), `game.delta.large` (warn: пакет > 75% лимита), `game.packet.oversize` (error: пакет больше лимита, не отправлен), `game.tick.slow` (warn: шаг > 50 мс, с числом игроков), `game.tick.stats` (info раз в минуту: p50, p95, max шага и интервала рассылки) |
  | NPC и язык | `npc.request.accepted`, `npc.request.started`, `npc.request.first_partial` (debug), `npc.request.completed`, `npc.request.cancelled` (info), `npc.request.failed`, `npc.request.timeout`, `npc.request.error` (warn: исключение ответчика) — с видом (npc, npc-stream, chat, suggest, babel-npc), длительностями ожидания и генерации, длиной ответа в символах; `npc.rejected` (info), `npc.slot.stuck` (error), `npc.responder.ready`/`language.ready` (info), `npc.responder.unavailable`/`language.unavailable` (error), `babylon.action` (info: тип, результат, длительность), `babylon.language` (debug), `babylon.translation.failed` (warn) |
  | Хранилище | `db.opened` (info: путь, версия схемы), `db.operation.failed` (warn: каждая неудачная операция хранилища), `db.transaction.failed` (error: с контекстом вызывающего), `db.slow` (warn: операция > 50 мс) |
  | Админка | `admin.change` (info: действие, тип и id цели, имена изменённых полей без значений), `admin.npc.orphaned` (warn: правка NPC не применена при запуске) — [ADMIN-SRV](server-admin-content.md) |
  | Клиент | `client.error`, `client.perf` (debug, OBS-011: учитывается метриками и показателями игрока, по одному в info не пишется) |
  | Наблюдаемость | `log.dropped`, `log.sink.failed`, `obs.incident.dumped`, `invariant.violated` (OBS-005), `metrics.minute` (info раз в минуту, OBS-015) |

- **OBS-004 (бортовой самописец):** в памяти всегда хранится кольцевой буфер последних 5000 событий уровня `debug` и выше, включая события высокой частоты в сокращённой форме, независимо от уровней вывода. Он сбрасывается в файл `data/logs/incident-<ts>-<runId>.jsonl`:
  - при первом событии `error` или `fatal` (не чаще раза в минуту, следующие учитываются счётчиком в следующем дампе);
  - при `invariant.violated`;
  - по кнопке администратора «Сохранить отчёт» на `/operator`.

  Дамп содержит буфер, снимок метрик OBS-007, последние 10 минут истории OBS-013 и сводку состояния (места, соединения, очередь NPC), без секретов и текстов OBS-006. Так у плавающей ошибки есть подробная история перед ней, даже если `fileLevel` выше `debug`.
- **OBS-005 (проверки инвариантов):** в критичных местах сервер проверяет состояние и при нарушении пишет `invariant.violated` (error, имя инварианта и контекст) и продолжает работу с безопасным исходом, а не падает и не портит состояние молча. Минимальный набор:
  - позиции и скорости игроков конечны; игрок с нечисловой позицией возвращается на безопасную опору;
  - у каждого занятого места не больше одного управляющего соединения, у каждой сущности игрока есть место;
  - счётчики очереди NPC неотрицательны и совпадают с числом задач; у игрока не больше одной незавершённой задачи;
  - revision AOI каждого соединения растёт на 1 с каждой отправленной delta;
  - в снимке нет повторяющихся ID сущностей;
  - отправленный пакет проходит `parseServerMessage` (в тестах — всегда, в рантайме — `monitoring.validateOutgoing`, включён в development); неверный пакет не отправляется;
  - delta больше лимита пакета не отправляется (`game.packet.oversize`): разрыв revision заставляет клиента запросить snapshot.
- **OBS-006 (приватность):** в логи, метрики, дампы и админку никогда не попадают: токены и их хеши, пароли и их хеши, временные пароли, тексты чата, вопросов и ответов NPC, сообщений и переводов BABEL, записи словаря, рисунки камней. Отображаемое имя пишется только в событиях входа и действиях администратора, чтобы сопоставить playerId с человеком; в остальных событиях — playerId. Проверка выполняется автотестом, который прогоняет сценарии с известными секретами и текстами и ищет их во всех выводах.

### Метрики

- **OBS-007 (реестр метрик):** в процессе — счётчики, gauge и гистограммы с фиксированными границами корзин, без внешних зависимостей. Обновление метрики — O(1) и не выделяет память на горячем пути. Минимальный набор:
  - процесс: uptime, rss, heap, задержка event loop (p50/p99), число дампов, потерянные логи;
  - игра: длительность шага, интервал рассылки, игроки на местах / подключённые / в удержании, соединения, сущности в AOI, размер delta в байтах, пакеты на вход и выход по типам, отклонённые handshake по коду, неверные пакеты, срабатывания лимитов, резервные точки появления, recovery движения;
  - RTT игроков (OBS-010) — гистограмма сэмплов heartbeat;
  - клиенты (OBS-011): FPS и интервал кадра — гистограммы по отчётам `perf` с видимой вкладки; число отчётов по виду;
  - NPC и язык: длина очереди, активные генерации, результаты по исходу, время ожидания, время до первого снимка (`npc_first_partial_ms`), время генерации, зависшие слоты; действия BABEL по типу и результату с длительностью;
  - HTTP: запросы по шаблону пути и статусу, длительность, байты `/world/*`;
  - вход: исходы по типу, блокировки, отзывы по причине, действующие сессии;
  - БД: длительность транзакций, ошибки, размер файла БД и WAL, свободное место на диске.
- **OBS-008 (доступ к метрикам):**
  - `GET /api/operator/metrics` — JSON-снимок текущих значений, только loopback;
  - `GET /api/operator/history` — история для графиков (OBS-014), только loopback.

  *(Изменено 2026-11-01: `GET /metrics` в формате Prometheus и доступ к нему по `monitoring.token` сняты вместе с OBS-009 — потребителя нет; для отладки через `curl` достаточно `/api/operator/metrics`. Ключ `monitoring.token` из конфигурации удаляется, конфигурация с ним отклоняется как неизвестная.)*

  Ни один из эндпоинтов не содержит данных OBS-006 и имён игроков; имена есть только в `/api/operator/status` (OFFLINE-010).
- **OBS-009:** *(снято 2026-11-01.)* Необязательный стек Prometheus/Grafana (`ops/monitoring/`) не используется: он требовал установки с интернетом и ~300 МБ RAM рядом с бюджетом LLM, а его роль выполняют история метрик и графики в админке (OBS-013, 014), минутная запись (OBS-015) и отчёт (OBS-017). Каталог `ops/monitoring/` удаляется.

### Админка и клиент

- **OBS-010 (админка, расширение OFFLINE-010):** `/operator` — админка, доступная только на самом сервере; дополнительно к OFFLINE-010 она показывает:
  - **общее состояние** — зелёное, жёлтое или красное с перечнем причин простыми словами. Окна «за 5 мин» считаются по истории OBS-013. Правила по умолчанию: p95 шага > 5 мс за 5 мин — жёлтое, > 20 мс — красное; p95 интервала рассылки > 120 мс — жёлтое; p99 задержки event loop > 50 мс — жёлтое; NPC или переводчик недоступны — жёлтое; доля таймаутов NPC за 5 мин > 25% — жёлтое; ошибка записи в БД за 5 мин — красное; свободно на диске < 1 ГБ — жёлтое, < 200 МБ — красное; потеря логов — жёлтое; у игрока RTT > 150 мс или FPS < 30 (медиана за минуту) — жёлтое с именем игрока («медленная сеть у …», «у … тормозит картинка»);
  - **по каждому игроку:** RTT (медиана за минуту), FPS, интервал кадра и draw calls (последний отчёт OBS-011 с видимой вкладки не старше 30 с, иначе «нет данных»), давность последнего отчёта по времени приёма сервером, число переподключений за 10 мин (≥ 3 — предупреждение «нестабильная связь»), время в игре. Значения за порогом выделяются цветом;
  - **графики** — OBS-014;
  - **последние 20 событий:** предупреждения и ошибки, а также ключевые события `info` — `app.ready`, `game.seat.attach`, `game.seat.release`, `npc.responder.ready`/`unavailable`, `language.ready`/`unavailable`, `auth.operator.action`, `obs.incident.dumped`; время, уровень, короткое сообщение по-русски, событие, без текстов игроков;
  - **действия:** «Выдать временный пароль», «Завершить сессии», «Снять блокировку входа» (AUTH-010), «Сохранить отчёт» (OBS-004). Подтверждение перед действием; защита от CSRF — как AUTH-010.

  RTT измеряется сервером без участия клиентского кода: по heartbeat Engine.IO (время от отправленного сервером `ping` до полученного `pong`), интервал heartbeat — `monitoring.pingIntervalMs` (по умолчанию 5000).
- **OBS-011 (ошибки и показатели клиента):** `POST /api/telemetry/client` с Bearer-сессией принимает отчёт клиента `{v: 1, kind: "error" | "unhandled_rejection" | "perf", ...}`. Тело ≤ 8 КиБ, неизвестные поля отклоняются, ответ 204 без тела; ошибки — 400/401/429. Строки ≤ 500 символов (`stack` ≤ 4000), без текстов игроков (это обязанность клиента; сервер обрезает и экранирует).
  - **`error` / `unhandled_rejection`:** `message?, stack?, source?, build?, map?`. Лимит — 10 в минуту на сессию. Пишется как `client.error` (warn) с playerId и sessionId.
  - **`perf`** *(изменено 2026-11-01: обязателен для админки)*: клиент в игровом мире отправляет его раз в 10 с (±1 с) и сразу после входа в мир, когда накоплено ≥ 2 с кадров. Поля:

    | Поле | Тип | Смысл |
    |---|---|---|
    | `fps` | число 0–1000, обязательно | средний FPS за окно с прошлого отчёта |
    | `visible` | boolean, обязательно | вкладка видна; при `false` FPS не учитывается в порогах и графиках (новое поле) |
    | `frameMs` | число 0–10000, желательно | p95 интервала кадра за окно, мс (существующее поле) |
    | `drawCalls` | целое, желательно | draw calls последнего кадра (существующее поле) |
    | `map`, `build` | строка, необязательно | карта и сборка клиента (существующие поля) |

    Лимит — 12 в минуту на сессию, отдельно от ошибок. Сервер пишет `client.perf` на уровне debug (OBS-012), учитывает FPS и `frameMs` в метриках OBS-007 и хранит последний отчёт в показателях игрока (OBS-010) до отключения.

  Ping клиент не присылает: источник ping в админке — RTT сервера по heartbeat (OBS-010). Клиент может не отправлять отчёты — тогда в админке «нет данных», игра не меняется.
- **OBS-012 (цена наблюдаемости):** события высокой частоты (каждый `input`, каждый пакет delta, каждый запрос чанка, каждое срабатывание лимита) не пишутся по одному: они учитываются метриками, итоги соединения пишутся в `realtime.disconnect`, запросы `/world/*` и опрос state — на уровне debug. С включённой наблюдаемостью p95 шага растёт не больше чем на 0,5 мс на профиле четырёх игроков (REALTIME S7). В этот бюджет входят история OBS-013 и приём отчётов `perf`.

### История, графики и отчёт

Заменяют внешний стек OBS-009. Все требования используют один источник — историю OBS-013 — и одни пороги: они задаются в одном месте кода и одинаковы для состояния OBS-010, графиков, отчёта и нагрузочного профиля.

| Порог | Значение | Откуда |
|---|---|---|
| p95 шага | ≤ 5 мс (жёлтое > 5, красное > 20) | OFFLINE-017, OBS-010 |
| p95 интервала рассылки | ≤ 120 мс | OFFLINE-017 |
| ошибки сервера (`error`, `fatal`) | 0 | OFFLINE-017 |
| RTT игрока | ≤ 150 мс | OBS-010 |
| FPS клиента (видимая вкладка) | ≥ 30 | OBS-010, [QUALITY](client-quality.md) |
| доля таймаутов NPC | ≤ 25% | OBS-010 |
| потерянные строки журнала | 0 | OBS-002 |

- **OBS-013 (история метрик в памяти):** раз в 10 с сервер делает кадр из реестра OBS-007:
  - текущие значения gauge: игроки на местах и подключённые, очередь и активные генерации NPC, RSS и куча;
  - приращения счётчиков за интервал: записи журнала по уровню (новый счётчик `log_records_total{level}`), исходы NPC (принято, ответов, таймаутов, занято, ошибок), HTTP 5xx, ошибки БД, потерянные логи;
  - приращения корзин гистограмм за интервал: шаг, интервал рассылки, RTT, FPS клиентов, первый текст и генерация NPC. Гистограммы реестра накапливаются с запуска, поэтому окна считаются только по приращениям корзин, а не по `snapshot().p95`;
  - по каждому игроку на месте — `playerId`, RTT (медиана за минуту), последние FPS и `frameMs` с видимой вкладки; имён в кадре нет.

  Кадры хранятся в одном кольцевом буфере на 1440 кадров (4 часа); из него же считаются окна «за 5 мин», «за 60 мин» и «за час». Перцентиль окна — верхняя граница корзины, как в OBS-007; границы корзин содержат пороги из таблицы (шаг 5 и 20 мс, рассылка 120 мс, RTT 150 мс, FPS 30), чтобы проверка порога не зависела от округления. Кадр без данных (нет игроков, нет отчётов клиента) хранит `null`, а не 0. Память истории ≤ 1 МБ; кадр собирается вне игрового шага и не выделяет память на горячем пути метрик. После перезапуска история начинается с нуля; прошлые запуски разбираются отчётом OBS-017.
- **OBS-014 (данные для админки):** вид страницы — каркас, разделы, плитки, вёрстка графиков и таблиц — задаёт [ADMIN](admin-panel-ui.md); эта спека задаёт данные, которые сервер отдаёт для разделов «Обзор», «Сервер» и «Клиенты». Все значения считаются по истории OBS-013 и порогам из таблицы; отсутствующее значение — `null`, а не 0.

  `GET /api/operator/status` (раз в 2 с) дополнительно к OFFLINE-010 и OBS-010 отдаёт текущие значения для плиток и карточек:

  | Группа | Значения |
  |---|---|
  | Сервер | окружение, версия, время работы |
  | Игроки | на местах / мест, подключены, средний ping (медиана RTT подключённых), средний FPS (медиана видимых), нестабильные подключения (≥ 3 переподключений за 10 мин) |
  | Шаг и рассылка | шаг: последнее значение, p50, p95, максимум за 5 мин; рассылка: p95 и максимум за 5 мин |
  | Память и диск | RSS, куча, свободно на диске, размер БД, потерянные строки журнала, p99 задержки event loop |
  | NPC | персонажей на картах, в очереди, выполняются, незавершённых из лимита; за 5 мин — принято, ответов, таймаутов, занято, p95 первого текста, p95 генерации |
  | Ошибки | за час — всего (`error`/`fatal`), HTTP 5xx, БД; HTTP 5xx, БД и NPC за 5 и за 60 мин |
  | По игроку | показатели OBS-010 |

  `GET /api/operator/history` (раз в 10 с) отдаёт ряды на весь буфер OBS-013: `{stepMs, from, to, series: {<имя>: [[ts, value | null], …]}, players: {<playerId>: {name, rtt: [[ts, v]…], fps: [[ts, v]…]}}, thresholds}`; ответ ≤ 256 КиБ.

  | Ряд | Значения | Порог |
  |---|---|---|
  | Игроки | на местах, подключены | 4 места |
  | Шаг и рассылка | p95 шага, p95 интервала рассылки | 5 и 20 мс; 120 мс |
  | Память | RSS, куча | — |
  | NPC | p95 первого текста, p95 генерации, очередь, таймауты и ошибки за интервал | — |
  | Ошибки | `error`/`fatal` и `warn` за интервал | — |
  | Ping и FPS по игрокам | RTT и FPS каждого игрока на месте | 150 мс; 30 |

  Ряды по игрокам — единственное место истории с именами (как `/api/operator/status`, OFFLINE-010). Графики рисует скрипт страницы без библиотек и внешних ресурсов (CSP не меняется), разрывы — на `null`, подписи времени — по часам сервера. Переключателя периода нет: ряд охватывает весь буфер.
- **OBS-015 (минутная запись метрик):** раз в минуту сервер пишет событие `metrics.minute` (info) в тот же журнал `server-*.jsonl` — с его ротацией, лимитом объёма и сроком хранения (OBS-002). Это минутный агрегат истории OBS-013: игроки (на местах, подключены, пик), перцентили шага, рассылки, RTT и FPS, исходы NPC и перцентили первого текста и генерации, ошибки и предупреждения, потерянные логи, RSS, куча и свободное место на диске, показатели по `playerId`. Отсутствующее значение — `null`; имён и текстов нет; строка ≤ 2 КиБ. Разбор без сервера: `jq 'select(.event=="metrics.minute")'`; пример выгрузки в CSV — в README сервера.
- **OBS-016:** *(снято 2026-11-01.)* Отдельный итог `app.session.summary` при остановке дублировал отчёт: его поглощает OBS-017.
- **OBS-017 (отчёт приёмки):** `npm --prefix server run report [-- --env <окружение>] [--file <путь>] [--since <ISO> | --last <длительность, например 2h>]` читает журнал без запущенного сервера. По умолчанию — последний запуск в каталоге логов окружения (файлы одного `runId` после ротации объединяются); `--since` / `--last` выбирают период, в том числе через несколько запусков. Источники: `app.start` (окружение, версия, Node, ОС), `metrics.minute`, `game.tick.stats`.
  - Выводит markdown-таблицу «показатель — значение — порог — итог» по таблице порогов и шапку: runId, окружение, период, пик игроков. Таблица вставляется в задачу как свидетельство OFFLINE-019.
  - Отсутствие данных — «нет данных» и никогда не «в норме»: например, FPS без отчётов клиента.
  - Код выхода отличен от 0 только при ошибке чтения журнала или аргументов.

  При штатной остановке сервер печатает эту же таблицу за текущий запуск в консоль. Нагрузочный профиль REALTIME S7 считает и печатает её той же функцией и с теми же порогами, вместо собственного разбора событий.

## Сценарии

- **S1 · OBS-001–003:** Given запуск, вход двух игроков, чат, вопрос NPC, BABEL-покупка, выход и остановка; When читается файл логов; Then каждое действие оставило событие из каталога с playerId/sessionId/requestId, каждая строка — валидный JSON с `ts`, `seq`, `runId`, `level`, `event`.
- **S2 · OBS-004:** Given `fileLevel: info`; When обработчик HTTP бросает исключение; Then в файле есть `http.failed` со стеком, а в `incident-*.jsonl` — предшествующие debug-события этого запроса, снимок метрик и последние 10 минут истории.
- **S3 · OBS-002:** Given лимит каталога 1 МБ в тесте; When пишется 5 МБ событий; Then каталог не превышает лимит, старые файлы удалены. Given недоступный каталог; Then игра продолжает работать, в консоли `log.sink.failed`.
- **S4 · OBS-005:** Given в тесте позиция игрока стала NaN; When выполняется шаг; Then `invariant.violated` с именем инварианта, игрок на безопасной опоре, остальные игроки не затронуты, создан дамп.
- **S5 · OBS-006:** Given сценарий с паролем «секрет12», чатом «тайное слово» и вопросом NPC; When просмотрены консоль, файлы, дампы, `metrics.minute`, отчёт OBS-017, `/api/operator/metrics`, `/api/operator/history` и `/api/operator/status`; Then ни пароля, ни токена, ни хешей, ни текстов нет.
- **S6 · OBS-007–008:** Given сервер с игроками; When запрошены `/api/operator/metrics` и `/api/operator/history` с loopback и из сети, а также `/metrics`; Then с loopback 200, из сети 404, `/metrics` — 404; в снимке есть метрики шага, игроков, RTT и NPC. Конфигурация с `monitoring.token` отклоняется при запуске.
- **S7 · OBS-010:** Given NPC-ответчик не стартовал и у игрока три переподключения; When администратор открывает `/operator`; Then состояние жёлтое с причинами «NPC недоступны» и «нестабильная связь у игрока …», у игроков видны RTT. When администратор нажимает «Сохранить отчёт»; Then появляется файл дампа.
- **S8 · OBS-011:** Given клиент отправляет 12 отчётов об ошибке за минуту; Then первые 10 — 204 и записаны как `client.error`, остальные — 429; отчёт с лишним полем — 400. Given в ту же минуту 12 отчётов `perf`; Then все 204 — лимиты раздельные; тринадцатый — 429.
- **S9 · OBS-012:** Given профиль REALTIME S7 с наблюдаемостью (включая историю OBS-013 и отчёты `perf` четырёх клиентов) и без; Then разница p95 шага ≤ 0,5 мс, `log.dropped` нет.
- **S10 · OBS-010–011:** Given три игрока: первый присылает `perf` с `fps: 58, frameMs: 18, drawCalls: 240, visible: true`, второй — с `fps: 22, visible: true`, третий отчётов не шлёт; When запрошен `/api/operator/status`; Then у первого FPS 58, кадр 18 мс, 240 draw calls и давность отчёта в секундах, у второго FPS 22 и состояние жёлтое с причиной «у … тормозит картинка», у третьего «нет данных»; ping есть у всех троих. Given второй присылает `visible: false`; Then его FPS не влияет на состояние и графики.
- **S11 · OBS-013:** Given искусственные часы и метрики с известными значениями; When проходит 5 часов кадров; Then буфер содержит последние 4 часа с показателями игроков; p95 шага за последние 5 мин отражает только эти 5 мин (после часа медленных шагов и 5 мин быстрых — быстрые); ошибки за 5 и за 60 мин считаются раздельно; память истории ≤ 1 МБ; кадр без игроков и без отчётов клиента даёт `null`, а не 0.
- **S13 · OBS-014:** Given сервер с двумя игроками 3 мин и одним вопросом NPC; When запрошены `/api/operator/status` и `/api/operator/history`; Then есть все группы и ряды из таблиц OBS-014, включая ряды ping и FPS по каждому игроку и p95 первого текста NPC; ответ истории ≤ 256 КиБ и без текстов OBS-006; разделы ADMIN «Обзор», «Сервер», «Клиенты» строятся из этих данных без внешних запросов.
- **S14 · OBS-015:** Given сервер проработал 3 мин; Then в `server-*.jsonl` три события `metrics.minute`, каждое — валидный JSON ≤ 2 КиБ без имён игроков.
- **S16 · OBS-017:** Given журнал запуска с пиком 3 игрока, одним `error` и двумя таймаутами NPC, клиенты без `perf`; When `npm --prefix server run report`; Then markdown-таблица с пиком 3, «превышен» у ошибок сервера, долей таймаутов и «нет данных» у FPS. When тот же сервер штатно остановлен; Then в консоли та же таблица. Given `--last 2h` и два запуска за этот период; Then таблица объединяет оба. Given пустой каталог логов; Then «нет данных» во всех строках. Given профиль REALTIME S7; Then он печатает ту же таблицу.

## Ограничения и вне scope

- Отправка логов и метрик за пределы компьютера-сервера, облачные сервисы, внешние сборщики и дашборды (Prometheus, Grafana, Loki, Elasticsearch) — вне scope.
- История хранится в памяти (4 часа) и в минутных событиях журнала; отдельной базы временных рядов нет. Более ранние периоды и сравнение запусков — через отчёт OBS-017 по файлам журнала.
- Вход в админку под отдельной ролью администратора не требуется: `/operator` доступен только на самом сервере (OFFLINE-010, AUTH-010). Пользователь в углу макета — не требование.
- Распределённая трассировка не нужна: процесс один, связь событий — через `requestId`, `connectionId` и `sessionId`.
- Метрики LLM (токены, память модели) добавляет адаптер модели через тот же реестр метрик ([LLM](server-llm-runtime.md)); их набор задаёт LLM-QA.

## Передача клиенту

Передача — [TASK-081](../tasks/081-client-perf-telemetry-handoff.md); первая часть контракта (ошибки) была в [TASK-044](../tasks/044-client-auth-observability-handoff.md).

**Клиенту нужно сделать для админки:**
1. **FPS (обязательно для требования «FPS и ping всех клиентов»):** в игровом мире раз в 10 с и после входа в мир отправлять `POST /api/telemetry/client` с `kind: "perf"`, `fps` и `visible`. FPS — по `requestAnimationFrame` за окно с прошлого отчёта; при скрытой вкладке — отчёт с `visible: false`.
2. **Желательно:** `frameMs` (p95 интервала кадра) и `drawCalls` — колонки «Кадр, мс» и «Draw calls» в разделе «Клиенты» (ADMIN-014). `map`, `build` — по желанию.
3. **Ошибки:** `kind: "error"` и `"unhandled_rejection"` из `window.onerror` и `unhandledrejection` — необязательно, но без них график «Ошибки» показывает только сервер.
4. Отправка не мешает игре: не чаще лимита, без повторов при 429, тихо при 401 и ошибке сети, без текстов игроков и имён в полях.

Ping клиенту присылать не нужно: сервер измеряет RTT сам по heartbeat Engine.IO (OBS-010).

## Открытые вопросы

- Пороги OBS-010 выбраны по текущему профилю (p95 шага ≈ 1,3 мс, рассылки ≈ 110 мс) и уточняются после замеров на целевых ноутбуках (OFFLINE-017). Пороги RTT 150 мс и FPS 30 — предварительные: RTT по Wi-Fi и FPS слабых ноутбуков ещё не измерялись.
- Нужен ли администратору просмотр файлов логов прямо на `/operator` или достаточно кнопки «Сохранить отчёт».
