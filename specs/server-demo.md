# SERVER-DEMO — Готовность бэкенда к защите

## Цель

Регламент защиты — 6 минут: идея, 3D-мир, мультиплеер, ИИ, архитектура. Бэкенд должен сделать каждый блок показуемым без импровизации: запуск одной командой, вход по имени, видимые данные игроков, NPC с индивидуальностью и памятью (через порт, без реальной LLM), схема архитектуры. Реальная LLM в эту спеку не входит.

| Время | Блок регламента | Что обеспечивает бэкенд |
|---|---|---|
| 00:30–02:00 | 3D-мир, перемещение, взаимодействие | раздача клиента и мира, авторитетное движение, `interact` с NPC |
| 02:00–03:00 | второй игрок, синхронизация | вход под вторым именем, AOI/delta |
| 03:00–04:00 | ИИ-агент, индивидуальность, память | профиль NPC, история в SQLite, заглушка с памятью, порт для LLM |
| 04:00–05:00 | архитектура, кеш, данные, авторизация | схема в architecture.md, `inspect`, лог доступа к чанкам, mock-вход и токен (AUTH) |

## Требования

- **SERVER-DEMO-001 (запуск):** `make demo` из корня выполняет все шаги и печатает адреса для открытия: `http://localhost:<port>/` и `http://<LAN-IPv4>:<port>/` для каждого не-loopback интерфейса.
  1. `npm --prefix client ci` и `npm --prefix server ci`, если нет `node_modules`;
  2. сборка клиента;
  3. генерация демо-мира (входит в сборку клиента);
  4. миграции;
  5. запуск сервера.

  Если не хватает собранного клиента или мира, `make server` завершается с подсказкой, какую команду выполнить. Всё работает без интернета после подготовки зависимостей.
- **SERVER-DEMO-002:** *(снято.)* Отдельный CLI аккаунтов не нужен: при mock-входе игрок создаётся при первом входе под новым именем (AUTH-001). Список игроков показывает `inspect`.
- **SERVER-DEMO-003 (данные игроков):** CLI `npm --prefix server run inspect` выводит таблицы из SQLite:
  - аккаунты: имя, создан;
  - игроки: playerId, карта, позиция, обновлён;
  - число действующих сессий;
  - число записей диалогов по паре игрок/NPC и последний вопрос каждой пары, усечённый до 60 символов.

  Хеши токенов, токены и полные тексты не выводятся. Чтение не блокирует работающий сервер (WAL). Команда показывает путь к файлу БД. Так на защите видно, где и что хранится.
- **SERVER-DEMO-004 (подгрузка и кеш):** Конфигурация `logWorldAccess: true` (по умолчанию false) пишет в лог для каждого ответа `/world/*`: playerId, путь ресурса, статус 200/404, размер. Тексты и токены не пишутся. При старте сервер пишет в лог для каждой карты `worldBytes`, лимит кеша клиента (10%) и число чанков. Так видно, что сервер выдаёт только окрестность игрока, а не весь мир.
- **SERVER-DEMO-005 (индивидуальность NPC):** `npcs.json` содержит для каждого NPC `persona` (1–500 символов: характер, манера речи) и `greeting`. Профиль передаётся в `NpcAnswerRequest.npc` (NPC-005). `interactable.label` NPC — его тема («История», «Наука»): клиент показывает её в заголовке диалога. Демо-NPC рынка: торговец фруктами (радушный, расхваливает финики), торговка тканями (неторопливая, рассказывает об узорах), гончар (ворчливый мастер, говорит о глине и обжиге), пастух (простой и внимательный, знает приметы и корм каждой козы). На карте `demo` остаются Лея (история) и Марк (наука).
- **SERVER-DEMO-006 (память в заглушке):** Заглушка `scripted` демонстрирует путь памяти без LLM. Первый вопрос к NPC получает приветствие персоны и ответ по теме. Повторный вопрос, в том числе после переподключения и перезапуска сервера, явно ссылается на предыдущий вопрос из истории («В прошлый раз ты спрашивал: “…”»). Тот же вопрос, что в прошлый раз, получает другое объяснение. Ответ строится только из `request` (персона, история), без доступа к БД. Это показывает, что история хранится на сервере и доходит до ответчика; адаптивность модели здесь не утверждается.
- **SERVER-DEMO-007:** *(отложено.)* CLI-бот второго игрока не входит в MVP: второго игрока показывают второй вкладкой браузера или вторым ноутбуком.
- **SERVER-DEMO-008 (схема архитектуры):** В architecture.md есть Mermaid-диаграмма клиент-серверной архитектуры. На ней видно:
  - браузеры и модули клиента;
  - каналы HTTP `/`, `/config.json`, `/api/auth/*`, `/world/*` и Socket.IO `/game`;
  - модули сервера по слоям, SQLite с таблицами;
  - порт NpcResponder с заглушкой и будущим адаптером LLM;
  - `shared/` как общий контракт.

  Рядом — короткие пояснения по подгрузке/кешу, хранению и авторизации, пригодные для показа на защите.
- **SERVER-DEMO-009 (сценарий):** README сервера содержит раздел «Сценарий защиты» с проверенными шагами по регламенту: команды, адреса, логины, что показать в каждом блоке и запасные действия при сбое (повторный вход, `inspect`).

## Внешняя зависимость от клиента

Клиент сам не получает серверную сессию: `GameApp.provideServerSession()` вызывается только в тестах, а `parseConfig` не принимает токен. Без клиентской правки браузер не подключится к серверу, и блоки «мультиплеер» и «ИИ» в браузере не показать. Минимальная правка — клиентская задача по NET-007, контракт сервера готов (AUTH-006):

1. В режиме `online` без сессии запросить имя игрока (одно поле).
2. Отправить `POST <serverUrl>/api/auth/guest` с телом `{name}`.
3. Передать JSON ответа (`{token, expiresAt}`) в `GameApp.provideServerSession()`, ошибку `{error: {message}}` показать текстом.

## Сценарии

- **S1 · SERVER-DEMO-001:** Given чистый клон с подготовленными зависимостями и без интернета; When выполнен `make demo`; Then сервер запущен и печатает localhost- и LAN-адреса; повторный `make demo` не теряет игроков и историю.
- **S2 · SERVER-DEMO-003–004:** Given «Аня» походила и задала NPC 2 вопроса; When выполнен `inspect`, а в логе включён `logWorldAccess`; Then видны позиция и число диалогов «Ани» без секретов, а в логе — только чанки около игрока и 404 для дальнего чанка.
- **S3 · SERVER-DEMO-005–006:** Given «Аня» спросила пастуха «Что ест козёнок?»; When она переподключается, сервер перезапускается, и она входит под тем же именем и спрашивает снова; Then ответ ссылается на прошлый вопрос и отличается от первого, стиль пастуха отличается от стиля гончара на тот же вопрос.
- **S5 · SERVER-DEMO-008–009:** Given README и architecture.md; When команда репетирует защиту по сценарию; Then все команды выполняются как написано, диаграмма отрисовывается в GitHub.

## Ограничения и вне scope

- Реальная LLM, качество и скорость ответов — AI/LLM/LLM-QA. Заглушка не выдаётся на защите за адаптивный ИИ: в сценарии она названа заглушкой порта, к которому подключается модель.
- Клиентский вызов mock-входа — клиентская задача (раздел выше).
- Физическая проверка на втором ноутбуке и с выключенным Wi-Fi — DEMO/TASK-016.
