# Обновление подготовленной LLM-установки после синхронизации main

Это **не новая установка**: модели, tokenizer, pins, venv, `~/kuda-llm/profiles.json` и `server/config.json` сохраняются. Не повторяйте `pull` модели, `make llm-import`, создание manifest или установку Python. Подробности новой установки — [SETUP](SETUP.md).

## Что изменилось

- Ветка LLM перебазирована на main398d2fb: история `npc-llm-clean-start` переписана. Обычный `git pull --ff-only` из прежней истории может отказать — это не потеря модели.
- Игровой протокол **v3**: клиент и сервер должны быть одной версии. Старый dist/старая открытая вкладка v1/v2 не подходят.
- `make server` — development с входом по имени. `make start`/`make demo` — production с обязательным паролем; парольный UI пока ожидает TASK-044.
- Новая серверная SQLite-схема мигрируется при запуске. **Перед первым запуском новой версии сделайте backup**. Откат одного кода поверх уже мигрированной рабочей БД не считается безопасным восстановлением.
- На рынке E открывает механики BABEL через отдельный LanguagePort, пока test. Наши Ollama/MLX подключены к NpcResponder. Для проверки настоящего LLM-диалога выберите **demo** (Лея/Марк), не выдавайте BABEL-заглушку за модель.
- Make `NPC_TIMEOUT=120` продолжает означать120секунд на запрос, включая очередь. Профиль не переписывается, клиент узнаёт срок от сервера и ждёт плюс2с.

## Безопасный порядок

1. Остановить игру Ctrl+C, дождаться штатного завершения. При сообщении о неподтверждённом cleanup не запускать ещё один runtime. Не менять config/БД параллельно.
2. До переключения версии сделать backup БД, используя **прежний config и прежний код**. Имя backup должно быть новым:

   ```sh
   npm --prefix server run backup -- "$HOME/kuda-llm/game-before-main-sync.sqlite"
   ```

   При нестандартном config добавить `--config /absolute/game.json`. Команда отказывает при существующем файле; не удалять его ради повторного запуска. Сохранить также копии config/profiles отдельно, не публиковать их в git. Проверить вывод и путь исходной БД. Если база отсутствует либо выбрано другое окружение, остановиться и выяснить, какая база использовалась; не принимать новый пустой файл за backup.

3. Проверить `git status --short`. Если есть свои изменения — сохранить их отдельно и согласовать перенос, не выполнять reset/clean. Подготовленные ignored config/веса должны остаться вне git.
4. Получить remote: `git fetch origin`. Если прежняя локальная ветка больше не fast-forward, можно **не сбрасывать её**, а создать новую локальную ветку в том же checkout:

   ```sh
   git switch -c local/llm-main-sync origin/npc-llm-clean-start
   ```

   Выполнять только после проверки чистого tracked worktree. Если такое имя уже существует — остановиться, выбрать новое осмысленное имя, не удалять существующую ветку. Это не второй clone, прежняя локальная ветка с историей сохраняется. Игнорируемые config/weights не переносятся в git и не должны удаляться.
5. С подготовленным Node24 проверить зависимости по lockfile новой версии. Если lockfile действительно изменился, обновить только соответствующие npm dependencies на этапе подготовки с интернетом/кешем. Не переустанавливать Python/модели автоматически.
6. Один раз собрать актуальный клиент/мир:

   ```sh
   npm --prefix client run build
   ```

7. Запустить подготовленную модель без повторного импортера:

   ```sh
   HOST=127.0.0.1 make server NPC_TIMEOUT=120
   ```

   Если `dbPath` явно задан в прежнем config, он сохраняется. Без явного dbPath development теперь использует `server/data/dev.sqlite`, production — `server/data/game.sqlite`: не путать смену окружения с потерей данных. Чтобы продолжить прежний мир/аккаунты в development, после backup явно укажите прежнюю БД одним полем dbPath, не заменяя остальной config. Для обычного server/config.json и прежнего server/data/game.sqlite это `"dbPath": "data/game.sqlite"`; при другом расположении использовать проверенный абсолютный путь. Не копировать наугад пустую dev.sqlite поверх прежней БД. Production не использовать для старого name-only UI.
8. Перезагрузить страницу после сборки, проверить профиль/timeout и `npc: ready`. Для текущей LLM-пробы выбрать `demo` в настройках карты. Не заменять весь config ради одной карты; свежая инструкция SETUP создаёт demo по умолчанию.

Реальные тесты RAM/качества/производительности и offline/LAN выполняются отдельно на компьютере оператора. Документация и rebase не превращают непроверенный профиль в квалифицированный.
